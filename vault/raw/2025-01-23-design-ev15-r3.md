# EV-15 round 3 — design position

## Design position

I **accept the principal's boundary-expansion framing**. The `login.urlPrompt` key lands, but as a *named* boundary expansion — not as an implicit row addition to `indonesianCopy`. The card author must do three explicit things in the same PR: (a) add the en row to the home that feeds `englishDefaults` (a `LOGIN_PROMPT_ROW` constant next to `NON_FAILURE_ROWS`, so the row lives in `login.ts`'s vocabulary, not in `FOOTER_ROWS` — that is the right home because it is a login-flow prompt, not a footer state); (b) add the id row to `indonesianCopy`; (c) edit `test/copy.test.ts`'s derivation (`test/copy.test.ts:77-85`) to include `login.urlPrompt` in an *explicitly-tagged covered set*, not silently pad `expected`. The boundary is renamed in `src/copy.ts`'s header from "22 keys" to "23 keys, including the login prompt" and the change is named in the PR description as a single sentence: "the consent prompt at the `/rc:login` entry becomes locale-aware via a new key `login.urlPrompt`; `test/copy.test.ts`'s drift alarm is updated to derive from `tunnelReasonCopy ∪ FOOTER_ROWS ∪ ["login.urlPrompt"]`." Net count: **23 keys with an explicitly-named expansion**, not the designer's #12 as written (which the principal correctly identified as a silent hand-edit of a data-derived assertion).

The justification that survives the framing check: my round-2 argument that the prompt is *the first user-perceived text on a fresh host* is not weakened by the principal's finding — it is strengthened. The principal's evidence is that the prompt's keyless state is a *documented gap* (`src/copy.ts:39-41`), not a feature. A documented gap that becomes a user-facing consent moment is exactly the case the boundary was drawn to police, which is why the boundary must be lifted deliberately and not stretched by accident.

## Gulf closed

Gulf of Evaluation, for a fresh host running `/rc:login` under `setLocale("id")`: today the user sees an English prompt regardless of locale — a partial-coverage surface that promises localizable copy in some places and English-by-design in others without telling the user which is which. After EV-15, the *consent sentence* — the only place a user makes a binding decision about which server they enroll against — joins the localized vocabulary, while the 28 login-flow rows (`src/copy.ts:39-41`) remain English-by-design because they are mechanical, not consent. The boundary's distinction (consent vs. mechanical) becomes legible on the surface instead of living only in the header comment.

## Principle and evidence

- **Signifier**: the consent moment at `/rc:login` needs a stated sentence in the user's chosen language, not a parenthetical in English. The current keyless literal at `index.ts:610` is "Control-plane server URL (or leave blank for PI_REMOTE_SERVER_URL / piRemote.serverUrl):" — that is documentation of internal plumbing, not a consent sentence, and it is in English regardless of locale.
- **Conceptual model**: under `id` locale, a user who reads `Daftarkan host ini ke \`<serverUrl>\` — tekan Enter untuk menggunakan server ini, atau ketik URL lain:` forms the model "I am consenting to *this* URL; I may type to override." The English-only literal forces them to *guess* what the brackets mean or to read plumbing names (`PI_REMOTE_SERVER_URL`) they have no reason to know. The wrong conceptual model invites the slip (press Enter thinking "skip," enroll against the relay).
- **Knowledge in the world, not the head**: today the user must know that bracket-prefill is a convention (or be told) for the prompt to be readable. After, the locale-aware sentence teaches the convention in the user's language.
- **Boundary expansion principle (the principal's instrument, restated)**: a documented partial-coverage boundary is a load-bearing claim about what the product vouches for and what it doesn't. Lifting it is a design decision, not a bookkeeping entry. The header comment in `src/copy.ts` exists precisely so the boundary is announced at the surface; editing it is the announcement, not a side effect of a row addition.

## Dispute 2 — `readCredential` tightening

The design position does not resolve this. My consent/feedback argument (the persisted credential's `serverUrl` is the user's "what server am I on" feedback, so its file-on-disk value must equal the consent prompt's prefill) argues *for* the tightening: if the resolver accepts `credential: ""` as a valid tier-3 input, a hand-edited credential silently enrolls against `https://relay.jumpseat.sh` with a token minted elsewhere, and the user's "what server am I on" feedback becomes *the literal default* even though the user consented to a different URL. That is the inverse of the forcing-function half of the prompt design. The owner's regression-prevention frame and the design frame point the same way. I land with **owner**: in-scope. The principal's "unreachable through shipped code" claim is correct for the shipped path; it is also correct that the resolver being total is what removes the only existing guard. Removing the only existing guard on a credential-integrity invariant while widening the tier that consumes the credential is exactly the regression this card introduces, not pre-existing debt.

## Dispute 3 — footer mechanism (R2-1 holds under either)

R2-1 (`status.off` footer equals the literal row, no `<serverUrl>`, no default URL substring, when no active dial) holds under either the owner's refreshed closure cache or the principal's per-emission `ErrorSource` threading, with one named caveat: under either mechanism, the *non-error* footer path must remain ignorant of `serverUrl`. The principal's framing — `errorSentence` consults `activeHttp?.serverUrl ?? source.serverUrl`; `renderFooter` already ignores `serverUrl` for non-error states — is the cleaner one because it requires no closure-cache bookkeeping at all. The owner's framing can produce the same result, but only if the cache is *only* read by the error branch; the natural reading of "initialize at construction, refresh at the three resolve sites" tempts a future maintainer to use it from the non-error branch, which would silently violate R2-1. I prefer the principal's mechanism on this ground. Either way, R2-1 is the binding test, and it pins.

## Preferences, ranked last

- I prefer the consent sentence to embed `<serverUrl>` directly in the clause that names the server, not as a trailing parenthetical. Grounded — mirrors `tunnel.error.unreachable` (src/login.ts:131) and the success line.
- I prefer the prompt verb to remain "Enroll this host against" in English (matching `login.attended.success`), not "Connect to" or "Sign in to." Taste, not strongly held.
- I have no preference on the bracket-vs-angle default-convention marker in the prompt title; both are legible. Ranked last.

## What I am not overturning

The resolver's total return type, the `readCredential` predicate, the headless-skip behavior, the load-time stays-explicit-only tier, and the `noServerUrl`/`rc.serverUrlRequired` removal all stand. This round's dispute is about the copy-key boundary — not the resolver, not the credential contract, not the footer source.
