## 3.1 Tunnel objects and lifecycle

A tunnel is a (tenant, host session instance) pair with a server-assigned `tunnelId` — an opaque, URL-safe string, globally unique across all tenants. Normative lifecycle: *created* (POST success) → *live* (its single connection token consumed at a successful upgrade) → *spent* (connection ended) or *deleted* (DELETE). Exactly one connection token per tunnel and exactly one successful upgrade per tunnel — a spent tunnel is never re-connectable; a new connection requires a new POST.

**"Live" is normatively defined as: the tunnel's host data-plane WebSocket is currently connected.** Socket state, never row existence. A socket that is closed or fails the server's liveness detection MUST be treated as not live. This definition is what makes the no-double-create rule (§3.2) implementable without deadlocking a crashed-and-restarted host, whose fresh create arrives with no prior delete on the wire (its best-effort teardown notification was lost with the crash).

**Reframed card sentence (normative prose obligation):** the connection token is self-describing in that **no lookup is required to interpret the token's claims**. Single-use consumption and post-deletion rejection are inherently stateful; §3.4 and §3.5 name the two bounded pieces of required server state (the consumed-`jti` set and the live-tunnel existence record) as REQUIRED, not as exceptions to a claimed statelessness.

## 3.2 Tunnel creation — `POST /tunnels`

Fixed path on the configured control-plane origin (the origin of §2.1 discovery) — endpoints are not discovered. `Authorization: Bearer <access token>` REQUIRED; §2.6/§2.7 semantics govern; tenancy is derived solely from the token's `tenant_id` (§2.6); any tenant-like request field MUST be ignored.

Request body `application/json`, all four fields REQUIRED (camelCase — these are the wire names an interoperating host parses):

| Field | Requirement | Meaning |
| --- | --- | --- |
| `sessionId` | REQUIRED | Non-empty string; the host session's stable identifier; treated as opaque by the server. |
| `sessionName` | REQUIRED | Non-empty string; display name; informational. |
| `cwd` | REQUIRED | Non-empty string; informational; the server MUST NOT interpret it. |
| `hostMetadata` | REQUIRED | JSON object with string keys and string values; MAY be empty; informational. |

Server validation MUST reject a missing/unparseable body, a missing or wrong-typed field, or a non-object `hostMetadata` with `400 invalid_request`. The server MUST accept all values within stated maxima and MAY reject beyond them with `400`: sessionId ≤ 128 chars, sessionName ≤ 256, cwd ≤ 1024, hostMetadata ≤ 32 entries with keys and values ≤ 256. (These maxima are guidance-grade; the owner MAY adjust them, but the accept-within/reject-beyond rule is normative.) Unknown request fields MUST be ignored. The request carries **no TTL field**; the TTL is server-chosen (§3.3).

Response **`200`** (not 201 — one shape) with `application/json`, all REQUIRED:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `tunnelId` | REQUIRED | Server-assigned, globally unique, URL-safe (unreserved URL characters only). |
| `url` | REQUIRED | Absolute `wss://` URL per §3.3. |
| `tokenTtl` | REQUIRED | Positive integer seconds, equal to the issued token's actual validity window (`exp` minus mint time). |

`sessionId`/`sessionName`/`cwd`/`hostMetadata` are retained as tunnel metadata and relayed to granted client devices; the server never interprets them (INV-1's spirit extended to metadata).

**No-double-create (normative on both sides, asymmetric):**

- Host-side expectation, normative: a host MUST NOT issue a second create while a tunnel it created is live; its correct behavior is a local no-op with a notification.
- Server-side enforcement, MUST: a server MUST reject with `409 tunnel_already_live` a create that would produce a second **live** tunnel for the same (tenant, `sessionId`) pair — live per §3.1's socket-state definition. Never-connected tunnels and spent tunnels MUST NOT block a create. Rationale stated on the page: issuing a fresh tunnel on collision would let a crashed host fork the single ordered frame stream across two live sockets, violating INV-1's single-producer ordering. Keyed on socket state, this MUST is deadlock-free: the reachable collision cases (crash recovery with the teardown notification lost; half-open sockets) self-heal — the client maps `409` on create into its generic retryable class and re-creates with backoff.
- A new POST SHOULD supersede any prior unconsumed token for that session (harmless regardless — single-use + `exp`); the owner refines or drops this SHOULD with a mechanism, or leaves superseding as a server-internal detail (O12 drafting item).
- Guidance: SHOULD reap unresponsive data-plane sockets promptly (ping timeout well under the token TTL), bounding the collision window.

## 3.3 The signed one-time connection URL

Shape: `wss://<data-plane host>/<tunnelId>?token=<token>`. Normative: scheme MUST be `wss` (`ws` MUST NOT be issued); the token rides in exactly one query parameter named `token`; the path's final segment MUST equal the `tunnelId`; the authority MAY differ from the control-plane origin (a dedicated data-plane host is permitted); no userinfo, no fragment.

The token is a **compact JWS** — three base64url segments — signed with a server-held key; hosts never hold signing keys. Claim verification requires no lookup (the claims are read off the verified token). **Claims — snake_case, consistent with §2.6's claim table:**

| Claim | Requirement | Meaning |
| --- | --- | --- |
| `tenant_id` | REQUIRED | MUST equal the creating enrollment token's `tenant_id` — INV-3's second contract point. |
| `tunnel_id` | REQUIRED | MUST equal the URL path segment. |
| `session_id` | REQUIRED | Echo of the create request's `sessionId`. |
| `exp` | REQUIRED | Expiry, in seconds since the epoch. |
| `jti` | REQUIRED | Unique per issued token — the single-use consumption identity. |
| `iat` / `iss` / `aud` | SHOULD | Standard JWT provenance claims. |

**TTL:** default 60 seconds (SHOULD); normative bounds: an issued TTL MUST be ≥ 5 s and ≤ 300 s; configured values clamp to the nearest bound (a misconfigured value is a workable token, not a boot failure). `tokenTtl` in the create response MUST equal `exp` minus mint time. Expiry is judged by the **server's clock** at upgrade only; the server MUST NOT rely on any host clock. A host's local pre-expiry check is advisory (a host-computed convenience, never a server-reported fact).

Guidance (one recommended shape): asymmetric signing with a rotating key pair, so token verification can be delegated to data-plane replicas; the consumed-`jti` record need only live until `exp` plus a small leeway, after which expiry rejection alone covers the token, so the store garbage-collects itself.

## 3.4 Token consumption at the WebSocket upgrade

The upgrade is the WebSocket opening handshake — an HTTP GET against the URL. Authentication happens strictly before `101`: a server MUST NOT accept the upgrade and reject afterwards.

Ordered checks, each named distinctly on the page (the distinction lives here, not in code strings — O10/O13 drafting item), then **atomic consumption**:

1. Extract the token: URL-level malformation — wrong scheme, missing `?token=`, non-single-segment path — is `400`.
2. Verify the signature → `401` on failure.
3. Check `exp` against the server clock → `401` on expiry.
4. Verify the path/claim bindings (path `tunnelId` = claim `tunnel_id`) and the live-tunnel existence record (tunnel exists, not deleted) → `401` on binding mismatch; `404` on absent/deleted tunnel.
5. **Atomically** mark `jti` consumed before sending `101`. Two simultaneous upgrades with one token: exactly one `101`; the other gets the replay rejection.

**Handshake closed partition: `{101, 400, 401, 404, 409, 5xx}`.** A server emitting any other status on this surface is non-conformant.

| Status | `error` | Failure |
| --- | --- | --- |
| `400` | `invalid_request` | No extractable token (URL-level malformation). |
| `401` | `invalid_token` | Single code for all does-not-authenticate cases: bad signature, expired, malformed token, binding mismatch. |
| `404` | `unknown_tunnel` | Token authenticates; tunnel deleted or never existed. No existence leak: an attacker without a valid signature is rejected `401` before any tunnel lookup. |
| `409` | `token_consumed` | Replay — the token's consumed state conflicts with the single-use rule (settled: §2.7 pins `403` to exactly one meaning, insufficient scope; a spent token is not that, so replay is `409`, making `409` mean state conflict uniformly with `tunnel_already_live`). |

These are diagnostic for operators: the dialing side treats any non-101 as a failed handshake with one uniform remedy — create a fresh tunnel and dial again; it does not parse handshake statuses or bodies. The handshake's 401/403-semantics *mirror* §2.7's axis (401 = does not authenticate; 403 would mean authenticates-but-not-authorized) but are the data plane's own contract with its own codes — the page states this so §2.7's `insufficient_scope` meaning is never read onto this surface. Post-upgrade socket close codes are §4's business; §3 defers there.

## 3.5 Tunnel deletion — `DELETE /tunnels/{tunnelId}`

Bearer-authenticated; tenancy derived from the token. Idempotent. Success: `204 No Content`, no body. Unknown, already-deleted, or another tenant's tunnel id: `404` — never `403` (no cross-tenant existence leak), and a repeated delete is indistinguishable from a first success. **`404`-only: no `410`, no deletion tombstone.** The absence of the live-tunnel record IS the `404` — "discards token state" means literal discard.

On success the server MUST do all of: (a) invalidate any un-consumed connection token for that tunnel (subsequent upgrade attempts are rejected per §3.4's ordered checks); (b) close the live data-plane connection if one exists (a normal WebSocket close; close code is §4's business); (c) release tunnel-scoped relay state (cached frame window, fan-out registrations). No retained record of a deleted tunnel is required. Deletion is permanent; the same session returns only via a fresh POST.

Statuses: `{204, 401, 403, 404, 5xx}` — closed partition. A failed delete notification is safe to ignore: the server SHOULD expire spent and abandoned tunnels itself, so a host that proceeds with local teardown despite a failed notification leaves no orphan.

## 3.6 Error taxonomy

The §2.7 body (`{"error": "<code>", "error_description": "<human-readable sentence>"}`) and the never-merge-401/403 rule extend to every non-2xx in this section. Vocabulary: inherited `invalid_token`, `insufficient_scope`; defined here: `invalid_request` (400), `tunnel_not_found` (404), `tunnel_already_live` (409 POST), `token_consumed` (409 handshake), `internal_error` (5xx).

**Closed status partitions (normative):** POST `{200, 400, 401, 403, 409, 5xx}`; DELETE `{204, 401, 403, 404, 5xx}`; handshake `{101, 400, 401, 404, 409, 5xx}`. A server emitting any other status on these surfaces is non-conformant. `429` is **not** in the POST partition: a conformant server that rate-limits maps throttling onto existing partition members; a server emitting `429` is non-conformant (the drafting of this sentence is the owner's — O11 item).

**The two credential failure classes — never merged (the card's core acceptance):**

| Status | `error` | Meaning | Remedy |
| --- | --- | --- | --- |
| `401` | `invalid_token` | The credential is invalid, expired, or revoked — it does not authenticate. | **Re-enrollment.** No retry, refresh, or re-consent recovers the credential. |
| `403` | `insufficient_scope` | The credential is valid but lacks the `pi-remote:host` scope. | **Re-consent** (re-run enrollment so the user sees the scope request) plus an administrator scope grant (administrative surface in §5). |

A server that returns `401` for a scope problem, or `403` for an invalid/expired/revoked credential, is non-conformant (§2.7's rule restated and extended to this section).

**Surface disambiguation of 401 — MUST be stated on the page (O10 drafting item):** a `401` at a control-plane tunnel endpoint means the enrollment credential is dead — the remedy is re-enrollment; a `401` at the data-plane handshake means the connection token is unusable — the remedy is to re-create the tunnel. Same status, different credential, different remedy — disambiguated by surface, so §2.7's "the status alone selects the remedy" rule stays true per-surface.

**The client-side failure classes, restated in the document's own words (the exhaustive-coverage contract):**

(i) **Invalid/expired/revoked credential** → control-plane `401` → re-enrollment. (ii) **Valid-but-insufficient scope** → `403` → re-consent plus administrator grant. (iii) **Connection-layer failure** (DNS/TCP/TLS; the request never completes) → no HTTP status exists; no server obligation can be stated; the remedy is check network and retry. (iv) **Response-shape defense** → a 2xx body deviating from §3.2/§3.5 is emitted only by a non-conformant server; a conformant server MUST NOT emit partial success (a 2xx MUST never carry an error body; a 4xx/5xx MUST never carry a usable tunnel). (v) **Failed delete notification** → only `5xx` can produce it on DELETE; the host proceeds with local teardown regardless (safe by §3.5's expiry rule). (vi) **Handshake failures** → §3.4's closed set, uniform remedy re-create.

**Host coarse grouping, restated (binding consistency with the class groupings an interoperating host renders):** on create, `400`, `409`, and `5xx` all land in one generic retryable class (correct-the-request is *not* a distinct remedy rendered for `invalid_request`; `tunnel_already_live`'s remedy for a conformant host is the same retry-with-backoff); on delete, `5xx` lands in a distinct non-blocking teardown-failure class — the host reports the notification failure and proceeds with local teardown, never retrying the delete. The taxonomy must carry this asymmetry; a page implying the host renders a distinct remedy for `invalid_request` or `tunnel_already_live`, or that DELETE `5xx` is retried, contradicts the acceptance check.
