## 2. Subsection plan and content

### 4.1 Scope and the two streams

One long-lived host-initiated WebSocket per tunnel (§3.1). Two logical
streams: the **downlink** (host → server → devices; the host is the single
producer) and the **host-bound** stream (devices → server → host; the server
is the single producer, multiplexing device input into one ordered stream).
Governing constraints restated: INV-1/INV-2/INV-3; the §1.2 negative
invariant is the section's ceiling — the server reads the envelope and
nothing else.

### 4.2 The envelope, per direction (rulings OJ-1's neighborhood; OJ-3)

- **Downlink envelopes (host→server): exactly `{v, seq, ack, frame}`** — four
  keys. (Wire-observable; matches the reference `envelope()` byte set.)
- **Host-bound envelopes (server→host): `{v, seq, ack, frame}` plus one
  optional server-stamped key `deviceId`** identifying which granted device
  produced the frame.
- **No other key, in either direction, ever.** The key set is closed; the
  evolution point is `v` (§4.4), not extra keys. A server that adds any other
  envelope key is non-conformant.
- `deviceId` is present **iff the frame is device-originated**; server-originated
  frames (`resync`, ack-only) carry none.
- **The deviceId trust rule (OJ-3 — within card authority):** the `deviceId`
  on host-bound envelopes is **server-stamped from the authenticated
  connection identity**; the server MUST NOT take it from any device-supplied
  byte (top-level or in-frame). Stated as a restated consequence of INV-4
  (the server is the enforcement point) and INV-3 (tenancy lives in
  credentials): it changes no contract surface, tenancy, or threat model.
  Grounded fact: the host trusts the envelope `deviceId` with zero
  verification, so the server is the only possible trust anchor.
- **Resume-frame `deviceId` precision (skeptic O1):** on a `resume` frame the
  host-side parser takes the identity from `frame.deviceId`, not the top
  level. §4 states: the server MUST validate the in-frame `deviceId` of an
  inbound `resume` against the authenticated connection identity and MUST NOT
  serve `lastAckedSeq` bookkeeping for a device other than the connection's
  own (this closes the cross-device watermark-peek vector).
- Envelope opacity: the server MUST NOT inspect `frame` beyond discriminating
  the closed set of §4.4 (restated INV-1).

### 4.3 Sequence and acknowledgement

- **Downlink seq is host-owned**: positive integer starting at 1 per session
  instance, monotonic, never reset; the server never reorders, renumbers, or
  stamps it.
- **Host-bound seq is server-owned** (settled; skeptic O9): the server
  rebuilds device input into one merged, monotonic host-bound sequence —
  positive integers starting at 1 per session instance. This is what makes
  the host's single `ack` watermark meaningful at N≥2 devices. The server
  MUST NOT preserve per-device seq passthrough on the host-bound stream.
- **Ack** is the sender's watermark: the highest inbound seq it has processed;
  `0` before any. Every envelope carries the sender's current ack
  (piggybacked; no dedicated ack frame exists).
- **Ack-only envelopes:** a sender MAY send `{v, seq, ack, frame:null}` to
  advance its watermark. **Downstream-only**: the reference host never emits
  `frame:null` (it heartbeats at the WS level); the server MAY emit these on
  the host-bound stream.
- **Ack monotonicity (normative):** ack MUST never decrease on any single
  stream; violation is a protocol violation closed with `3400`
  (wire-observable; matches the reference close).
- **Seq continuity across tunnels (normative; skeptic O2 probe):** the
  host's seq is bound to the session instance, not the tunnel — reconnect
  mints a new tunnel (§3.1) while seq continues unreset. The server MUST NOT
  assume a tunnel's first frame carries seq 1, and MUST NOT reset or renumber
  seq at tunnel boundaries.

### 4.4 The frame slot's closed set and the versioning escape hatch

The `frame` value is exactly one of:

a. an application frame (opaque to the server),
b. `null` (ack-only; downstream-only),
c. `{"type":"resume","deviceId":<string>,"lastAckedSeq":<finite number>}`,
d. `{"type":"resync","fromSeq":<finite number>}`.

**The only-these-control-frames rule, normative:** within envelope version
`1`, `resume` and `resync` are the only control frames a server may emit or
relay, and the frame slot admits no further types.

**`pi.resync.done` is NOT a control frame** (settled): it is an ordinary
`CUSTOM` application frame (`name:"pi.resync.done"`, `value:{uptoSeq}`)
emitted host-upstream. The server MUST relay it opaquely and MUST NOT parse
it; fan-out needs no replay-end signal.

**Versioning escape hatch, named:** a server needing a new control frame or
changed envelope MUST version the protocol — increment `v` and define the new
grammar — never improvise inside `v:1`. A server receiving a `v` it does not
implement closes the connection as a protocol violation (`3400`).

### 4.5 The resume/resync handshake

- A **device** sends `resume` (`{type:"resume", deviceId, lastAckedSeq}`,
  inside the envelope's `frame` slot) to request catch-up;
  `lastAckedSeq` is in the **host's** seq space — the highest host-seq the
  device has processed.
- **The server MUST NOT forward a `resume` frame to the host, and MUST answer
  resumes itself** (OJ-4: normative MUST NOT — direction is part of the
  contract; a resume appearing in the server→host direction is checkable by
  any conformance harness playing the host).
- The server answers from its ring buffer by delivering the missed range of
  the host's stream in host-seq order.
- **On a cache miss** the server sends `{type:"resync", fromSeq}` to the
  **host**. **`fromSeq` pinning (OJ-5):** `fromSeq` SHOULD equal the
  requesting device's `lastAckedSeq + 1` — explicitly advisory: the host MAY
  ignore it, and the server MUST NOT assume exact-range replay (at-least-once
  tolerance; duplicates and gaps tolerated). The host replays from its own
  store as ordinary application frames (INV-2) — in the reference, the full
  active branch — and the server relays them like any others.
- **At-least-once delivery (normative, restated consequence of INV-2):** the
  relay never guarantees exactly-once; a resume/resync path may redeliver;
  recipients dedupe by deterministic event id. The remedy ladder is total:
  reconnect → resume → resync → full-branch replay from the host's
  authoritative store.
- **Cache miss resolves to resync, never to error, stall, or fabrication**
  (normative, restated INV-2) — including the empty cache of a fresh tunnel
  answering a post-reconnect resume.
- **Revocation interaction:** if the requesting device is revoked while its
  resume is outstanding, the server cancels its catch-up; a resync already
  sent is not recalled (the host's replay fans out to the remaining granted
  devices — never wasted work). Per-device bookkeeping for a revoked device
  is discarded; the stream and other devices are unaffected.

### 4.6 Fan-out (1:N)

- The server delivers each host-produced frame to **every granted connected
  device**, in host-seq order, identically: same frames, same order, no
  per-device filtering of the stream.
- Grant enforcement happens at delivery (INV-4): a device whose grant does
  not cover the tunnel receives nothing.
- Revocation takes effect at the next delivery opportunity without host
  cooperation: the server MUST stop delivering to a revoked device
  immediately and SHOULD close its socket promptly (control-plane act, §5).
- Per-device bookkeeping (last delivered seq, in-flight catch-up) is
  bookkeeping only, never protocol logic — single producer ⇒ one total order.
- Uplink concurrency: input from any granted device is accepted; concurrent
  uplink frames interleave into the server's host-bound stream order;
  arbitration between devices is out of scope for the data plane.

### 4.7 The ring buffer

- **MUST-not-rely (normative, restated INV-2):** correctness MUST NOT depend
  on the cache — a server with an empty or short cache MUST still deliver
  every live frame and MUST resolve every miss via `resync`; the server MUST
  NOT treat the cache as authoritative history.
- **SHOULD (capacity):** a server SHOULD cache a bounded recent window per
  live tunnel to serve fast catch-up without a host round-trip.
- Release: the cache is discarded at tunnel deletion (§3.5(c)); because seq
  continues across tunnels, a post-reconnect resume MUST be answered with
  `resync` (§4.5), never an error.

### 4.8 Liveness and close codes (resolves §3.4/§3.5(b) forward refs)

- Liveness via native WS ping/pong; no application-level keepalive. The
  server MUST answer pings per the WS protocol and MAY send its own pings to
  reap dead sockets. The reference host pings at 10 s (non-normative example).
- Close codes are **diagnostic, not a contract**: the dialing side's remedy
  for any close is uniform (re-arm → new tunnel → reconnect); a client MUST
  NOT be required to parse close codes. Two codes are named: `1000` —
  deliberate close, including deletion per §3.5(b) (normative on the host
  side; the server's deletion close uses it); `3400` — protocol violation
  (normative: malformed envelope, unknown `v`, frame-slot value outside
  §4.4's set, ack inversion — each wire-observable).

### 4.9 Guidance (non-normative) — including the frame-size material (OJ-1)

One recommended shape per concern, in a clearly marked Guidance block:

1. **Ring sizing:** fixed-capacity count-based ring per live tunnel
   (e.g. last 512 envelopes), oldest evicted; no unbounded growth, no
   time-based retention.
2. **Connection state machine:** host socket `dialing → live → closing →
   closed`; per-device delivery `attached → catching-up → streaming →
   detached`; one line each on what transitions on close, revocation, and
   cache miss.
3. **Backpressure:** bounded per-device send queue; on overflow, disconnect
   that device rather than buffering unboundedly or blocking the host's
   stream — safe because the device's remedy ladder is total.
4. **Deployment topology:** the single-live-socket-per-tunnel rule (§3.1)
   pins each tunnel to one server process, so the ring cache can be
   in-process memory with no cross-replica coherence; token signing keys can
   be shared/asymmetric per §3.3's guidance.
5. **Frame-size handling (OJ-1 ruling — pure guidance, no wire bound):**
   recommend that a server bound per-message memory (a ~1 MiB example number,
   clearly marked non-normative); note that a server refusing an oversized
   message closes `1009` — safe because the client remedy ladder is total.
   **And restate normatively, as a consequence of INV-1 already on the page,
   that a relay never truncates or splits a frame** — truncation is a payload
   transform. No accept-floor and no emit-ceiling enter the wire contract.
