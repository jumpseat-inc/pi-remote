## 0. Binding rulings applied (recorded on the card, 2026-09-02)

These are binding; the write-up implements them and cites them where they
bite. Verbatim text is on the card face.

- **Q1 (OBJ-4):** drop `pi-remote:device` from the scope-grant closed union.
  The scope-grant endpoint's body is `{scope}` ∈ `{pi-remote:host,
  pi-remote:admin}`. The opaque-secret device credential model stands
  unchanged. Devices obtain their credential through `POST /devices`, never
  through `POST /subjects/{sub}/scopes`; that endpoint discharges the

- **Q2 (OJ-1):** the owner's 401-fold branch. The device upgrade folds the
  device-status check into the existing `401 invalid_token` branch — token

  `{101, 400, 401, 404, 409, 5xx}` unchanged. The DEVICE upgrade's REQUIRED
  lookup states are three — the consumed-`jti` set, live-tunnel existence,
  and the device registry row (existence + status) keyed by the verified
  token's `device_id` claim — while §3.4's host handshake keeps its existing
  two; §5's ordered-checks list names all three in order.
- **Q3 (OJ-2):** R6's "device registration, admin grant operations, and other
  registry surfaces the client never calls … with their own admin/operator

## 1. What §5 closes (writer precision — skeptic OBJ-1)

The §5.0 opening must state its closures **precisely**, because they are not
all the same kind:

1. **One literal forward reference:** §4.1 — "The population of *granted
   connected devices* is defined by the registry and grants section (§5)."
2. **One undefined concept with no pointer:** §4.2's "authenticated
   connection identity" — it carries **no** `(§5)` marker on the page today.
   §5 does not "close a forward reference" here; it **defines the concept**
   for the first time. Do not write "two forward references." (Whether §4.2
   gains a pointer is EV-14's call, not this card's.)
3. **The scope-grant debt:** §2.5 and §2.7 both route the `403
   insufficient_scope` remedy through "an administrator grant of the scope
   (administrative surface in §5)"; §3.6's remedy row repeats it. §5
   discharges these with its admin surface (§5.10 of the design, below).
4. **The distinct-surface statement:** §3.1's single-token/single-upgrade
   rule and §3.4's handshake govern the **host** connection. Device
   connections are a **distinct, second** data-plane surface, specified
   here — a device MUST NOT attach over the host's §3.3 URL (that token
   carries no device identity; see §17, claim 6).

## 2. §5.0 — Opening

One paragraph stating: what §5 closes (per §1 above, with the
pointer/undefined-concept distinction kept exact); that §5 specifies the
device registry, the device data-plane connection (a mint surface plus a
WebSocket upgrade), the grant-enforcement algorithm at fan-out, revocation,
the reserved push record shape, the admin surface; and that the registry and
admin surfaces are precisely the surfaces client devices never call
themselves (R6, per ruling Q3). §5 carries its own closed status partitions

## 3. §5.1 — The device object and identity

The registry record, one row per device:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `deviceId` | REQUIRED | Server-assigned, opaque, URL-safe identifier. **Tenant-unique MUST; globally unique MAY.** The wire never observes more: a host only sees `deviceId`s on its own tenant-bound streams, and §2.6's `sub` namespacing already supplies cross-tenant ambiguity-freedom. |
| `tenantId` | REQUIRED | Immutable after registration. Fixed at registration; moving a device between tenants is revoke + re-register (§5.4). |
| `displayName` | REQUIRED | Informational; the server never interprets it. |
| `status` | REQUIRED | `active` \| `revoked`. Terminal in the `revoked` direction: there is no un-revoke. |
| `pushProvider` | REQUIRED | §5.9. |
| `createdAt` | REQUIRED | Registration time. |

**`deviceId` stability (normative, load-bearing):** `deviceId` MUST be stable
for the registration's lifetime and MUST NOT be recycled after revocation.
Grounding to restate in §5: the host tracks per-device acknowledgements keyed
by the envelope `deviceId` (§4.3's per-device bookkeeping note) and attributes
`pi.human_input` by it (§4.2's trust rule); a server that re-assigned or
recycled `deviceId`s would make per-device bookkeeping and audit identity
meaningless — or actively falsifiable, which is why the no-recycle rule is a
guard against audit laundering, not mere hygiene.

**The device credential (normative shape):** an **opaque, server-generated
secret** — long-lived, revocable, stored only as a hash (`credential_hash`;
never the credential itself), presented only to the control plane over TLS,
compared in constant time. It is **not** an OAuth token: no authorization
server round-trip, no `scope` claim, no refresh semantics (ruling Q1's
grounds). It is the third INV-3 contract point's credential, made concrete in
§5.11. Lost credential ⇒ revoke + re-register (the §2.8 replace-not-merge
discipline's device-side analogue).

## 4. §5.2 — Device registration — `POST /devices` (admin-minted, per Q3)

Registration is **admin-minted**, not device self-enrollment: R6's text
enumerates device registration among "registry surfaces the client never
calls … with their own admin/operator auth," and a self-enrolling device has
no admin-authenticated registration surface anywhere in the document. (Ruling
Q3 owns this interpretation; EV-14 may not reopen it.)

- **Authentication:** enrollment access token carrying `pi-remote:admin`
  (§5.10); tenancy derived solely from the token's `tenant_id` claim (§2.6's
  rule, restated — the request carries no tenant field and any tenant-like
  request field is ignored).
- **Request body:** `displayName` (REQUIRED, non-empty string, ≤ 256 chars —
  guidance-grade maximum per §1.5); `pushProvider` (OPTIONAL; §5.9's union
  and default). Unknown fields MUST be ignored; missing/wrong-typed fields
  are `400 invalid_request`.
- **Response (success):** `200` — not `201`; §3.2 states the precedent
  ("there is one response shape") and this document keeps it. Fields:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `deviceId` | REQUIRED | The new registry row's identity. |
| `deviceCredential` | REQUIRED | The opaque secret. **Shown exactly once, never re-retrievable** — the response-table REQUIRED-once field is the only normative lever on the out-of-band handoff; §5.3's read surface MUST NOT include it (skeptic OBJ-8). |
| `pushProvider` | REQUIRED | Echo of the stored value. |

- The registry record is created by this call. The out-of-band transfer
  channel is **guidance** (non-normative), not contract.

## 5. §5.3 — Device list — `GET /devices`

Admin-authenticated (§5.10). Lists the admin token's own tenant's devices.

- **Response (success):** `200` with a JSON array; each element carries
  `deviceId`, `displayName`, `status`, `pushProvider`, `createdAt`.
- **Writer obligation (skeptic OBJ-8, binding):** the response MUST NOT
  include `deviceCredential` — "shown exactly once, never re-retrievable"
  (§5.2) is violated the moment a read surface returns it.
- This endpoint is one of the two observation points that make
  `pushProvider`'s normativity enforceable (write at `POST /devices`, read
  here).
- **Closed partition:** `{200, 401, 403, 5xx}`.

## 6. §5.4 — Tenant membership is the base grant

Normative, restating INV-3/INV-4 made concrete: every device belongs to
exactly one tenant, fixed at registration. **Membership is the base grant**:
a device may receive a tunnel's frames if and only if the device's tenant
equals the tunnel's tenant. No grant ever widens beyond the base grant;
narrower restrictions only ever reduce access below it (§5.7). Moving a
device between tenants = revoke + re-register; there is no move operation.

## 7. §5.5 — The mint surface — `POST /device/connections`

The device data-plane connection is a **two-surface model**. The long-lived
device credential is presented over REST (where the browser's `fetch` can set
an `Authorization` header — the browser `WebSocket` constructor cannot, a
verified load-bearing fact of this design: skeptic OBJ-3 closed-green on MDN,
WHATWG, and undici); the REST surface mints a short-lived, single-use,
signed connection URL; the WebSocket upgrade (§5.6) is §3.4-shaped. This
mirrors the host model exactly (§2 enrollment → §3.3 URL → §3.4 upgrade) and
keeps the long-lived secret out of WebSocket URLs, which end up in browser
history and server logs (INV-5's shape, held at the data plane).

**Request:** `Authorization: Bearer <device credential>`; body
`application/json`, `{"tunnelId": "..."}` REQUIRED.

**Ordered checks:**

1. **Extract and parse.** Absent/malformed credential header, or unparseable
   body, or missing `tunnelId` → `400 invalid_request`.
2. **Authenticate the device.** Constant-time comparison of the presented
   credential's hash against the stored `credential_hash` → no match (never
   existed or wrong) or row `status: revoked` → `401 invalid_token`. No
   existence leak: revoked and never-existed are byte-indistinguishable —
   same status, same `error` code (`error_description` is diagnostic per
   §2.7 doctrine).
3. **Grant coverage.** The device row's `tenantId` compared with the named
   tunnel's tenant → mismatch = **`404 unknown_tunnel`, never `403`**.
   Under base-grant-only, "does the tunnel exist *in the device's tenant*?"
   is the same question as existence, and §3.5's no-existence-leak prose
   transfers. Byte-indistinguishable (same status + same `error` code) from
   a genuinely unknown tunnel.
4. **Live-tunnel existence.** Absent or deleted tunnel → `404
   unknown_tunnel`.
5. **Layered denial (MAY path).** `403 tunnel_not_granted` — **a reserved
   code, stated as reserved on the page: reachable by no MUST in v1**. No
   wire surface for managing per-tunnel restrictions is specified; this is
   the only observable a layered denial ever produces.

**Response (success):** `200` with `url` and `tokenTtl`, both REQUIRED —
same three-field shape discipline as §3.2 (`tokenTtl` equals the issued
token's actual validity window).

- **URL shape:** `wss://<data-plane host>/<tunnelId>/devices?token=<token>`
  — the **distinct device path**, whose final segment is the literal
  `devices` (the principal's blind-spot call, adopted: this makes §3.1's
  one-upgrade carve-out structural rather than claim-inference — §3.4's
  "final segment equals tunnelId" simply cannot be read onto this URL).
- **Token:** compact JWS — §3.3's grammar with one claim added: `tenant_id`,
  `tunnel_id`, `device_id`, `exp`, `jti` (all REQUIRED); `iat`, `iss`,
  `aud` (SHOULD). TTL bounds identical to §3.3: 60 s default (SHOULD), 5 s
  minimum / 300 s maximum (MUST), clamp-then-issue on misconfiguration,
  judged by the server's clock at the upgrade and only there.
- **Single use:** the minted token is consumed atomically at the upgrade
  (§5.6 step 5); replay → `409 token_consumed`.

**Closed partition:** `{200, 400, 401, 403, 404, 5xx}`. **`403` lives only
on this surface** — the mint surface is control plane, where every security
decision is made (§1.2); the upgrade carries no `403` (§5.6).

**Identifier, not capability (normative guard):** `tunnelId` is an
identifier, not a capability. Possession of a `tunnelId` plus a valid device
credential is not sufficient to attach: the mint surface's grant check
(step 3) is the only gate. Device-facing tunnel discovery is out-of-band for
v1 — a named non-decision, not an omission (§5.13).

## 8. §5.6 — The device upgrade — the data-plane connection for devices

The device dials the minted URL and performs a WebSocket opening handshake
against `wss://<data-plane host>/<tunnelId>/devices`. Authentication happens
strictly before the `101`, exactly as §3.4 requires.

**Binding check wording (writer obligation — skeptic OBJ-7, binding):** the
path's **first segment** equals the token's `tunnel_id` claim. §3.4's
"final segment" wording MUST NOT be bolted on verbatim — here the final
segment is the literal `devices`.

**Ordered checks** (ruling Q2, in full):

1. **Extract the token.** URL-level malformation → `400 invalid_request`.
2. **Verify the signature.** Failure → `401 invalid_token`.
3. **Check expiry.** `exp` vs the server's clock → expired → `401
   invalid_token`.
4. **Verify the bindings.** The token's `tunnel_id` claim must equal the URL
   path's **first segment** (mismatch → `401 invalid_token`); the
   live-tunnel existence record must show the tunnel present and not deleted
   (absent/deleted → `404 unknown_tunnel`).
5. **Consume the token atomically.** The `jti` is marked consumed before the
   `101` is sent; two simultaneous upgrades presenting one token admit
   exactly one `101`; replay → `409 token_consumed`.
6. **Device registry row.** Look up the row keyed by the verified token's
   `device_id` claim. Row absent, or row `status: revoked` → `401
   invalid_token`. **This is the folded branch (ruling Q2): `invalid_token`
   on this surface means token invalid OR named device row revoked — one
   code, one meaning (does-not-authenticate, per §2.7's binding
   classification), closed partition unchanged.** Revocation is terminal
   (retained record, no un-revoke), so this branch can never fire on a
   device that will live again; a revoked device's credential is also
   already dead at the mint surface, so the mint→dial TTL window is closed
   by this check.

**REQUIRED lookup states (ruling Q2 — stated explicitly on the page):** the
device upgrade consults **three** server-side lookup states, named in order
above: the consumed-`jti` set, the live-tunnel existence record, and the
device registry row (existence + status) keyed by the verified token's
`device_id` claim. The contrast is stated in one sentence: §3.4's host
handshake keeps its existing two (consumed-`jti` set, live-tunnel
existence) — the third state is what makes mid-window revocation enforceable
without adding a status code.

**Closed partition:** `{101, 400, 401, 404, 409, 5xx}` — identical to
§3.4's. **No `403` anywhere on the upgrade:** the mint surface has already
adjudicated grants before any URL exists; a security decision on the data
plane is what §1.2 forbids and what ruling Q2's folded branch avoids
duplicating.

**On success:** the server binds the connection to `(tenant, tunnel,
deviceId)` and this binding is the **only** source of the server-stamped
envelope `deviceId` — `deviceId` is stamped from the token's `device_id`
claim, never from any device-supplied byte (§4.2's trust rule, with its
mechanism now on the page); the in-frame `deviceId` of an inbound `resume`
is validated against it (§4.5's cross-device watermark-peek guard).

**Reconnect and contrast with the host:** the device credential is **not**
single-use; a device re-dials by minting a fresh URL (re-running §5.5) —
there is no `409` on credential reuse, only on token replay. Unlike the
host's §3.1 one-tunnel/one-upgrade rule, multiple device connections per
tunnel are the expected steady state (§4.6's 1:N fan-out) — each device
connection is its own mint→dial cycle.

## 9. §5.7 — Grants and the enforcement algorithm at fan-out

**Floor (MUST, harness-observable):** the server MUST NOT deliver any
data-plane frame for tunnel T to a device that is not a member of T's tenant
(restated INV-4).

**Enforcement at two points:** attach-time (§5.5 steps 3/5, §5.6) **and**
re-checked at every delivery opportunity — the second check is what makes
mid-connection revocation take effect without host cooperation (INV-4,
§4.6's "takes effect at the next delivery opportunity").

**The algorithm, stated once** (each line a restated consequence of
INV-1/INV-4): on a host-produced frame F for tunnel T, for each attached
device d (snapshot at delivery time):

1. d revoked → detach; never deliver.
2. d's tenant ≠ T's tenant → detach; never deliver.
3. A layered per-tunnel policy denies d → skip (MAY path; reachable by no
   MUST in v1).
4. Else deliver — same frames, same order, no per-device filtering of the
   stream (§4.6 restated).

**The uplink half (audit-critical, MUST):** after revocation the server MUST
NOT merge any further uplink frame from that device into the host-bound
stream. The host attributes input by the server-stamped `deviceId` (§4.2);
delivering a revoked device's frame would launder an audit identity. Frames
already merged before revocation are not recalled — the stream is
append-only (INV-1).

**Ceiling (MAY):** the server MAY layer narrower per-tunnel restrictions;
they only ever reduce access below the base grant, are never observable on
the wire (a device presents only its credential and receives frames or does
not), and require no device-side knowledge of which rule denied it. Clients
never depend on them; the base grant is the only grant any conformant host
or device needs.

## 10. §5.8 — Revocation — `DELETE /devices/{deviceId}`

Revocation is a control-plane act, admin-authenticated (§5.10).

- **Semantics:** idempotent; `204` on success. Unknown, foreign-tenant, or
  already-revoked `deviceId` → `404 unknown_device` — never `403` (no
  existence leak, mirroring §3.5's rule; a repeated delete is
  indistinguishable from a first success). `404`-only: no `410`.
- **Closed partition:** `{204, 401, 403, 404, 5xx}`.

**On success, in order:**

a. Registry row `status` → `revoked`; the credential is dead — subsequent
   `POST /device/connections` is `401` (§5.5 step 2).
b. Fan-out stops **immediately** (§4.6's MUST; the mechanism is §5.7's
   delivery-time re-check).
c. The live socket SHOULD close promptly with `1000` (§4.8's deliberate
   close).
d. Per-device bookkeeping and any outstanding catch-up are discarded
   (§4.5); the host-bound stream and the other devices are unaffected; a
   resync already triggered is not recalled.

**The record is retained, not erased.** The envelope `deviceId` audit trail
must remain interpretable (§4.2 makes the server the only trust anchor for
stamped `deviceId`s; the registry is the only decoder ring). This is a
documented, reasoned difference from §3.5's no-tombstone rule — which is
**tunnel-scoped** prose and does not transfer to devices. Corollary
(normative): a revoked `deviceId` MUST NOT be recycled (§5.1's audit-laundering
guard).

**Without host cooperation (INV-4):** all of the above takes effect with
zero host-side action. Restated in this document's own words: the host has
no revocation logic; frames from a revoked device simply stop arriving, and
the server is the only authority (§4.2's trust rule).

## 11. §5.9 — The reserved push record shape (`pushProvider`)

Normative and wire-observable at the two observation points:

- The registry field and the `POST /devices` request field `pushProvider`
  MUST be exactly one of `"webpush" | "apns" | "fcm"`; absent at
  registration = default `"webpush"`; any other value = `400
  invalid_request` at set time.
- **Observation points:** write at `POST /devices`, read at `GET /devices`
  — both REQUIRED for the reservation to be enforceable rather than
  decorative (EV-12's observation-point test; round-1 finding adopted).
- **No push delivery behavior, endpoint, or payload is specified.** The
  field is a reservation so the browser-PWA client (which needs no vendor
  account) works first. Settable at registration; mutation is reserved for
  future push surfaces, which extend from this reservation. (Adding a
  vendor to the union later is closed-vocabulary growth — ruling-required,
  per ruling Q1's note.)

## 12. §5.10 — The admin surface (scope grants; the §2.5/§2.7 debt)

**Admin authentication (normative):** the `pi-remote:admin` scope, carried on
the **enrollment-credential contract point** — an operator enrolls via §2
requesting admin scope on the same authorization server. Tenancy is derived
from the admin token's `tenant_id` exactly as §2.6: an admin is tenant-bound
by credential like everything else. **No fourth tenancy mechanism exists;
INV-3's list stays at three** (§5.11). §2.7's never-merge 401/403 rule
extends to every admin surface verbatim.

**Endpoints:**

- `GET /devices` — §5.3.
- `DELETE /devices/{deviceId}` — §5.8.
- `POST /subjects/{sub}/scopes` — body `{"scope": "..."}`; **closed union
  exactly `{pi-remote:host, pi-remote:admin}`** (ruling Q1: `pi-remote:device`
  is NOT in the union — the device credential is an opaque secret with no
  scope and no AS round-trip, so a grantable `pi-remote:device` would name a
  grant nothing can bear; devices obtain their credential through `POST
  /devices`, never through this endpoint; this endpoint discharges the
  §2.5/§2.7 debt for enrolled subjects — hosts and admins, which devices are
  not). Grants the scope to an enrolled subject in the admin token's own
  tenant. **Grants are explicitly scoped to the admin token's own tenant**
  (ruling Q1; no cross-tenant escalation). Success `204`; partition
  `{204, 400, 401, 403, 404, 5xx}`; unknown or other-tenant `sub` → `404`
  (no existence leak). An unknown scope value → `400 invalid_request` (the
  union is closed).

## 13. §5.11 — Multi-tenancy: the three credential contract points, mapped to mechanisms

Self-contained table (restated INV-3, made concrete); each row maps one
contract point to its server-side enforcement mechanism:

| Contract point | Credential | Mechanism | Enforced at |
| --- | --- | --- | --- |
| Enrollment token | OAuth2 access token (§2.6) | Authorization server validates; `tenant_id` claim scopes all host control-plane state; tenancy derived solely from the token, never from request fields | Every control-plane request |
| Tunnel token | Signed one-time compact JWS in the URL (§3.3) | Server signs at create; `tenant_id` claim read off the verified token; tunnel-existence binding checked at upgrade | The host handshake (§3.4) |
| Device grants | Opaque device credential (§5.1) → minted device connection token (§5.5) | Registry row's tenant binding carried into the token's `tenant_id`/`device_id` claims; mint-surface tenant check; upgrade-time registry-row check; delivery-time re-check | Mint (§5.5), upgrade (§5.6), and every fan-out delivery (§5.7) |

Plus the INV-3 restatement: the frame envelope carries **no tenant field
anywhere** (§4.2's closed key set), and every connection is bound to exactly
one `(tenant, tunnel)` pair before a single frame flows.

## 14. §5.12 — The trust summary, from the server's side of the table

**Self-containment requirement (card acceptance):** the trust table is
restated in full from the server's perspective; **no row may be defined by
reference to another document.** Rows for Host / Server / Client device /
Admin-operator, each with Holds / Can do / Server-visible consequence.
Content elements the write-up must carry (from the converged design):

- **Server holds:** the token-signing key(s), the authorization-server
  registry, the device registry, the consumed-`jti` set, the live-tunnel
  records, the ring buffers, and every envelope byte on every tunnel it
  hosts.
- **Server can do:** issue and revoke enrollment credentials, mint and
  consume tunnel tokens, register/grant/revoke devices, stamp `deviceId`,
  enforce fan-out, relay.
- **Frame visibility is total within its tunnels.** TLS terminates at the
  server; no payload-level end-to-end encryption is specified anywhere in
  this document.
- **The compromise statement, honestly (card acceptance):** a compromised
  server exposes every frame payload of every tunnel it serves, in the
  clear; it can mint valid connection tokens for any tunnel of any tenant it
  hosts; it can forge `deviceId` stamps — envelope audit identity is only as
  trustworthy as the server; it can impersonate any host or device; it can
  read both registries. **The blast radius is total across the tenants it
  hosts and zero beyond them** — it cannot reach data or credentials for
  tenants it does not host. INV-1's relaying-opaquely obligations are
  behavioral constraints on a conformant server, **not** cryptographic
  guarantees against a compromised one. There is no host↔device integrity
  that excludes the server.
- **Host compromise** (from the server's side): a compromised host holds
  credentials for exactly one tenant, affects only its own tunnels, cannot
  mint tokens, cannot reach other tenants (INV-3 scoping).
- **Device compromise:** a leaked device credential reaches only its tenant
  and only the tunnels its grant covers; revocable at the control plane
  without host cooperation (INV-4), and the blast radius of a leaked
  *minted token* is bounded by its TTL and single use (§5.5).
- **Admin-operator:** a compromised admin credential reaches its own tenant's
  registry and scope-grant surfaces; it cannot reach other tenants (§2.6
  tenancy derivation; §5.10's tenant-scoped grants).

## 15. §5.13 — Guidance (non-normative; one shape each, per R3)

a. **Registry storage sketch:** one row per device keyed by `deviceId`:
   `tenant_id`, `display_name`, `status`, `push_provider`,
   `credential_hash` (never the credential), `created_at`; constant-time
   credential-hash comparison.
b. **Admin operations:** bootstrap the first admin out-of-band per
   deployment; device lifecycle register → revoke; audit = retained device
   rows plus host-side attribution.
c. **Key ceremony:** signing keys generated on the server, never exported to
   hosts or devices; asymmetric pair with rotation, per §3.3's existing
   guidance.
d. **Device tunnel discovery:** out-of-band for v1 — written as a **named
   non-decision**, not an omission: a device learns `tunnelId`s out-of-band;
   possession is not capability (§5.5's guard).

## 16. Error vocabulary and closed partitions (§5's own tables)

New codes, each defined **exactly once**: `unknown_device` (`404`,
device delete/mint surfaces); `tunnel_not_granted` (`403`, mint surface,
**stated as reserved — reachable by no MUST in v1**). Naming note kept
honest: `tunnel_not_granted` and §3's `tunnel_not_found` are confusably
close — the write-up defines each exactly once and never merges them.
Inherited without redefinition: `invalid_request`, `invalid_token`,
`insufficient_scope`, `unknown_tunnel`, `token_consumed`, `internal_error`.

**Closed partitions (normative, §5's own table):**

| Surface | Partition |
| --- | --- |
| Register (`POST /devices`) | `{200, 400, 401, 403, 5xx}` |
| List (`GET /devices`) | `{200, 401, 403, 5xx}` |
| Revoke (`DELETE /devices/{deviceId}`) | `{204, 401, 403, 404, 5xx}` |
| Scope grant (`POST /subjects/{sub}/scopes`) | `{204, 400, 401, 403, 404, 5xx}` |
| Mint (`POST /device/connections`) | `{200, 400, 401, 403, 404, 5xx}` |
| Device upgrade (`wss://…/<tunnelId>/devices`) | `{101, 400, 401, 404, 409, 5xx}` |

A server emitting any other status on these surfaces is non-conformant.
`429` is in none of them (§3.6's rule extends).

## 17. Testable claims (how the write-up meets the card's acceptance)

1. **The device-connection gap is closed:** §1–§4 contain no sentence
   specifying how a client device authenticates to the data plane, and
   §3.1/§3.4 forbid reusing the host path; §5.5/§5.6 specify the attach, so
   §4.6's "input from any granted device is accepted" is implementable.
2. **`deviceId` stability is load-bearing in the shipped host:** per-device
   ack tracking and attribution are keyed by it; §5.1 mandates stability and
   no-recycle — no contradiction with the client's expectations.
3. **The scope-grant forward reference is discharged:** §2.5, §2.7, and
   §3.6 all route the 403 remedy through "an administrator grant of the
   scope (administrative surface in §5)"; §5.10 is that surface.
4. **Browser-first attach is implementable:** the browser `WebSocket`
   constructor cannot set an `Authorization` header (verified during
   deliberation — OBJ-3 closed-green); the device attach rides the URL
   token the way §3.3 does, and the long-lived credential rides `fetch` on
   the mint surface, where browsers can set headers.
5. **Harness floor test:** attach two devices; revoke one mid-stream; assert
   (a) zero subsequent host-bound envelopes carry the revoked `deviceId`,
   (b) zero downlink frames reach the revoked socket, (c) the other
   device's stream is byte-identical to a no-revocation run.
6. **Distinct-surface rule:** a device presenting the host's §3.3 tunnel
   token over the host URL is non-conformant — that token carries no device
   identity; the distinct `/<tunnelId>/devices` path makes the carve-out
   structural.
7. **pushProvider matches the reserved shape and default** (card
   acceptance): closed union, default `"webpush"`, both observation points
   normative.

## 18. Tradeoffs accepted (from the deliberation, recorded so the owner need not re-argue)

- §5 grows a connection surface (mint + upgrade) the card's scope list
  didn't name explicitly — accepted because §4.1 delegates it and no other
  section can carry it.
- Two-credential device model (long-lived opaque secret → short-lived
  single-use connection token) adds one endpoint versus dialing with a
  long-lived bearer — worth it: keeps INV-5 true at the data plane and the
  long-lived secret out of WebSocket URLs.
- No wire surface for managing per-tunnel grants in v1; `403
  tunnel_not_granted` at the mint is the only observable.
- Device records retained after revocation (unlike §3.5's tunnel rule) —
  deliberate, in service of audit identity; the no-recycle corollary guards
  it.
- Registration is admin-minted rather than self-enrolling (R6, per Q3);
  OAuth token responses are closed REQUIRED-field tables, so self-enrollment
  would strand `pushProvider`/`displayName` with no writable home.
- `POST /devices` returns `200`, not `201` — §3.2's stated precedent.
