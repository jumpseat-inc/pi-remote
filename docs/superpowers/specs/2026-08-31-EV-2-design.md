# EV-2 Design Spec — Control-plane tunnel REST client

Card: `EV-2` (EPIC-1) — "Control-plane tunnel REST client"

Status: settled by Council deliberation (rounds converged), Skeptic protocol verification (step 4), and product-owner rulings (Items 1–4) applied and binding. This file is the **complete** design. The owner reads only this file. If anything here is ambiguous, the design is wrong.

## 0. What the card is

Implement `src/tunnel.ts`: the control-plane REST client that creates a tunnel via `POST /tunnels` using the enrollment credential, consumes the returned signed one-time `wss://` URL, and deletes the tunnel via `DELETE /tunnels/:id` on teardown — **the only code besides `transport.ts` that touches the network**. It presents the enrollment credential (provisioned by `/rc:login`, EV-7) as opaque, and hands the validated signed one-time `wss://` URL plus an absolute deadline to the transport (EV-3). It is host-side plumbing with no direct user surface, but its failure copy indexes the `/rc`/footer status the user sees (EV-8 renders it).

## 1. The settled architecture (binding)

`tunnel.ts` is a **pure, STATELESS REST client** over HTTP(S) only. It exposes three stateless request functions, one error type, and one pure copy map:

```
createTunnel(input, deps)        -> Promise<{ tunnelId: string; url: string; expiresAt: number }>
refreshAccessToken(refreshToken, deps) -> Promise<{ accessToken: string; refreshToken?: string; expiresAt: number }>
deleteTunnel(tunnelId, deps)     -> Promise<void>
```

- **No module-level mutable state** — none whatsoever (the discovery-cache limit, O7, is honored inside the request functions or a closure-bound memo, never a top-level mutable).
- **No `ctx`** — no session/UI/pi wiring. `tunnel.ts` never calls `setStatus`, never reads pi settings or `process.env`.
- **No `WebSocket`** — tunnel.ts never dials. "Consumes" the signed URL = **runtime-validates it and hands `{url, expiresAt, tunnelId}` to EV-3**; it never connects.
- **Dependencies injected**: `fetch` and `now` (a clock returning epoch ms) are constructor/parameter-injected so the module is unit-testable without a real control plane and without a real clock. The base `serverUrl` and the enrollment credential are function parameters / an injected config object — never read from `process.env` or pi settings.
- **Fetch only in tunnel.ts; WebSocket only in transport.ts.** This resolves the §3 contradiction (O1): tunnel.ts is the HTTPS REST client; transport.ts is the WS transport (see §5 amendment).

All render calls (`setStatus`, footer, `/rc` output) belong to EV-8. `tunnel.ts` only returns typed data/errors and ships the copy vocabulary (reason → copy), which EV-8 renders.

## 2. The three request functions

### 2.1 Discovery (shared, per serverUrl)

All control-plane endpoints are derived at runtime from RFC 8414 discovery (`GET {serverUrl}/.well-known/oauth-authorization-server`); **no endpoint paths are hardcoded**. `refreshAccessToken` needs `token_endpoint` (there is no separate `/refresh` endpoint). Discovery results are cached **per `serverUrl` within the request/closure scope** — never module-level state (O7). A failed or malformed discovery maps to the `control_plane_unreachable` reason (it is a network/metadata fetch failure — same user-line class as an unreachable control plane; the card and the 7-code vocabulary do not distinguish a separate `discovery_failed` reason).

### 2.2 `createTunnel`

- `POST /tunnels` with `Authorization: Bearer <access_token>`, payload: session id, session name, cwd, host metadata (all opaque host metadata, provided by the caller).
- Response `{ tunnelId, url, tokenTtl }`. **Runtime-validation gate**: `url` must be a `wss:` (or `ws:`) scheme string; `tokenTtl` must be a positive finite number. `expiresAt` is computed **at the conversion site** as `now() + tokenTtl * 1000` — an **absolute epoch-ms timestamp**, never a raw relative value (O2). A 0/negative/non-number `tokenTtl`, or a non-ws `url`, is a typed error before any dial (a `TunnelError` with the appropriate `kind`) — the one-time URL is never handed to a dialer invalid.
- Returns `{ tunnelId, url, expiresAt }`.
- **No auto-refresh inside `createTunnel`.** It does not refresh on 401; a 401 from create is a terminal rejection (`enrollment_expired`), matching spec §8. The one-silent-refresh is EV-8 policy (`ensureFresh` → create, ≤1 refresh per `/rc`), not a tunnel.ts behavior.
- **The signed one-time URL must never be persisted and must never appear in any error string or log message** (PI-SPEC §7.2 single-use/secret). On the happy path the caller (EV-3) dials it and tunnel.ts discards its reference; the tunnel grant (tunnelId + signed URL) is the only token discarded at teardown. **The enrollment credential survives teardown** and is EV-7's to persist (token-discard boundary, settled).

### 2.3 `refreshAccessToken`

- `POST {token_endpoint}` with `grant_type=refresh_token` and the current refresh token (RFC 6749 §6 / OAuth 2.1 §4.3; no separate `/refresh`).
- Returns `{ accessToken, refreshToken?, expiresAt }`. `expiresAt` is an **absolute epoch-ms timestamp** computed as `now() + expires_in * 1000` at the conversion site (O2). A rotated refresh token is returned (not applied internally) when the response carries one — **return-then-persist** is the persistence seam (O6): tunnel.ts returns rotated tokens; EV-8 persists them via the EV-7-owned settings keys. tunnel.ts itself never writes settings.
- The ≤1-per-`/rc` refresh cap is EV-8 policy, not tunnel.ts state.
- Converted timestamp uses `expires_in` (relative seconds); the raw relative value is never stored or returned (O2).

### 2.4 `deleteTunnel`

- `DELETE /tunnels/:id` with `Authorization: Bearer <access_token>`.
- **Best-effort on the wire; never blocks teardown** — a network failure is swallowed (the local tunnel grant is still discarded) so `off` never hangs on DELETE. HTTP 404/410 are treated as success (idempotent). Any other non-2xx surfaces as a `teardown_failed` result, but teardown proceeds locally regardless (spec §8: `/rc:off` idempotent, never gated on DELETE success).
- Second `deleteTunnel` of an already-cleared id is a no-op (idempotency is enforced by the caller/EV-8; deleteTunnel is safe to call with a cleared/absent id).

## 3. The error type and the reason→copy vocabulary

### 3.1 `TunnelError`

A single discriminated error type:

```
type TunnelErrorKind =
  | "unauthenticated"   // 401 — expired or revoked enrollment credential
  | "forbidden"         // 403 — valid credential lacking pi-remote:host scope
  | "unreachable"       // network/DNS/TCP/TLS failure or discovery failure
  | "server_error"      // 5xx
  | "validation"        // create response failed runtime validation (bad url/tokenTtl)
```

Each `TunnelError` carries `{ kind, reason, serverUrl, status? }`. `reason` is the semantic category resolved by the copy map (below). **No error string, no log line, and no copy ever contains the raw HTTP body, a stack trace, or the one-time tunnel URL** (only debug-level structured logging may carry a redacted trace; user strings never do).

### 3.2 The reason→copy map (settled + ruled)

`tunnel.ts` exports the pure map `reason → { footerState, userLine, severity }` and an **English default lookup** that resolves each `userLine` **message key** to its user-facing string. Per ruling Item 2, `userLine` is a **stable message key** (e.g. `"tunnel.error.unauthenticated"`), and tunnel.ts ships the English default for each key. Both live in tunnel.ts so the table is unit-testable without rendering (EV-8 renders). Future localization is a separate card adding a second lookup + resolver — **not part of EV-2**.

Reasons and their (footerState, key, English userLine, severity):

| `reason` | `kind` | footerState | `userLine` key | English userLine (the English default) | severity |
|---|---|---|---|---|---|
| `enrollment_expired` | `unauthenticated` | `error` | `tunnel.error.unauthenticated` | "Enrollment expired or revoked — run /rc:login" | `error` |
| `enrollment_rejected` | `forbidden` | `error` | `tunnel.error.forbidden` | "This host lacks the pi-remote:host scope — run /rc:login to re-consent; if the scope is missing after that, ask your control-plane admin to grant it" | `error` |
| `control_plane_unreachable` | `unreachable` | `error` | `tunnel.error.unreachable` | "Control plane unreachable at `<serverUrl>` — check your network and try again" | `error` |
| `server_error` | `server_error` | `error` | `tunnel.error.serverError` | "Control plane returned a server error — try again" | `error` |
| `teardown_failed` (DELETE non-2xx, non-404/410) | — | (no footer change; off proceeds) | `tunnel.error.teardownFailed` | "Failed to notify the control plane of tunnel teardown" | `error` (but no footer transition per spec §8) |
| `validation` (bad url/tokenTtl) | `validation` | `error` | `tunnel.error.invalidResponse` | "Control plane returned an invalid tunnel response" | `error` |

Copy rules (binding):
- **401 and 403 are distinct, non-identical rows** (ruling Item 1, Reading B). `enrollment_expired` (401) names only `/rc:login`; `enrollment_rejected` (403) names `/rc:login` **and** the distinct "ask your control-plane admin to grant it" clause. The two user-lines are never byte-identical. The card acceptance's "rejected credential" includes 403 (RFC 6750 §3 counts 401 and 403 as distinct rejection classes).
- `control_plane_unreachable` names `<serverUrl>` and **must not** contain "/rc:login" (a network fault is not an enrollment problem; `/rc:login` would not help).
- `server_error` is distinct from `unreachable`.
- The set of reasons emitted by tunnel.ts is closed to the rows above — no `unknown`/raw `http_401`-style leak.
- Every result is tagged with a **severity** field (ruling Item 4): tunnel.ts's obligation is to ship the severity tag; the footer **merge rule** is EV-8's policy (deferred to EV-8's deliberation, with the recorded non-binding preference that severity ordering is error > live > resyncing).

### 3.3 `already_live` (ruling Item 3)

`already_live` is **not an error** and is **not a severity-tagged reason**. It is the idempotent-while-connected acknowledgment, returned once by the `/rc` command output, with the **exact** copy:

> "already connected to `<serverUrl>`; ignoring this `/rc`"

- footer stays `live` (no transition, no severity tag, no journal entry — a successful no-op, not an error).
- `<serverUrl>` is the **configured control-plane server URL** (the URL the user's `/rc:login` was aimed at) — **never** the one-time tunnel URL (PI-SPEC §7.2: the tunnel URL is a secret that must never appear in copy).
- The idempotency guard that decides "already live" lives in EV-8 (an `activeTunnel: {tunnelId,url,expiresAt} | null` checked **before** `createTunnel`, keyed on "live" not "ever created" so EV-3 reconnect re-arm is not blocked). tunnel.ts's contribution is only that `createTunnel` is stateless and safely re-callable.

## 4. Seam boundaries (settled, from the deliberation)

- **tunnel.ts / transport.ts**: tunnel.ts = HTTP fetch only; transport.ts = WebSocket only. tunnel.ts validates and hands `{url, expiresAt, tunnelId}`; it never dials.
- **tunnel.ts / EV-8**: EV-8 sequences `ensureFresh` (≤1 refresh) → `createTunnel` → hand to EV-3; EV-8 holds the `activeTunnel` idempotency guard; EV-8 calls `setStatus` and renders copy (including `already_live`); EV-8 persists rotated refresh tokens via EV-7-owned keys (O6).
- **tunnel.ts / EV-7**: EV-7 provisions and persists the enrollment credential (access/refresh/tokenExpiry); tunnel.ts consumes it as opaque Bearer input and never writes settings. Teardown discards the tunnel grant, not the enrollment credential.
- **tunnel.ts / EV-3**: EV-3 dials the validated signed URL within `expiresAt`. Single-use-URL reconnect re-arm is EV-3/EV-8 scope (a follow-up), not an EV-2 blocker.

## 6. Test / gate contract (what the acceptance means)

A fixture suite `test/tunnel.test.ts` uses an **injected mock `fetch`** (a real in-repo fake control plane via `Bun.serve` binding 127.0.0.1, no real network, no env). It must assert, per the settleable claims and open objections:

- **Create success**: parsed `{tunnelId, url, expiresAt}`; `Authorization: Bearer <access_token>` header; the payload body fields (session id, session name, cwd, host metadata) present.
- **Validation**: a non-ws `url` or a 0/negative/non-number `tokenTtl` → typed `validation` error before any dial.
- **O2**: `expiresAt` is absolute epoch-ms `now + tokenTtl*1000`, computed at the conversion site; for refresh, `expiresAt = now + expires_in*1000`. No raw relative value is ever returned.
- **401 → `enrollment_expired`**: kind `unauthenticated`, copy resolved from key `tunnel.error.unauthenticated` contains "/rc:login", no raw body leak, no one-time URL.
- **403 → `enrollment_rejected`** (O3): kind `forbidden`, copy from `tunnel.error.forbidden` contains "/rc:login" **and** "admin"; the 401 and 403 user-lines are non-identical; no raw body.
- **Unreachable**: fetch network failure → kind `unreachable`, reason `control_plane_unreachable`, copy contains `<serverUrl>` and **does not** contain "/rc:login".
- **Server error**: 5xx → `server_error`, distinct copy from `unreachable`.
- **Refresh**: expired token + valid refresh → `refreshAccessToken` returns `{accessToken, refreshToken?, expiresAt}`; a rotated refresh token is returned (not applied internally) — the O6 return-then-persist seam.
- **Refresh failure**: refresh returns a rejection → error naming `/rc:login`, no `POST /tunnels` issued from `createTunnel` (no auto-refresh).
- **No auto-refresh inside createTunnel**: a 401 to `/tunnels` with an expired token does **not** trigger a refresh call from within `createTunnel` (O5, terminal 401).
- **Delete + discard**: `deleteTunnel` issues exactly one DELETE; 404/410 treated as success; a network-failed DELETE is swallowed (does not throw); the tunnel grant is cleared so a second call is a no-op.
- **Already_live copy**: the exact sentence "already connected to `<serverUrl>`; ignoring this `/rc`" is available as copy, with `<serverUrl>` the control-plane server URL — and the one-time tunnel URL never appears in any copy.
- **Discovery cached per serverUrl (O7)**: two `createTunnel`/`refreshAccessToken` calls on the same `serverUrl` fetch discovery once; discovery is not module-level state.
- **O1 seam gates**: `grep` asserts no `WebSocket(` / `wss://` literal in `src/tunnel.ts`; no `process.env` in `src/tunnel.ts`; no `PI_REMOTE_HOST_KEY`-style hardcode anywhere.
- **Copy map**: the reason→copy map resolves each key to its English default; the 401 and 403 lines differ; the reason set is closed to the rows in §3.2.

## 7. Explicit non-goals (from the deliberation record)

- **No dialing** — tunnel.ts never opens a WebSocket; EV-3 owns the socket.
- **No `setStatus` / no rendering** — EV-8 owns the footer and `/rc` output; tunnel.ts ships the copy map.
- **No idempotency guard** — EV-8 owns `activeTunnel`; tunnel.ts is stateless and re-callable.
- **No auto-refresh-on-401 inside createTunnel** — O5; a 401 from create is terminal.
- **No persistence** — tunnel.ts never writes settings; rotated refresh tokens are returned for EV-8 to persist via EV-7 keys; no token is ever persisted by tunnel.ts.
- **No single-use-URL reconnect re-arm** — EV-3/EV-8 scope / follow-up, not EV-2.
- **No localization** — English-default only, per ruling Item 2; a future card adds a second lookup + resolver.
- **No footer-merge rule** — EV-8's policy (ruling Item 4); EV-2 only ships the severity tag.
- **No control-plane implementation** — §10 keeps the server out of repo scope (the "ask your control-plane admin" clause is a user instruction, not a server contract).
- **No changes to PI-SPEC beyond the §3 line** in §5 above.
