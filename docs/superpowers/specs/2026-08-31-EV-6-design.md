# EV-6 Design Spec — Remote Input Injection

Card: `EV-6` (EPIC-1) — "Remote input injection"

Status: settled by Council deliberation (2 rounds, converged ≤ cap), Skeptic
attack (7 claims all closed-green, no open objections), consolidation, and
product-owner ruling **R2** + steward ruling **R3** (binding, applied —
verbatim records in `council/cards/EV-6.md`). This file is the **complete**
design. If anything here is ambiguous, the design is wrong — so it is not.
The owner reads only this file (plus the files it names). The owner's
non-goal boundary is EV-8 (live wiring in `src/index.ts`); EV-6 builds and
unit-tests the pure module and syncs PI-SPEC §5.4 only.

## 0. What the card is

Implement `src/inject.ts`: a pure module that converts inbound AG-UI
user-message frames into `pi.sendUserMessage` calls with the correct
`deliverAs` mode for idle / mid-stream / queued input, and resolves pending
human-input prompts (`pi.human_input`) with the sending `deviceId` recorded.
**R3 (Side B) is binding:** the steering fallback is the **permanent**
product behavior — pi-remote does not sponsor or wrap the host UI, and the
direct-resolution seam (`resolvePendingPrompt`) is a **test-only** fixture
seam. **R2 (Position A) is the durable user-facing contract:** a single
stated-sentence notice on the first fallback-to-steer occurrence in a
session; silent thereafter.

**Files touched by the PR:** `src/inject.ts` (new), `src/translate.ts`
(additive, one-line widening: `TextMessageStartFrame { name?: string }`),
`test/inject.test.ts` (new) + any fixtures, `docs/PI-SPEC.md` (§5.4 sync
only), `docs/superpowers/plans/2026-08-31-EV-6-implementation.md` (new, the
owner's plan). **Nothing else.** `src/index.ts` is NOT touched (EV-8's
wiring); existing 62 tests stay green.

## 1. The settled design (binding)

### 1.1 Module surface (`src/inject.ts`)

Pure, STATELESS-of-globals module with an injected-deps factory (matches the
repo's `createTransport` / `createState` DI style). It holds no
WebSocket/timer/`randomUUID`/`Date.now` state of its own — only the
session-bound message-assembly buffer, the (promptId → occurrence) pending
registry, and the R2 "announced this session" boolean, all instance state.

```ts
export type DeliverAs = "steer" | "followUp";

/**
 * Pure decision: the deliverAs for an injection, given the SDK's isStreaming
 * read at injection time and the optional wire intent (validated name).
 * NEVER returns an undefined deliverAs while streaming (the never-throw
 * property): streaming + steer|unknown|absent → steer; streaming + followUp
 * → followUp; idle → no deliverAs.
 */
export function pickDeliverAs(isStreaming: boolean, intent?: string): { deliverAs?: DeliverAs };

export type InjectResult =
  | { kind: "ignored" }                                    // non-final / non-injectable / malformed frame
  | { kind: "injected"; deliverAs?: DeliverAs }            // a remote user message was injected
  | { kind: "resolved"; promptId: string; direct: true; deviceId?: string } // fixture seam returned true (test only)
  | { kind: "steered_fallback"; promptId: string; text: string; direct: false; deviceId?: string; reason: "mode" }
  | { kind: "stale"; promptId: string; deviceId?: string } // already-consumed prompt; surfaced, NOT delivered

export interface InjectDeps {
  /** Inject remote text into the live session, pi-side. */
  sendUserMessage: (content: string, opts?: { deliverAs?: DeliverAs }) => Promise<void>;
  /** SDK run-state at injection time (same synchronous tick as sendUserMessage). */
  isStreaming: () => boolean;
  /**
   * TEST-ONLY SEAM (R3, Side B). In production this returns false, so every
   * approval answer that would need direct resolution falls back to steer.
   * A future post-epic card (only if pi exposes a public resolve API) may
   * wire it live; EV-6 does not.
   */
  resolvePendingPrompt: (promptId: string, result: unknown, deviceId?: string) => boolean | Promise<boolean>;
  /** Emit an outbound CUSTOM control frame back to the remote client. */
  emitCustom: (name: string, value: unknown) => void;
  /** R2 loud-once session flag (optional; defaults to internal instance boolean). */
  hasAnnouncedFallback?: () => boolean;
  markAnnouncedFallback?: () => void;
}

export interface Injector {
  /** Process one inbound envelope frame. NEVER throws. */
  handle(env: InboundEnvelope): Promise<InjectResult>;
  /**
   * Host-side seam, wired by EV-8: register a raised pending human-input
   * prompt and return its per-promptId occurrence number (R1). Called
   * alongside the outbound `pi.human_input` raise.
   */
  registerPrompt(input: { promptId: string; kind: string; prompt: string }): { occurrence: number };
}
export function createInjector(deps: InjectDeps): Injector;
```

`InboundEnvelope` is `{ v, seq, ack, deviceId?, frame }` — the settled
4-key+deviceId envelope from `transport.ts`. `deviceId` comes **only** from
the envelope, never from inside a frame, and is carried structurally into
`InjectResult` — never smuggled into message text.

### 1.2 Remote user message injection (idle / mid-stream / queued)

Wire contract (settled): inbound `TEXT_MESSAGE_START` `{ type, messageId,
role: "user", name?: "steer" | "followUp" }` → one or more
`TEXT_MESSAGE_CONTENT` → `TEXT_MESSAGE_END`. The extension assembles the
content into a single text string and injects **at END**:

```
deliverAs = pickDeliverAs(deps.isStreaming(), validateName(start.name))
sendUserMessage(assembledText, deliverAs ? { deliverAs } : undefined)
→ { kind: "injected", deliverAs? }
```

- **Intent channel = the `name` field** on `TEXT_MESSAGE_START`. It must be
  runtime-validated against exactly `{ "steer", "followUp" }`; any absent or
  unknown value is treated as absent (never passed to `deliverAs`). This is
  a documented pi-remote extension convention — `name` is otherwise a free
  sender-name string in AG-UI, and the relay treats frames opaquely.
- **Run-state source = SDK `isStreaming`**, read at injection time in the
  **same synchronous tick** as `sendUserMessage` (no intervening `await`).
  `isStreaming`/`isIdle` are the same boolean inverted; the injector reads
  `isStreaming` to mirror the SDK's own branch and guarantee the never-throw
  property (never call `sendUserMessage` with undefined `deliverAs` while
  streaming — the SDK throws in `prompt()` in that
  case).
- Only `role: "user"` messages are injected. Non-user roles and malformed
  sequences (`CONTENT`/`END` for an unopened `messageId`, `START` with a
  non-string `messageId`) are ignored: no `sendUserMessage`, no throw.
- **Replay-correctness invariant:** inject.ts NEVER registers an `input`
  extension handler and NEVER returns `{ action: "handled" | "transform" }`
  — enforced by static grep (negative invariant). Every injection passes
  through untouched, so the JSONL record is indistinguishable from typed
  input.
- **Never-drop:** idle-and-streaming routing never silently drops a user
  message; mid-stream always carries `deliverAs`.

### 1.3 Pending human-input approval resolution

**Raising (host side, seam only in EV-6):** when the host raises a
`ui.confirm`, EV-8 wires `injector.registerPrompt({ promptId, kind, prompt })`
(which returns the next `occurrence` for that `promptId`, starting at 1)
alongside the existing outbound `pi.human_input` raise from translate. This
gives the (promptId → occurrence) registry that R1 requires: two identical
prompts produce two distinct `(promptId, occurrence)` entries. EV-6 unit
tests call `registerPrompt` directly to seed the registry.

**Resolution (inbound wire, from the remote client):** a `CUSTOM` frame

```
{ type: "CUSTOM", name: "pi.human_input.response",
  value: { pi: "ui.confirm.response", data: { promptId, occurrence, response } } }
```

`deviceId` is read from the envelope, never the frame. The injector
`handle` path:

1. Validate: `promptId` is a non-empty string, `occurrence` is a finite
   number, `response` present. Any malformed value → `{ kind: "ignored" }`
   (no throw, no `sendUserMessage`, nothing emitted).
2. Registry lookup by `(promptId, occurrence)`:
   - **Live (present + unconsumed)** — this device wins. Consume the entry
     (first-wins), record the winner `deviceId`. Then:
     - Call `resolvePendingPrompt(promptId, response, deviceId)`. If it
       resolves truthy → `{ kind: "resolved", promptId, direct: true,
       deviceId }` (only reachable through the fixture in tests — R3).
     - Otherwise (production: always) → **steering fallback**:
       `sendUserMessage(response, { deliverAs: isStreaming() ? "steer" :
       undefined })` — **never dropped** — plus the R2 loud-once notice
       (below), then `{ kind: "steered_fallback", promptId, text: response,
       direct: false, deviceId, reason: "mode" }`.
   - **Stale (present + already consumed)** — a late/losing race answer.
       Emit `emitCustom("pi.human_input.stale", { promptId, winnerDeviceId? })`
       and return `{ kind: "stale", promptId, deviceId }`. It is **NOT
       delivered** (never re-inject a duplicate answer). Does NOT trigger the
       R2 loud-once fallback notice.
   - **Unknown (promptId not in registry)** — the prompt belongs to another
     extension or was never observed (the "mode does not support direct
     resolution" case). **Steering fallback, never dropped**:
       `sendUserMessage(response, { deliverAs: isStreaming() ? "steer" :
       undefined })` + R2 loud-once notice, then
       `{ kind: "steered_fallback", ... reason: "mode" }`.

**R2 loud-once notice (binding):** on the first fallback-to-steer occurrence
in a session (the first `reason: "mode"` steer of an approval answer), emit
`emitCustom("pi.human_input.fallback_to_steer", { promptId, statement })`
where `statement` is **a sentence, not a glyph**, that (a) names the cause
class (host mode cannot resolve the pending prompt directly — RPC/print/
headless, or the prompt belongs to another extension) and (b) honestly states
the reply was surfaced as a steering message instead of being delivered
directly. Default copy — `"This reply was surfaced as a steering message
instead of being delivered directly: this host cannot resolve the pending
prompt directly."` Subsequent fallback-to-steer occurrences in the same
session emit **no** notice (the `hasAnnouncedFallback`/`markAnnouncedFallback`
session flag, defaulted to internal boolean). No re-stating of what the
system already knows; no fabrication.

### 1.4 Determinism

- No `crypto.randomUUID` / `Date.now` / `Math.random` in `inject.ts`.
  The registry and buffer use only the values carried in the wire frames.
- Pure decision surfaces (`pickDeliverAs`) are exported for direct unit
  testing.

### 1.5 PI-SPEC §5.4 sync (same PR)

Amend `docs/PI-SPEC.md` **§5.4 only** to make the settled wire contracts and
the R3/R2 reality explicit, without disturbing the section's existing
table. Concretely add, beneath §5.4's table + the existing
"`input` event ..." paragraph:

1. **Intent field:** the delivery-intent (`steer`/`followUp`) rides the
   optional `name` field on inbound `TEXT_MESSAGE_START`; absent or unknown
   = idle-decided (mid-stream default is `steer`). No fifth envelope key, no
   CUSTOM wrapper for the common user-message path.
2. **Approval response frame:** inbound `CUSTOM pi.human_input.response`
   with `value.data: { promptId, occurrence, response }`, matched against
   the extension's (promptId → occurrence) pending registry; `deviceId` is
   taken from the envelope and recorded with the resolution.
3. **Permanent steering fallback:** (R3) direct resolution is not wired —
   the response is surfaced as a steering message via `sendUserMessage`
   (the spec-mandated path, §5.4 row 4), with a loud-once
   `pi.human_input.fallback_to_steer` notice (R2) on the first such
   occurrence per session; already-resolved (stale) answers are surfaced
   as `pi.human_input.stale`, not delivered. PI-SPEC is the durable record
   that this is permanent behavior, not a stopgap.

No other PI-SPEC section changes.

## 2. Non-goals (explicit)

- **Live wiring** into `src/index.ts` (pi.on → injector.handle) is **EV-8**.
  EV-6 ships the pure module + its unit tests + the §5.4 sync only.
- **Host-UI sponsorship / wrapping** (`setUIContext`, a live resolve path)
  — **R3 rules it out.** `resolvePendingPrompt` stays a test-only fixture
  seam. Any EV-7/EV-8 design that reopens it must name the four items in the
  binding general rule (recorded in `council/cards/EV-6.md`).
- **`pi.human_input.resolved`** host-side completion event (needs a new
  `ui_prompt_end` PiEvent in EV-4 + EV-8 wiring) — **forward dependency,
  NON-BLOCKING** for EV-6; filed as a follow-up card, not built here.
- Removing the dead `user_input` PiEvent in translate.ts — recorded as a
  step-4 non-blocking finding (FLLWUP-candidate), not part of this PR.
