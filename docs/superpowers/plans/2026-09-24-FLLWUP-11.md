# FLLWUP-11 — Reconcile the ExtensionAPI stand-in's non-`on` members with the real SDK surface

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every non-`on` member of index.ts's `ExtensionAPI` stand-in either exists on the installed pi SDK's `ExtensionAPI` (typed against its real signature) or is removed, so the extension loads against a real pi host without a TypeError.

**Architecture:** Keep the three members the real API actually has (`on`, `registerCommand`, `sendUserMessage`) with real signatures; remove the rest. Context-dependent needs (`ctx.ui.setStatus`, `ctx.ui.input`, `ctx.isIdle()`, `ctx.sessionManager`, `ctx.cwd`) are re-homed through a lazy context holder captured from real SDK callbacks (the `ExtensionFactory` receives only `pi`; `ExtensionContext` arrives per event/command handler). The remaining members re-home to documented local capabilities (`process.env`, `node:os`, local config-dir resolution). All vendored SDK signatures live beside FLLWUP-9's `pi-sdk-on.ts` pattern with provenance notes.

**Tech Stack:** Bun, TypeScript (strict), `bun test`; no SDK dependency (R-TYPE-1 — vendored signatures only).

**Spec:** council/cards/FLLWUP-11.md (Acceptance) + run ruling R-TYPE-1.

## Verified SDK ground truth (dist/core/extensions/types.d.ts, loader.js, core/session-manager.d.ts)

- `ExtensionHandler<E, R = undefined> = (event: E, ctx: ExtensionContext) => Promise<R | void> | R | void` (~line 974).
- `ExtensionAPI` (~978): `on` (returns `() => void` unsubscribe), `registerTool`, `registerCommand(name, { description?, handler: (args: string, ctx: ExtensionCommandContext) => Promise<void> })`, `registerShortcut`, `registerFlag`, `getFlag`, renderers, `sendMessage`, `sendUserMessage(content: string | (TextContent|ImageContent)[], options?: { deliverAs?: "steer"|"followUp"; expandPromptTemplates?: boolean }): void`, `appendEntry`, session-name get/set, `setLabel`, `exec`, tool getters/setters, `setModel`, thinking-level get/set, `registerProvider`, `unregisterProvider`, `events`. **No** `getSetting`, `env`, `setStatus`, `input`, `sessionId`, `readActiveBranch`, `isIdle`, `configDir`, `version`, `platform`, or `arch` — confirmed in the type surface AND in loader.js's runtime `api` object (~line 200), so `pi.configDir()` at load is a real TypeError in a host.
- `ExtensionContext` (~210): `ui: ExtensionUIContext` (`setStatus(key, text?)`, `input(title, placeholder?)`), `mode`, `cwd`, `sessionManager: ReadonlySessionManager` (`getSessionId()`, `getBranch(fromId?): SessionEntry[]`), `isIdle()`, …
- `ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>` — **no ctx at factory time**; ctx arrives per handler invocation.
- SDK session entry (`core/session-manager.d.ts`): `{ type, id, parentId, timestamp, … }`; message entries embed `message: AgentMessage` (pi-ai `Message`: roles `system|user|assistant|toolResult`; content blocks `text|thinking|toolCall|image`).
- Config dir (dist/config.js): `ENV_AGENT_DIR = "PI_CODING_AGENT_DIR"` → else `$HOME/.pi/agent`.

## Review Focus

- A ctx-dependent dep read before any host callback delivered a context → `requireCtx()` fails loud (clear error), never silently misbehaves.
- Settings file absent/corrupt → fail-open (no setting), never throw at load.
- Replay of a real `getBranch()` stream must skip unknown/unused entry kinds, not crash (forward-compat discipline already in the adapter).
- The load smoke must fail if the entry ever touches a member outside the real host surface (strict Proxy), not just if types drift.
