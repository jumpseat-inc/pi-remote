## Intent

The registry and trust model, server-side and on the page: device registration
and credential issuance; tenant membership management; the grant-enforcement
algorithm at fan-out (tenant membership is the base grant; narrower per-tunnel
restrictions may layer on top but clients never depend on them); revocation
semantics (a revoked device's frames stop arriving; clients treat the server as
authority); the reserved push record shape (`pushProvider: "webpush" | "apns" |
"fcm"`, default `"webpush"` — no vendor account needed for the browser-PWA
client first); and the trust summary **stated from the server's side of the
table**: the server holds the signing key and the registries, its frame
visibility is total within its tunnels, its compromise blast radius is its own
statement to make and this document makes it. Multi-tenancy is carried entirely
by credentials at three contract points (enrollment token, tunnel token, device
grants) — each mapped to a server-side mechanism. Non-normative guidance:
registry storage, admin operations, key ceremony.

**Self-containment requirement:** the trust table is restated in full from the
server's perspective; no row may be defined by reference to another document.

## Acceptance

- Device registration, membership, grants, and revocation are specified to
  implementation precision, with no contradiction to the shipped client's
  expectations.
- The pushProvider reservation matches the reserved shape and default.
- The trust summary is restated completely from the server's perspective,
  including an honest statement of what server compromise exposes.
- Multi-tenancy is specified as carried entirely by credentials, with the
  three contract points (enrollment token, tunnel token, device grants) each
  mapped to a server-side mechanism.

**§5 must close a hole §4 itself opens, not just describe a registry.** §4.1 explicitly delegates: *"The population of granted connected devices is defined by the registry and grants section (§5)"* — yet §1–§4 contain **no device-authentication contract anywhere**. §3.1 pins exactly one successful upgrade per tunnel (the host's), §3.4's handshake is the host's token only. So a device cannot currently connect to the data plane at all under this document, and §5 must specify the device attach or the fan-out of §4 is unimplementable. §5 therefore carries one normative connection surface (device attach) plus the registry/admin surfaces.

**Proposed §5 layout:**

- **§5.1 The device object and identity** — the registry record: `deviceId` (server-assigned, opaque; MUST be unique within its tenant — the wire never needs more, since a host only sees `deviceId` inside one (tenant, tunnel)-bound stream; global uniqueness MAY), `tenantId` (immutable after registration), `displayName` (informational), `status` (`active | revoked`), `pushProvider` (§5.6), creation time. `deviceId` MUST be stable for the registration's lifetime — restated consequence of INV-4 plus a restated client-side expectation: the host tracks per-device acknowledgements keyed by the envelope `deviceId` and tags input attributions with it, so a server that re-assigned `deviceId` per connection would make per-device bookkeeping and audit identity meaningless.
- **§5.2 Device registration and credential issuance** — `POST /devices`, admin-authenticated (§5.5). Response carries `deviceId` and the **device credential** shown once. Credential model (recommendation): one long-lived, revocable bearer secret — the device analogue of §2's refresh token — presented only to the control plane over TLS; it mints **short-lived, single-use, signed device connection tokens** for the data plane. Keeps INV-5 clean (the long-lived thing never rides a WebSocket URL) and mirrors the host model exactly (refresh → short-lived capability → dial). One-time display, never re-retrievable — restating §2.8's replace-not-merge storage discipline for the device side.
- **§5.3 Tenant membership** — normative: every device belongs to exactly one tenant, fixed at registration; membership **is** the base grant (INV-3/INV-4 made concrete). Moving a device between tenants = revoke + re-register.
- **§5.4 The device attach (data-plane connection for devices)** — two surfaces: `POST /device/connections` with body `{tunnelId}`, Bearer device credential → `200 {url, tokenTtl}` with a signed one-time `wss://…/<tunnelId>?token=…` URL whose token carries `tenant_id, tunnel_id, device_id, exp, jti` — same claim grammar, same 5–300 s TTL bounds, same single-use consumption as §3.3/§3.4. The attach handshake: ordered checks mirroring §3.4 exactly (extract → verify signature → expiry vs server clock → tunnel binding/existence → atomic `jti` consume), then two registry checks: device exists and is `active` (else `401 invalid_token` — a revoked device's credential does not authenticate), and grant coverage (else `403 tunnel_not_granted`). On success the server binds the connection to `(tenant, tunnel, deviceId)` and this binding is the **only** source of the server-stamped envelope `deviceId` (restating §4.2's trust rule with its mechanism now on the page).
- **§5.5 Grants and the enforcement algorithm at fan-out** — floor (MUST, harness-observable): the server MUST NOT deliver any data-plane frame for a tunnel to a device that is not a member of the tunnel's tenant (restated INV-4); a harness playing the host with a revoked/non-member device attached asserts zero delivered frames. Ceiling (MAY): the server MAY layer narrower per-tunnel restrictions that only ever reduce access below the base grant. No wire surface for managing them is specified in v1; a layered denial is expressed only as the attach-time `403 tunnel_not_granted`. Algorithm (each line a restated consequence of INV-1/INV-4): on host-produced frame F for tunnel T — for each attached device d (snapshot at delivery time): revoked → detach, never deliver; tenant ≠ T.tenant → detach, never deliver; layered policy denies → skip; else deliver (same frames, same order, no per-device filtering, restated §4.6). Uplink half (audit-critical): after revocation the server MUST NOT merge any further uplink frame from that device into the host-bound stream — a revoked device's input must never reach the host, because the host attributes input by the server-stamped `deviceId`; delivering a revoked device's frame would launder an audit identity. Frames already merged before revocation are not recalled (stream is append-only; INV-1).
- **§5.6 Revocation semantics** — the control-plane act: `DELETE /devices/{deviceId}` (admin, idempotent, `204`; unknown/foreign/already-revoked = `404`-only, mirroring §3.5's no-existence-leak rule). On success, in order: (a) registry status → `revoked`, credential dead — subsequent `POST /device/connections` is `401`; (b) fan-out stops **immediately** (§4.6's MUST, mechanism here); (c) live socket SHOULD close promptly with `1000` (§4.8); (d) per-device bookkeeping and any outstanding catch-up discarded per §4.5; the stream and other devices unaffected; a resync already triggered is not recalled. Unlike tunnels, the **record is retained, not erased** — the envelope `deviceId` audit trail must remain interpretable — a documented, reasoned difference from §3.5's no-tombstone rule.
- **§5.7 The reserved push record shape** — normative, wire-observable at registration: `POST /devices` MAY carry `pushProvider`; MUST be exactly one of `"webpush" | "apns" | "fcm"`; absent = default `"webpush"`; any other value = `400 invalid_request`. The server stores and returns it; **no push delivery behavior, endpoint, or payload is specified** — the field is a reservation so the browser-PWA client (which needs no vendor account) works first. Settable at registration; mutation reserved.
- **§5.8 The trust summary, from the server's side of the table** — self-contained restatement (no row defined by reference): rows for Host / Server / Client device / Admin-operator, each with Holds / Can do / Server-visible consequence. The compromise statement: a compromised server exposes every frame payload of every tunnel it serves, in the clear — no payload-level end-to-end encryption is specified anywhere in this document, and TLS terminates at the server. It can mint valid connection tokens for any tunnel of any tenant it hosts, forge `deviceId` stamps (envelope audit identity is only as trustworthy as the server), impersonate any host or device, and read both registries. The blast radius is bounded by the deployment, not the protocol — INV-1's relaying-opaquely obligations are behavioral constraints on a conformant server, not cryptographic guarantees against a compromised one.
- **§5.9 Multi-tenancy: the three credential contract points, mapped to mechanisms** — each row self-contained: enrollment token (OAuth access token; `tenant_id` claim, tenancy derived solely from the token, never from request fields — §2.6 restated) enforced at every control-plane request; tunnel token (signed one-time connection token; `tenant_id` claim read off the verified token, tunnel-existence binding checked at upgrade — §3.4 restated) enforced at host handshake; device grants (device credential → device connection token; registry row's tenant binding carried into the token's `tenant_id`/`device_id` claims; attach-time and per-delivery checks) enforced at device handshake + every fan-out delivery. Plus: the frame envelope carries no tenant field anywhere; every connection is bound to exactly one (tenant, tunnel) pair before a single frame flows.
- **§5.10 Guidance (non-normative, one shape each per R3):** (a) registry storage sketch — one row per device keyed by `deviceId`: `tenant_id`, `display_name`, `status`, `push_provider`, `credential_hash` (never the credential), `created_at`; constant-time credential-hash comparison. (b) admin operations — bootstrap the first admin out-of-band per deployment, scope-grants ride the same surface the 403-remedy table points at, device lifecycle register → (revoke), audit = retained device rows plus host-side attribution. (c) key ceremony — signing keys generated on the server, never exported to hosts or devices; asymmetric pair with rotation per §3.3's existing guidance.

**Admin authentication (R6):** the same authorization server as §2, with an admin credential carrying scope `pi-remote:admin`; tenancy derived from its `tenant_id` exactly as §2.6 — an admin is tenant-bound by credential like everything else (INV-3 holds with no new mechanism), and tenant creation/bootstrap stays deployment-local (guidance only).

**Tradeoffs accepted:** §5 grows a connection surface (§5.4) the card didn't name explicitly — accepted because §4.1 delegates it and no other section can carry it. Two-credential device model (long-lived secret → short-lived connection token) adds one endpoint versus a single long-lived bearer dialed directly — worth it: keeps INV-5 true at the data plane, keeps the long-lived secret out of WS URLs (which end up in browser history and server logs), same shape the host side already uses. No wire surface for per-tunnel grants in v1 — clients never depend on them; `403 tunnel_not_granted` at attach is the only observable. Device records retained after revocation (unlike §3.5's tunnel tombstone ban) — deliberate, reasoned, in service of audit identity.

**Testable claims:** (1) the device-connection gap is real — no sentence in §1–§4 specifies how a client device authenticates to the data plane, and §3.1 forbids reusing the host's handshake; §5 without a device-attach spec leaves §4.6's "input from any granted device is accepted" unimplementable. (2) `deviceId` stability is load-bearing in the shipped host — per-device ack tracking and attribution are keyed by it; a §5 permitting per-connection reassignment contradicts this. (3) the scope-grant forward reference dangles without §5 — §2.5, §2.7 and §3.6 all route the 403 remedy through "an administrator grant of the scope (administrative surface in §5)". (4) browser-first device attach cannot use headers — the browser WebSocket API cannot set an `Authorization` header, so the device attach MUST ride the URL query the way §3.3 does (client-side half is inferred — the PWA is not in this repo; flagged as such). (5) harness test for the floor: attach two devices, revoke one mid-stream, assert (a) zero subsequent host-bound envelopes carry the revoked `deviceId`, (b) zero downlink frames reach the revoked socket, (c) the other device's stream is byte-identical to a no-revocation run.

**Judgment calls needing a ruling:** (1) device attach placement and shape — in §5 (my position), two-credential model (my rec) vs single long-lived device bearer at the handshake. (2) registration actor — admin-minted credential transferred out-of-band (my rec) vs invite/pairing-token redemption flow the device completes itself. (3) admin auth model — tenant-scoped `pi-remote:admin` on the existing authorization server (my rec) vs deployment-level operator credential outside OAuth; tenant creation stays out of scope. (4) `403 tunnel_not_granted` as the new error code for layered attach denial. (5) device-facing tunnel discovery — `GET /device/tunnels` listing live tenant tunnels (my rec) vs push-only discovery vs out-of-band only. (6) `deviceId` uniqueness scope — tenant-unique MUST + global MAY (my rec) vs globally-unique MUST. (7) revocation endpoint naming/retention — `DELETE /devices/{deviceId}` meaning revoke-with-retained-record (my rec) vs explicit `POST /devices/{id}/revocation`. (8) `pushProvider` mutability — registration-time only, mutation reserved (my rec) vs a normative update endpoint now.

Grounded in: `docs/SERVER-SIDE-SPEC.md` §1–§4 (read in full), `docs/PI-SPEC.md` §7.3/§7.4/§7.5 and §9.2, `src/transport.ts`, `src/inject.ts`, and `vault/wiki/`. The deliverable below is a §5 design; nothing written into the spec.

**Cross-seam reading — the contract as it actually is right now.** The load-bearing seam is not the registry record shape. It is that **§1–§4 define "granted connected devices" and "authenticated connection identity" but never define the surface that produces them, and two different sections each assume the other one owns it.** Three concrete findings:

1. **Nothing connects a device to the data plane.** §3.1/§3.3/§3.4 are written entirely from the host-dial direction: "exactly one connection token is issued per tunnel, and exactly one successful upgrade is ever admitted per tunnel"; the handshake partition `{101, 400, 401, 404, 409, 5xx}` and the `?token=` compact-JWS are host-specific. A device cannot use the §3.3 URL — a second upgrade of the single-use token is rejected `409 token_consumed` by §3.4. So devices must have a *second, distinct* connection surface. §4.1 says it out loud: "The population of *granted connected devices* is defined by the registry and grants section (§5)." §4.2 makes §5 the only place the trust anchor can be named: `deviceId` is "server-stamped from the authenticated connection identity" — and the identity is never defined. **The device data-plane connection surface is unambiguously §5's to specify, and the card's explicit scope list doesn't name it.** That is the single largest thing this card is about and doesn't know it's about.
2. **The third INV-3 contract point is actually two things.** A grant is server-side state; it is not something a device presents. What a device presents is a *credential*, and the grant is the server-side record that maps that credential to coverage. The recorded contract has "each device holds a `deviceId` + device credential" but never says what the credential *is*. §5 must name both halves: the device credential (the third point's credential) and the grant record (the server-side enforcement mechanism), and say explicitly that the device credential is the third contract point — not a fourth tenancy mechanism.
3. **The admin surface sits on top of §2's 401/403 contract, and §2 already handed §5 a debt.** §2.5 states `pi-remote:host` "does not confer … any administrative capability" and that "the administrative surface that governs scope grants belongs to the registry section (§5)." §2.7's `403 insufficient_scope` remedy is "re-consent … *plus an administrator grant of the scope*." So §5's admin surface must govern **scope grants** (at minimum `pi-remote:host`) as well as device membership — not just device CRUD. If admin is a *fourth* credential type, §5 has expanded the tenancy contract surface — which the binding rule forbids. If admin is a *scope on the existing enrollment-credential point*, no expansion occurs but §5 must say so in terms a server implementer can't misread.

Recorded client-side expectations (safe to restate, in this document's own words): `deviceId` server-stamped from connection identity, never device-supplied (§4.2); in-frame resume `deviceId` validated against connection identity (§4.5); host-bound envelope carries `deviceId` iff device-originated (§4.2); host reads envelope `deviceId` for attribution and trusts it with no verification. **Inference-only (flagged as such):** the device's connection mechanism, its credential format/claims, its enrollment flow, and the device WS handshake — none of these exist anywhere on the page today.

**Complete §5 design proposal:**

- **§5.0 Opening.** One paragraph stating what §5 closes: the two §4 forward references ("granted connected devices," "authenticated connection identity") and the §2.5/§2.7 forward reference ("the administrative surface that governs scope grants"). State that §3.1's single-token/single-upgrade rule governs the **host** connection and that device connections are a distinct surface, specified here.
- **§5.1 Device identity and the device credential** (normative shape). `deviceId`: server-assigned, opaque, URL-safe, globally unique (same terms as `tunnelId`, §3.1). It is the device's `sub` claim. Device credential = OAuth2 access token (+ refresh), issued by the §2.1 authorization server, scope `pi-remote:device`. This *reuses* §2's machinery; no new token format, no new signing path. Claims extend §2.6's table: `sub` (REQUIRED, = `deviceId`), `tenant_id` (REQUIRED), `scope` (REQUIRED, includes `pi-remote:device`), `exp` (REQUIRED), `iss`/`iat` (SHOULD). The credential is self-describing (INV-5); the server derives `deviceId` and tenant from the token alone, never from device-supplied bytes. **Explicit sentence:** the device credential *is* the third INV-3 contract point's credential; device enrollment reuses §2's flows (attended PKCE for the browser PWA; the device flow is permitted), and is *not* a fourth tenancy mechanism.
- **§5.2 Device registration** (mostly restatement + one normative point). Registration = §2 enrollment with scope `pi-remote:device`; the server creates the registry record at first token issuance. No new self-registration REST endpoint — the OAuth2 endpoints are the registration surface. Normative point: the server MUST create/update the registry record keyed by `sub` when it issues a device token, with the reserved `pushProvider` field of §5.7. Guidance (one shape): PWA uses attended PKCE with the loopback redirect.
- **§5.3 The device data-plane connection** (normative; the reframe's payload). Endpoint: `wss://<data-plane host>/<tunnelId>/devices`, credential presented as `Authorization: Bearer <device access token>` on the upgrade request. Explicitly a **distinct surface** from §3.3's host URL; §3.3's "final segment equals tunnelId" and §3.1's single-token rule do not apply to it. Ordered checks (mirroring §3.4's 400/401 boundary): (1) extract credential from the header — absent/malformed → `400 invalid_request`; (2) verify signature + `exp` → `401 invalid_token`; (3) scope check: token must carry `pi-remote:device` → `403 insufficient_scope` (§2.7's meaning, never merged); (4) tunnel existence (after auth, so no existence leak): absent/deleted → `404 unknown_tunnel`; (5) grant coverage: `token.tenant_id == tunnel.tenant_id` → else `403 grant_denied` (base grant); (6) attach socket; stamp `deviceId` = `token.sub` on every host-bound envelope the device produces, and validate in-frame resume `deviceId` == `sub` (§4.5). **Closed status partition: `{101, 400, 401, 403, 404, 5xx}`.** No `409` — device credentials are not single-use; reconnect re-dials with a (possibly refreshed) access token and resumes per §4.5. State the contrast with §3.4's single-use explicitly so a reader doesn't import it. Reconnect and refresh reuse §2.4's refresh semantics at the token endpoint.
- **§5.4 Grants and the enforcement algorithm** (normative base grant; narrower grants = guidance). Base grant (normative, restated INV-4/§4.6): a device may receive a tunnel's frames iff `device.tenant_id == tunnel.tenant_id`. Enforcement at two points: refuse at attach (§5.3 step 5) *and* re-check at every delivery opportunity — the second check is what makes mid-connection revocation take effect. Algorithm, stated once: at each fan-out delivery, the server delivers a host frame to a connected device iff (a) its socket is authenticated, (b) its grant covers the tunnel, (c) it is connected. Same frames, same order, no per-device filtering (§4.6 restated). Narrower grants: the server MAY layer per-tunnel or per-host restrictions; they are **never observable on the wire** — a device presents only its credential and receives frames or does not, and nothing in the protocol requires a device to know which rule denied it. The base grant is the only grant any conforming host or device needs. Guidance (one shape): a per-tunnel device-allowlist column consulted after the tenant-equality check.
- **§5.5 Admin/operator surfaces** (normative endpoints; the §2.7 debt + R6). Auth: `pi-remote:admin` scope carried on the **enrollment-credential contract point** (an operator enrolls via §2 requesting admin scope). Tenancy derived from the token (§2.6). This keeps INV-3's list at three points. Endpoints (prose + request/response tables, closed partitions): `GET /devices` → `200` device array, partition `{401, 403, 5xx}`; `DELETE /devices/{deviceId}` → `204`, revoke + deregister, idempotent, unknown/other-tenant → `404 unknown_device`, never `403` (no existence leak, mirroring §3.5), partition `{401, 403, 404, 5xx}`; `POST /subjects/{sub}/scopes` → `204`, grant a scope (`pi-remote:host` / `pi-remote:device` / `pi-remote:admin`) to an enrolled `sub` — the §2.7 re-consent companion, partition `{401, 403, 404, 5xx}`. 401/403 never-merge rule of §2.7 extends to every surface here, verbatim. New vocabulary entries (`unknown_device`, `grant_denied`) are §5-defined, named exactly once, following §3.6's closed-vocabulary pattern. Guidance (one shape): the admin *workflow* is non-normative; the endpoints and partitions above are the contract.
- **§5.6 Revocation semantics** (restatement of INV-4's consequences, not new rules). Revocation is a control-plane act: mark the device credential invalid (refresh and access), remove grant coverage, discard per-device bookkeeping (§4.5). Takes effect without host cooperation (INV-4). Data-plane consequences are §4's, restated here only: delivery stops at the next delivery opportunity, the socket SHOULD be closed promptly (§4.6), outstanding catch-up is cancelled and a sent `resync` is not recalled (§4.5). §5 adds nothing new — this subsection exists so an operator reading §5 alone sees the whole arc. Host-side effect, in this document's own words: the host has no revocation logic; frames from a revoked device simply stop arriving, and the server is the only authority (§4.2's trust rule, restated).
- **§5.7 Reserved push record shape** (normative reservation). The device registry record reserves exactly one field: `pushProvider`, closed union `"webpush" | "apns" | "fcm"`, default `"webpush"` — no vendor account, serves the browser-PWA client first. Push delivery itself is out of scope; no surface in this document carries push payloads. The name, the union, and the default are the reservation; future push surfaces extend from them.
- **§5.8 Multi-tenancy as server-side mechanisms** (restated INV-3, self-contained table). Three rows: enrollment credential (OAuth2 access token; authorization server validates; `tenant_id` claim scopes all host control-plane state) / tunnel connection token (compact JWS in the URL; server signs at create; `tenant_id` claim scopes the data-plane binding) / device credential + grant (device access token + registry record; `sub`=`deviceId`, `tenant_id` scopes attach and fan-out). Plus the INV-3 restatement that the envelope carries no tenant field and the server scopes relay/cache/fan-out state by the connection binding alone.
- **§5.9 Trust summary, from the server's side** (full restatement, no row by reference). Server holds: the token-signing key(s), the authorization-server registry, the device registry, the consumed-`jti` set, the live-tunnel records, the ring buffers, and every envelope byte on every tunnel it hosts. Server can do: issue/revoke enrollment credentials, mint/consume tunnel tokens, register/grant/revoke devices, stamp `deviceId`, enforce fan-out, relay. **Server compromise — stated honestly:** the server's MUST NOT (INV-1) is a behavioral obligation, not a cryptographic boundary. A compromised server can read, modify, drop, reorder, and fabricate frames on every tunnel it hosts; can stamp any `deviceId` (it is the trust anchor, §4.2); can mint valid enrollment, tunnel, and device credentials for any tenant in its registries; can exfiltrate opaque payload bytes. **Its blast radius is total across all its tenants and zero beyond them** — it cannot reach data or credentials for tenants it does not host. There is no host↔device integrity that excludes the server. Host compromise (from the server's side): a compromised host holds credentials for exactly one tenant, affects only its own tunnels, cannot mint tokens, cannot reach other tenants (INV-3 scoping). Device compromise: a leaked device credential reaches only its tenant and only the tunnels its grant covers; revocable at the control plane (INV-4).

**Judgment calls needing a ruling:** (1) admin auth model — tenant-scoped `pi-remote:admin` scope on the enrollment-credential point (my proposal, satisfies the no-expansion rule) vs a distinct deployment-operator credential (a *fourth* tenancy-carrying credential needing an explicit INV-3-expanding ruling). Highest-stakes open question. (2) whether the device connection surface is in §5's authority — my position: yes, §4.1/§4.2 forward-reference it there. (3) device credential = OAuth2 vs a distinct signed device token — I recommend OAuth2 (reuse §2, no new format); it makes the device handshake Bearer-header-shaped rather than `?token=`-shaped, unlike §3.4. If uniformity with §3.4 is required, a separate device connection token is the alternative — a new credential format needing its own ruling. (4) `pushProvider` normativity — "reserved" with no current consumer, so under the observation-point test it's arguably unenforceable as a MUST; I recommend normative as a record-shape reservation (observation point = the `GET /devices` response and the future push surface). (5) vocabulary extensions — `grant_denied`, `unknown_device`, and whether grant-coverage denial may share `insufficient_scope` — closed-vocabulary additions; each named exactly once and never merged. (6) admin scope-grant endpoint shape — `POST /subjects/{sub}/scopes` is my minimal proposal for the §2.7 debt; exact path and one-endpoint-vs-per-scope unspecified.

**Testable claims:** (1) §3.4 and §5.3 are distinct surfaces — a conformant server that admits a device over the §3.3 host URL with the host's tunnel token and then stamps `deviceId` is non-conformant (that token has no device identity); harness plays a device against the host URL and asserts rejection. (2) `deviceId` is never device-supplied — a device sends a top-level `deviceId` key and an in-frame resume `deviceId` ≠ its token `sub`; a conformant server stamps the token `sub` and rejects/ignores the mismatch; harness-observable on the host-bound envelope. (3) base grant closes — two tenants, one tunnel in tenant A, one device in tenant B; the device's attach must deny, and a device granted tenant A must receive tenant A's frames in order; harness plays both devices. (4) revocation is immediate and host-agnostic — revoke a connected device mid-stream; assert no further frames reach it and its socket closes, with zero host-side action. (5) trust-summary honesty is checkable against §1–§4 — every "server can do" row must be derivable from a §1–§4 MUST/MAY plus the §5 statement; a row claiming the server *cannot* see something contradicts §4.2 and must be struck.
