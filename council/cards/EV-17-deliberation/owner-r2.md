## 2. Abort semantics — Principal's SDK reading verified; guard suffices, stronger condition adopted

Verified against the installed SDK:
- TUI: `showExtensionConfirm` (`interactive-mode.js:2073–2076`) awaits `showExtensionSelector`; the abort listener is `onAbort = () => { hideExtensionSelector(); resolve(undefined) }` (:2044–2047), and an already-aborted signal at call time resolves `undefined` immediately (:2034–2037). `result === "Yes"` ⇒ abort returns `false`.
- RPC: `confirm` is `createDialogPromise(opts, false, …)` (`rpc-mode.js:85`); `onAbort = () => { cleanup(); resolve(defaultValue) }` (:57–60); already-aborted ⇒ `Promise.resolve(defaultValue)` (:49). Abort returns `false`. Rejection is possible only via the host rejecting the pending request (`pendingExtensionRequests.get(id).reject`, :74), never via abort.

So an abort is an ordinary `false` in both modes — the Principal's factual claim stands. However, the spin conclusion does **not** follow for the r1 loop shape: the `while (!ctrl.signal.aborted)` condition is re-evaluated *after every await* (that is what a top-of-loop check is). Under abort→`false`, the pending confirm resolves `false`, control returns to the condition, `aborted === true`, loop exits. The infinite spin requires a `while (true)` whose only exit inspects the resolved value — not this shape. That said, the loop's termination now rests on the invariant "every settle path aborts the signal," which is exactly what the Principal's `finish()` guarantees — the two corrections are synergistic, and the condition is written explicitly as `while (!ctrl.signal.aborted && !settled)` to make it spin-proof even if a future settle path forgets to abort. On the Principal's open ruling: accept **re-arm on rejection** (rejection ≠ abort ≠ cancel; Escape-keeps-waiting semantics), with an explicit test, replacing the r1 `catch { return; }`.
