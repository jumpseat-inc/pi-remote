The success line prints while the dialog lingers; the user reads it as "did the dialog see my cancel? did the cancel fail?" ## Principle and evidence

- **Single guarded finisher (mapping + feedback).** Every settle path — server callback (:491-493), timer (:563-567), confirm-true, `cancel()` — must run *the same four steps in the same order*: set `settled`, resolve `cbPromise`, `controller.abort()`, `clearTimeout(timer)`. This collapses four "settle but forget the dialog" paths into one. Evidence: `src/login.ts:491-493` (server settle) and `:563-567` (timer settle) currently only do the first two; the existing `await cbPromise; clearTimeout(timer)` at `:568-569` covers `clearTimeout` only because `cbPromise` already resolved. Adding `ctrl.abort()` to the server and timer settle sites (the simplest place: inside the same `if (!settled)` guard that already protects them) makes the dialog dismissal a deterministic consequence of every terminal event. **Files:** `src/login.ts:491-493`, `:563-567`. **Smoke:** P-D and P-E, falsifiable by the smokes named in r1.
- **Abort-resolves-false (constraint).** Principal's finding is binding: `showExtensionConfirm` resolves `undefined` on abort (TUI) and `defaultValue` on abort (RPC), both of which yield `false` to the dep. The re-arm loop therefore **cannot** branch on the resolved value to decide "abort vs. dismiss" — it must check `ctrl.signal.aborted` *after* the await. Owner's `while (!ctrl.signal.aborted)` check at loop top satisfies this; combined with the post-await yes-check, abort → false → loop-top check fails → loop exits cleanly. **Smoke:** P-F (Escape re-presents; abort exits the loop), plus principal's "abort-spin" assertion (after a browser callback wins, the `waitForCancel` call count stops increasing — directly falsifies a `while(true)` loop).
- **Wake seam (forcing function for `cancel()`).** Owner's `ctl.wake = () => { ctrl.abort(); if (!settled) settle({type:"cancelled"}); }` plus facade `cancel = () => { ctl.cancelled = true; ctl.wake?.(); }` is the correct shape. It satisfies all four steps of the r1 cancel-responsibility — (a) flag, (b) settle, (d) abort — and (c) `clearTimeout` falls out automatically because settle unblocks the existing `await cbPromise; clearTimeout(timer)` at `:568-569`. **One subtle correctness point worth pinning in the implementation:** confirm-true must settle `{type:"cancelled"}` *without* setting `ctl.cancelled = true`, so the `:572` early-return doesn't fire and the dead `:575` branch becomes reachable — that is exactly what makes Acceptance 5 ("the dead branch becomes reachable") true. External `cancel()` does both (flag + settle), which makes the `:572` early-return fire on the external path and the `:575` branch on the confirm path — two honest causes, neither fabricating the other. **Evidence:** `src/login.ts:572-576`.
