# Designer — round 1 (job-21.3, step 2 independent first pass)

Grounding: card; `council/cards/EV-16-deliberation/` (consolidator-synthesis S8/S9, designer-r1/r2, round3, owner-r2, principal-r2, skeptic-r1); `src/login.ts` (:198–220 wait/cancel copy; :470–620 attended driver; :800–870 facade/cancel; wait-line print :541; dead `cmd.cancel()` site :866; success print :618+/finalizeSuccess; timeout :566); `src/pi-sdk-on.ts` (minimal vendored mirror, `ui.confirm` deliberately omitted); `src/copy.ts` (coverage boundary; cancel line English-under-every-locale by design); `index.ts` (:116, :683, :717–727); `vault/wiki/index.md` (nothing covers `ui.confirm` modal semantics directly).

## Design position

I confirm the shared-pass settlement: a `LoginDeps.waitForCancel?: (signal) => Promise<boolean>` injected as `requireCtx().ui.confirm("Waiting for browser…", "Cancel sign-in?", { signal })`, raced against the loopback callback, re-armed on `false` until the signal aborts. On top of the settled shape, I argue for a **named lifecycle** in the implementation — a four-step ordering (wait-line print → dialog mount → press paths → terminal settle) and an explicit `cancel()` responsibility (set `ctl.cancelled`, settle `cbPromise` with `{type:"cancelled"}`, `clearTimeout`, abort the signal — all four) — so the moment-by-moment experience is provable rather than emergent. The copy stays settled; what this pass adds is interaction ordering and the falsifiable predictions that nail each edge.

## Gulf closed

- **Gulf of Execution, during the 5-minute wait.** A user who pressed `/rc:login` and saw `Waiting for browser…` previously had *no in-session exit* — only `cmd.cancel()` from external code or a process kill. The dialog adds a one-keystroke exit from the surface the user is already staring at. (`src/login.ts:541` is the wait-line print; `src/login.ts:866` is the dead `cmd.cancel()` site.)
- **Gulf of Evaluation, at the moment of cancellation.** When the user presses confirm, they need to know *the cancel took effect* — not just that a dialog dismissed. The settled facade print of `login.cancelled` exactly once (`src/login.ts:201`, byte-exact, printed by the facade not by the driver) is what closes this gulf: the cancel line is the receipt.
- **Gulf of Evaluation, at the moment of natural completion.** When the browser completes first, the dialog must dismiss without a confusing flicker. The settled "signal aborts when the callback wins" wiring closes this: the dialog disappears *because* the wait is over, not by some independent mechanism.

## Principle and evidence

| Instrument | Where it lands | Evidence |
| --- | --- | --- |
| **Signifier — dialog over wait line** | The wait line `Waiting for browser…` (settled) is now the *title* of the dialog. The person sees the same string twice: once as a printed line, once as the dialog title. The dialog reads as a status overlay on the wait state, not as a new state. | Settled copy; O5 (skeptic) proved byte-exact at `src/login.ts:201` for the cancel line; the wait line is settled unchanged. |
| **Mapping — message ↔ primary button** | Dialog message `Cancel sign-in?` is the question; the primary button is the answer. If the host labels the primary button `Cancel sign-in` (or similar), mapping is clean; if it labels it `OK` / `Yes`, mapping weakens (see open item 2). | Settled copy; the host's button-label behavior is not in the record. |
| **Feedback — three terminal receipts** | Three terminal states, three distinct receipts: (1) confirm-cancel → `Sign-in cancelled — no credentials were saved.`; (2) browser-wins → success line; (3) timer-fire → `login.failure.redirectTimeout`. The dialog dismissal is *itself* feedback for cases (2) and (3). | Settled: facade prints cancel exactly once; success line; timeout line. |
| **Re-arming as persistent affordance, not new state** | On `false` (Escape / dismiss), the dialog dismisses then re-presents. The user pressing Escape *keeps the wait alive* — Escape means "not now, keep waiting." This is the inverse of `inputPrompt`'s Escape semantics (which means "cancel"). | Shared pass S8: "re-armed on `false` until the signal aborts." The semantic flip is a real edge (see P-F). |
| **Forcing — none** | The cancel is opt-in. A user who wants the 5-minute wait can press Escape repeatedly, or just ignore the dialog. No forcing function — and there should not be, because the user is *already* waiting voluntarily. | By construction (the dialog re-arms on `false`). |
| **Conceptual model — "wait with an off-switch"** | The dialog is not a new state. It is the same wait state with a new affordance grafted on. The user's mental model: "I'm waiting; I can stop." Not: "I'm in a new prompt." | Settled copy mirrors this (title = wait line); the cancel line uses the existing `login.cancelled` key. |

## Moment-by-moment experience

| Moment | What the user sees | What the system does |
| --- | --- | --- |
| **Arrival** | The J2 replacement prompt resolves (if applicable), then `Opening your browser to enroll this host with <serverUrl>…` (only if `openUrl` is wired; absent → skipped per S2), then `If the browser does not open, visit: <authorizeUrl>`, then `Waiting for browser…`. | `runAttendedLogin` binds the loopback listener, builds the PKCE verifier, prints the lines, kicks off the redirect-URI build. |
| **Dialog mount** | A modal dialog appears with title `Waiting for browser…` and message `Cancel sign-in?`. The dialog overlays the printed wait line — same string, now in a title bar. | Driver constructs `new AbortController()`, calls `deps.waitForCancel?.(signal)`; the host's `ui.confirm` mounts. |
| **Steady state** | The dialog sits open while the user works the browser. They can press the primary button (cancel) or dismiss (keep waiting). | The loopback listener awaits `GET /callback`; the redirect timer counts down; the dialog sits. |
| **Path A — primary button** | Dialog dismisses; `Sign-in cancelled — no credentials were saved.` prints once; the user is back at idle. | Driver: `ctl.cancelled = true`, settle `cbPromise` with `{type:"cancelled"}`, `clearTimeout(timer)`. The `await cbPromise` resolves; the `cb.type === "cancelled"` branch (currently dead — Skeptic O7(3) proved unreachable at base) becomes reachable. Facade prints `login.cancelled` once. |
| **Path B — Escape / dismiss** | Dialog dismisses, brief gap, dialog re-presents. No state change visible to the user. | The confirm promise resolves `false`. The driver (or its orchestrator) calls `waitForCancel(signal)` again — same signal, same title/message. |
| **Path C — browser completes first** | Dialog auto-dismisses (signal aborts); success line prints (with tenant parenthetical if J1 derives one). | Loopback listener receives `/callback` with matching `state` and `code`; `settle({type:"code", code})`. Driver `clearTimeout(timer)`, abort the signal (dialog dismisses), token exchange, `finalizeSuccess` (saves credential, prints success). |
| **Path D — redirect timeout** | Dialog auto-dismisses (signal aborts); `The browser did not complete the consent in time. No credentials were saved.` prints. | `setTimeout` fires; `settle({type:"timeout"})` if not yet settled; driver `clearTimeout` (defensive — same call site); abort the signal; `cb.type === "timeout"` branch prints `login.failure.redirectTimeout`. |
| **Path E — external `cmd.cancel()`** | Same as Path A: dialog dismisses, cancel line prints once. | Per shared pass S8: `cancel()` must (a) set `ctl.cancelled`, (b) settle `cbPromise` with `{type:"cancelled"}` if not yet settled, (c) `clearTimeout(timer)`, (d) abort the signal. **All four**, in any order that doesn't deadlock — but (b) and (c) must precede the driver's `clearTimeout`/`await cbPromise` resolution path so we don't double-settle. |

Falsifier: the dialog lags the wait line by ≥100ms — the user sees the wait line, then a perceptible blank, then the dialog. |

## Open items outside the settled block

1. **`cancel()` is a four-step responsibility; the record names "settle + clearTimeout" but not "abort the signal."** If `cancel()` does not abort the signal, the dialog will not dismiss on external cancel. I argue (d) is mandatory for the moment-by-moment contract above. This is a settled-block interpretation, not a re-opening, but flagged because the literal text is silent.
2. **Host-controlled primary button label.** The title and message are settled; the button label is not. Falsifiable via P-G. Not a correctness issue — the title+message is the binding — but a design concern.
3. **`ui.confirm`'s modal semantics on the real host.** `ui.confirm` is a different primitive from `inputPrompt`, and the shared pass accepted it on existence + signal semantics (O1) — not on modal vs. non-modal behavior. P-H is the smoke that would falsify the implicit assumption that `ui.confirm` is non-modal enough not to eat the input pipeline.
4. **Headless flow has no cancel affordance.** EV-17 is attended-only by the card's own scope. Out of scope here.
5. **`waitForCancel` is optional (`?:`).** If absent — e.g., the host is `mode: "rpc"` — the cancel affordance is gone; only `cmd.cancel()` from external code can interrupt. Acceptable by construction (no TUI user in RPC mode), but EV-17's user-facing affordance silently disappears in non-TUI hosts. The card does not promise otherwise.
6. **The wait-line copy is unchanged, and the dialog title is the same string.** Intentional — the dialog reads as a status overlay on the wait. But the user sees the same six-word string twice in a row; a reader could mistake this for a bug. Not a defect — worth a one-line comment in the implementation so a future reader doesn't try to "fix" the duplication.

## Preferences, ranked last

- **Button-label alignment** is the most consequential open item in the abstract, but it is host-controlled; P-G is the falsifier. **Taste / not in our hands.**
- **Slight preference for the dialog title to be distinguishable from the wait line** — **withdrawn; the duplication is the design.** If a future reader files a confusion bug, that's the moment to revisit, not now.
- **Slight preference for the dialog to be constructed in the facade (`createLoginCommand`), not in the driver** — `runAttendedLogin` is pure and ctx-free today. **Taste / implementation detail; the pure-seam test (P-I) pins the wire regardless of which layer holds the dep.**

**Position stated.** The settled affordance is sound; the interaction ordering above is what I'd add on top, and the ten falsifiable predictions are the smokes the Skeptic can run to verify the contract on the real host. The open items are gaps in the record, not re-litigations.
