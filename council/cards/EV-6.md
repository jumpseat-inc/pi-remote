## Intent

Implements §5.4 in `src/inject.ts`. Remote input must be indistinguishable
from typed input in the session log — the extension does not filter or
transform its own injections — which is what makes EV-5's replay correct by
construction. User-visible surface — on the host, an injected remote prompt
appears in the transcript like typed input; on the remote client, an approval
prompt raised by the session (CUSTOM `pi.human_input`) can be resolved from
the device, and that resolution carries the approving `deviceId` for audit.

## Acceptance

- A prompt sent while idle starts a run identical in effect to typing it
  locally; the `input` event shows `source: "extension"` and the JSONL record
  is indistinguishable from a typed message.
- A prompt sent mid-stream arrives as a steer; one sent during an active run
  with queue intent arrives as a followUp (verified against pi's actual
  delivery behavior).
- Resolving a pending approval via `pi.human_input` unblocks the waiting
  session and the resolution is tagged with the sending deviceId; when the
  mode does not support direct resolution, the reply is surfaced as a
  steering message instead of being dropped.

## OWNER position — `src/inject.ts` (EV-6)

### Approach

Ground first in what the installed SDK actually does, because the whole module is `[AgUiFrame, run-state] → pi-side call` and every branch maps to one SDK gate. `sendUserMessage` is `sendUserMessage(content, {expandPromptTemplates:false, streamingBehavior: deliverAs, source:"extension"})` → `prompt(text,{…, streamingBehavior:deliverAs, source:"extension"})` (agent-session.js:1161–1188). `prompt` consults `deliverAs` **only if `this.isStreaming`** (line 861): idle → runs a normal turn ignoring `deliverAs`; streaming → `_queueSteer`/`_queueFollowUp` (1046–1070: steer interrupts, followUp waits); streaming **with no `deliverAs` → throws** (861–863). So the run-state source of truth is **`isStreaming`** (getter = `_isAgentRunActive`, 616–618) read **at injection time**, not `isIdle` — it is the literal gate `sendUserMessage` branches on, so mirroring it guarantees we never diverge from the SDK's own decision and never hand it an undefined `streamingBehavior` while streaming (the throw case).

**Module surface** (matches the repo's `create*` DI style like `createTransport`/`createState`):

```ts
type ContentLike = { type: "text"; text: string } | { type: "image"; image: unknown };
export interface InjectDeps {
  sendUserMessage: (c: string | ContentLike[], o?: { deliverAs?: "steer" | "followUp" }) => Promise<void>;
  isStreaming: () => boolean;
  /** Matches a pending prompt pi-remote sponsors; false = mode can't resolve → steer fallback. */
  resolvePendingPrompt: (promptId: string, result: unknown, deviceId?: string) => Promise<boolean>;
}
export type InjectResult =
  | { kind: "injected"; deliverAs?: "steer" | "followUp" }
  | { kind: "resolved"; promptId: string; direct: true; deviceId?: string }
  | { kind: "steered_fallback"; promptId: string; text: string; direct: false; deviceId?: string };
export function createInjector(deps: InjectDeps): {
  handle(env: InboundEnvelope): Promise<InjectResult>;
}
```

`InboundEnvelope` already carries `deviceId?` end-to-end (transport.ts:61–65, handed to `onInbound` at ~line 330), which is what makes the audit tag possible.

**Idle / mid-stream / queue decision** — a pure two-branch fold, because it must be a pure function to unit-test against the SDK's *documented* behavior (the seam): `!isStreaming → {}` (no `deliverAs`); `isStreaming && intent==="followUp" → {deliverAs:"followUp"}`; `isStreaming && otherwise → {deliverAs:"steer"}`. The **never-throw** property (never call without `deliverAs` while streaming) is the load-bearing falsifiable claim. Intent comes from the inbound frame: bare AG-UI user frames (`TEXT_MESSAGE_START` role `user`, or a `CUSTOM` `pi.user_input` wrapper) carry normal input; a queue-intent must be explicitly carried in the frame (a wrapper with `intent`) or it cannot produce `followUp` — I flag this as the one wire-format point that must be pinned with the client before EV-6 is verifiable end-to-end.

**`pi.human_input` resolution end-to-end.** The host emits the prompt as `CUSTOM name:"pi.human_input"` with a **deterministic** `promptId = fnv1a(promptKind \0 prompt)` (translate.ts:474–486) — determinism is what lets a resolution match the same prompt across replay (EV-5). A resolution reaches pi by the inverse path: an inbound `CUSTOM`/user frame carrying `{promptId, result}` is matched against **pi-remote's own pending-prompt registry** (keyed by `promptId`, whose `resolve` it holds — the only prompt an extension can actually "resolve", because the SDK exposes **no** API to answer another component's `ui.confirm`; runner.js tracks `activeUIPrompt` privately and only emits `ui_prompt_start/end` events}. Direct resolution = the promptId matches a sponsor-owned pending prompt **and** the mode can await it → `resolvePendingPrompt` returns true, result delivered, `deviceId` recorded. **"Mode does not support direct resolution"** means one of two concrete states: (a) the prompt was raised by pi/another extension (pi-remote observed it via `ui_prompt_start` and broadcast it, but doesn't hold the resolver), or (b) headless mode where there's no local confirm to await. In both, `resolvePendingPrompt` returns false and the reply becomes a steering message — `sendUserMessage(replyText, {deliverAs: isStreaming ? "steer" : undefined})` — never dropped. This satisfies acceptance verbatim.

**Replay-correct-by-construction constraint**: inject.ts must **not** register an `input` handler and **not** return `{action:"handled"/"transform"}` — pi-remote passes every injection through untouched, so the JSONL record is byte-indistinguishable from a typed message (EV-5 replay is trivially correct). Design asserts this as a negative invariant.

### Tradeoffs accepted

- **`isStreaming` (not `isIdle`) as source of truth**: identical today (`isIdle = !_isAgentRunActive`), but it couples our decision exactly to the SDK's own branch, so a future SDK redefinition of "idle" (compaction, queued continuation) can't silently split our routing from the SDK's. Cost: reads a slightly less "user-meaningful" flag.
- **Pure decision + injected SDK seams** rather than wiring real `pi.sendUserMessage`/`ctx.ui.confirm` into inject.ts: we can't run real pi in `bun test`, so correctness is pinned at the boundary by unit tests + documented fixtures. That's the honest seam — real steer/followUp behavior is trusted to the SDK and grounded by source here, not re-verified in tests.
- **Only sponsor-owned prompts resolve directly**: we give up trying to answer arbitrary session prompts remotely (SDK physically can't), routing them to steer instead. Matches acceptance's "surfaced as steering message instead of dropped." The cost is a real product limitation that should be surfaced to the owner: remote-only approval of *other* extensions' confirms is not achievable without an upstream pi feature.

**principal** (job-21.2, verbatim).

**Cross-seam reading**

1. **Transport hands inject a frame typed as the *outbound* union, not a validated inbound contract.** `transport.ts`'s `parseInbound` accepts any object whose `frame.type` is a string in `AG_UI_TYPES`, then casts it to `AgUiFrame` and passes it to `onInbound` with `deviceId` on the envelope. It validates nothing about `TEXT_MESSAGE_START.messageId/role` or `CUSTOM.name/value`. So `inject.ts` inherits a trust boundary: it must runtime-validate every inbound frame itself, and it may *not* assume the `AgUiFrame` type describes what actually arrived.
2. **The inbound user-message shape is AG-UI `TEXT_MESSAGE_START`(role "user") → `TEXT_MESSAGE_CONTENT` → `TEXT_MESSAGE_END`. There is no wire field for steer vs followUp.** AG-UI's `TextMessageStartEventSchema` is `{type, messageId, role, name?}`; no event type carries a delivery-mode field. `pi`'s `deliverAs` concept exists only on the SDK side. PI-SPEC §5.4 has a "Client intent" column, but neither `InboundEnvelope` (settled 4-key `{v,seq,ack,frame}`) nor any frame in `AgUiFrame` carries that intent. **The queue-intent case has no wire representation anywhere in the repo today.** Each side of this seam assumes the other side owns that field; neither does.
3. **`pi.sendUserMessage` is the correct and sufficient injection path, but it is fire-and-forget and swallows its own failures.** Grounded: `agent-session.js:1161-1196` → `prompt(text, { expandPromptTemplates: false, streamingBehavior: options?.deliverAs, images, source: "extension" })`; `prompt` emits the `input` event with `source` and `streamingBehavior` (the latter only when `this.isStreaming`), then throws if streaming with no `streamingBehavior`, else `_queueSteer`/`_queueFollowUp`. `types.d.ts` declares `sendUserMessage(...): void`, and the runtime binding catches and routes delivery errors to the extension error bus. **Consequence: `inject.ts` cannot "catch the throw"** — it can only avoid triggering it by always passing a valid `deliverAs` when the run is not idle.
4. **The approval half of the seam is keyed to events the SDK does not emit.** `translate.ts`'s `PiEvent` union contains `{event:"ui.confirm"; promptKind; prompt}` and `{event:"user_input"; ...}`. The real `ExtensionEvent` union has neither; it has `ui_prompt_start`/`ui_prompt_end` with `{kind: UIPromptKind; title?}` and `message_start`(role user). So the emitted `pi.human_input` frame (with `promptId = fnv1a(promptKind + "\0" + prompt)`) is never produced by the live path as written, and the `user_input` echo mapping is dead code. There is also **no public API to programmatically resolve a pending prompt**: `grep` across `dist` finds no `resolvePrompt`/`resolveUIPrompt`/`approvePrompt`; `ExtensionRunner.activeUIPrompt` is private and `withUIPrompt` only *wraps* `ui.*` creators. The only public way to get text into the session is `sendUserMessage`/`sendMessage`. "Resolved via the matching pending UI prompt when the mode supports it" is therefore **not implementable against the installed SDK surface**; only the steering-message fallback is real.

**Reframe**

EV-6 is not "call `sendUserMessage` with the right option" — that part is a thin adapter. The seam itself is the risk, and it is currently unframed in two places. Reframe the card around two explicit inbound wire contracts that must be pinned before the acceptance is testable:

1. **Intent rides the user-message frame, namespaced.** Use the already-valid `name` field on inbound `TEXT_MESSAGE_START` as the sole delivery-intent channel: `name: "steer" | "followUp"` (absent = idle-decided). No 5th envelope key, no new frame family, no CUSTOM-correlation for the common path. The extension does not add intent; the client does, and the client can express it because `name` is part of the AG-UI schema.
2. **Approval responses are a dedicated CUSTOM frame keyed by the emitted `promptId`**, e.g. `{type:"CUSTOM", name:"pi.human_input.response", value:{pi:"ui.confirm.response", data:{promptId, response}}}`. Matching is a map lookup on `promptId`, not "the only pending prompt."

And reframe the approval path honestly: **make the steering fallback the only live code path, and model direct resolution as an injected `resolvePrompt` seam that the current SDK cannot wire.** `inject.ts` should be built around `sendUserMessage(text, {deliverAs:"steer"})` when a resolution can't be applied directly; `resolvePrompt?` exists so the acceptance's "unblocks the waiting session" clause has a home, but we flag it as a fixture seam, not a real pi surface. The mode signal is the *presence of the seam* (`resolvePrompt` absent/throws → fallback), not a read of `ctx.mode`.

Run-state source: `inject.ts` takes `isIdle: () => boolean` injected by EV-8. EV-8 should capture the SDK's own `ctx.isIdle()` from a `session_start` handler. EV-8's `sendUserMessage` wiring must call `pi.sendUserMessage` synchronously (no intervening `await`) so the `isIdle` read and `prompt()`'s internal `isStreaming` check happen in the same microtask.

Testable claims: (P1) inject START(role user,"m1")/CONTENT/CONTENT/END with isIdle true → exactly one `sendUserMessage("Hello")`, no options, no call before END. (P2) same frames isIdle false → `sendUserMessage("Hello",{deliverAs:"steer"})`. (P3) START(role user, "m2", name:"followUp")/CONTENT/END isIdle false → `sendUserMessage(text,{deliverAs:"followUp"})`; with isIdle true the name is ignored → `sendUserMessage(text)`. (P4) decision timing: fake isIdle false-first-then-true must produce `deliverAs:"steer"` for a message finalized on first call — mode read at END/injection time, not cached at START. (P6) approval fallback (live path): register pending {promptId:"p1"}; inbound CUSTOM pi.human_input.response {promptId:"p1",response:"yes"} isIdle false, **no resolvePrompt** → exactly one `sendUserMessage("yes",{deliverAs:"steer"})`, exactly one `recordApproval({promptId:"p1",deviceId:"dev1",response:"yes",at})`, p1 removed. **designer** (job-21.3, verbatim — position file `vault/raw/2026-08-31-design-ev6-remote-input-injection.md`, read in full).

The user-visible work is two experiences: on the **host** an injected remote prompt lands in the JSONL exactly like a typed one (replay-correctness invariant); on the **remote client** a `pi.human_input` frame received while the session waits on a host UI prompt can be answered, carrying the `deviceId` of the answering device. Smallest viable shape: a thin I/O-free `inject.ts` exposing one seam per responsibility — `injectUserMessage({content, deliverAs})` → `pi.sendUserMessage(content,{deliverAs})`; `resolveHumanInput({promptId, text, deviceId})` → resolves the pending host prompt directly when the host UI is wrapped and lets us, else falls back to `sendUserMessage(text,{deliverAs:"steer"})` so it is **never dropped**. The fallback is the product choice; dropping is the design failure. Replay-correctness = no transformation: EV-6 must **not** register an `input` extension handler (static-grep gate), and must not return `action:"handled"/"transform"`. `deliverAs` is what pi actually does (verified agent-session.js). `promptId` is the only durable correlation (deterministic in translate.ts) — key on `promptId`, never prompt text. deviceId is opaque and already on `InboundEnvelope.deviceId` — read it from the envelope, propagate as a structured field, never smuggled into `text`. Resolving the host UI prompt is conditional: `runner.js:88 noOpUIContext` is the default; `:269 setUIContext` wraps host UI confirms; the host mode (interactive vs print vs RPC) determines whether a pending confirm promise can be reached. The resolver must detect "no pending prompt I can resolve" and fall back to steer — the fallback is the spec-mandated answer (§5.4 row 4); dropping is a regression. Interaction questions raised (not ruled): (i) how the remote knows a prompt is pending and when the host finished waiting — proposes host emits CUSTOM `pi.human_input.resolved {promptId,deviceId,ts}` from a new `ui_prompt_end` PiEvent (forward dependency on EV-4/EV-8; must not block EV-6); (ii) multiple devices racing to answer — first deviceId wins, others see `pi.human_input.resolved` with `winnerDeviceId`, stale answers surfaced as notice not delivered (a slip); (iii) steer landing while already steering → queued, remote renders `queue_update` feedback (SDK-owned); (iv) reply when direct resolution unsupported → router to `{deliverAs:"steer"}` and remote sees `CUSTOM pi.human_input.fallback_to_steer`. Falsifiable predictions H1–H7: H1 transcript indistinguishability (call args `{content:"x",options:{source:"extension"}}`, no input handler registered); H2 mode derivation (steer vs followUp routed to right SDK queue); H3 human-input resolution carries deviceId structurally not in text; H4 fallback is not a drop (unknown promptId → exactly one steer); H5 remote sees resolution feedback via CUSTOM pi.human_input.resolved (depends on new ui_prompt_end PiEvent — forward dep); H6 stale answers surfaced not delivered; H7 purity (no WebSocket/setTimeout/randomUUID). Preferences: deviceId as structured field not smuggled into text; one function per inbound responsibility; remote renders approval as a modal (one decision at a time); host-side "who answered?" surfaces in JSONL as a `custom_message` entry of kind `human_input_resolution` carrying {promptId,deviceId,ts}. Notes for implementing seat: no input handler (H1 grep); promptId is the only durable correlation; resolution only possible when host UI registered with a context exposing the resolution promise — RPC/print mode → informational frame + steer fallback; forward dependency H5 must not block EV-6 (fallback is the floor, H5 the ideal).
