## Intent

The extension should work out of the box against Jumpseat's relay; today a fresh host must be
handed a URL. The default is the last-resort tier — below any stored credential — so a host
already enrolled against a self-hosted relay is not silently re-pointed. The URL prompt is
kept (pre-filled with the resolved value) as the interactive override affordance, and the
resolved relay stays visible at enrollment and in the `<serverUrl>`-rendering surfaces. The
constant needs one home and one resolver rather than three `??` chains (`index.ts:263`,
`index.ts:545`, load-time `index.ts:856`, `rcLoginCommand`).

## Acceptance

1. On a fresh host (no env override, no `piRemote.serverUrl`, no stored credential),
   `/rc:login` presents the URL prompt pre-filled with `https://relay.jumpseat.sh`; accepting
   the prefill (empty submission) enrolls, and the persisted credential's `serverUrl` is
   exactly `https://relay.jumpseat.sh`.
2. Precedence is pinned by test: env → setting → stored credential →
   `https://relay.jumpseat.sh`. A stored credential carrying
   `serverUrl: "https://custom.example"` still dials `https://custom.example/tunnels`, never
   the default; the prompt prefill reflects the resolved tier in each case.
3. The three runtime resolve sites (`rearm` `index.ts:263`, `rcCommand` `index.ts:545`,
   `rcLoginCommand`) consult one shared resolution function so they cannot diverge; the
   load-time value at `index.ts:856` remains the explicit-override-only tier, not the default.
4. With the total resolver, `login.failure.noServerUrl` is unreachable: its emission site and
   copy rows are removed in this PR and the removal is named in the PR description.
5. The `<serverUrl>`-rendering surfaces (footer/error copy) render the literal
   `https://relay.jumpseat.sh` when the default is in force, pinned by test.
6. `AGENTS.md`'s configuration-contract table and `docs/PI-SPEC.md` §7.2 and §8's `/rc` row are
   synced in the same PR.
