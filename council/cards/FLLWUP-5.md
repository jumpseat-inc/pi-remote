## Intent

Filed from EV-6's step 13. EV-6 shipped the steering-fallback resolution path
(per product-owner R2 and steward R3 rulings — the fallback is the permanent
product behavior) but deferred the host-side completion signal as a
forward-dependency: the remote user currently gets no explicit confirmation
that their resolution was applied, only indirect evidence from session output.
Root cause: the SDK emits `ui_prompt_start`/`ui_prompt_end` but translate.ts's
PiEvent union only carries `ui.confirm`, so `ui_prompt_end` never reaches the
AG-UI stream. User-visible surface — the remote client's approval UI, which
after this card can flip the prompt to "resolved" state on real feedback
instead of guessing.

## Acceptance

- translate.ts's PiEvent union carries `ui_prompt_end` and maps it through the
  established CUSTOM conventions; the pure fold shape and purity guards stay
  green.
- The lifecycle wiring (or its owner at run time) emits CUSTOM
  `pi.human_input.resolved` with `{promptId, deviceId, ts}` when a resolution
  (direct or steering-fallback) is applied to a prompt EV-6 tracked.
- The deviceId in the frame is the resolving device from the envelope, never
  into free text (EV-6's invariant).
- Fixtures cover the direct-resolution and steering-fallback paths; bunx tsc
  --noEmit exit 0; bun test exit 0 with the full suite green.
- Any §4-adjacent spec sentence this needs rides the PR as a
  facilitator-authored evidence-cited amendment per the standing precedent.

### Step 2 — independent first pass (round 1; owner job-34.1, principal job-34.2, designer job-34.3 — dispatched in parallel, each with only the card + binding contract)

(2) Lifecycle completion in index.ts: change onInbound to capture InjectResult; on `resolved` or `steered_fallback`-with-`tracked:true` emit `CUSTOM name:"pi.human_input.resolved" data:{promptId, deviceId, ts}` — deviceId from result (recorded from envelope, never free text), ts from injected `deps.now`. Requires adding `tracked: boolean` to the steered_fallback InjectResult so index.ts can tell tracked from untracked. Resolved fires ONLY for EV-6-tracked prompts (resolved ∪ tracked steered_fallback); NEVER for untracked steered_fallback (a prompt this host never raised — a phantom ack) or stale (already surfaced via pi.human_input.stale). Two frames neither feed each other; split is forced by purity (fold cannot mint ts/deviceId/promptId). §4-adjacent amendments: §4 row note pinning ui_prompt_end→pi.human_input value.pi:"ui_prompt_end" data:{kind,title?} as passive mirror; §5.4 paragraph pinning the resolved frame (fires only for tracked; deviceId from envelope never into text; ts host clock). **principal (job-34.2, verbatim).** The frame the card asks for is a lifecycle emission, not a pure mapping — ui_prompt_end is a *different* frame entirely. Forced by three purity facts: (1) promptId lives in the inject.js (promptId→occurrence) registry closure invisible to the fold, and ui_prompt_end carries no promptId (types.d.ts {type,reason:"ui_prompt",kind,title?}); (2) deviceId only on inbound envelope transport.ts, never seen by the fold; (3) ts is a clock read banned by purity. So pi.human_input.resolved {promptId,deviceId,ts} cannot be produced by translate.ts. translate.ts owns the informational ui_prompt_end mapping → `CUSTOM name:"pi.human_input.closed"` value:{pi:"ui_prompt_end", data:{kind,title,schemaVersion:1}}; index.ts owns the resolution emission. The ui_prompt_end→registry correlation is *impossible* (schema gap: kind≠promptKind, title≠prompt; plus purity), so ui_prompt_end/closed is an independent "host stopped waiting" surface — correct, because ui_prompt_end fires for reasons unrelated to a remote answer (host operated own TUI, dismissed, timeout) that must not forge a resolved. Trust boundary: index.ts:341 `void injector.handle(env)` throws away the InjectResult — the seam. New wiring awaits and dispatches by kind: resolved→emit; steered_fallback tracked→emit; steered_fallback untracked→no resolved (R2 fallback_to_steer already fired); stale→no resolved (pi.human_input.stale already emitted); ignored/injected→nothing. Seam gap: steered_fallback carries reason:"mode" for BOTH unknown-promptId and tracked-but-not-directly-resolvable — index.ts can't distinguish without a `tracked:boolean` flag on steered_fallback (false at unknown-entry fallback, true at live-entry fallback). Q5: separate, never merged — resolved sourced from InjectResult, not ui_prompt_end (in the steer-fallback path the host UI promise may never settle, so ui_prompt_end/closed may not fire at all — strongest argument resolved must come from InjectResult). Q6: the resolved frame belongs at §5.4/§7.3, plus a one-line §4 note that ui_prompt_end maps to informational pi.human_input.closed. **designer (job-34.3, verbatim).** The remote approval UI should treat `pi.human_input.resolved {promptId, deviceId, ts, kind:"won"|"stale"|"fallback"}` as a single, terminal frame that closes the prompt row on real evidence, keying identity on (promptId, occurrence). Exactly-once per (promptId, occurrence), emitted only from the lifecycle layer. Folded into the same name namespace as the existing two surfaces (pi.human_input.stale, pi.human_input.fallback_to_steer); kind is the single thing the client keys state-transition on. No ui_prompt_end PiEvent needed in translate.ts for the resolution — the resolution is an EV-6 outcome, not an SDK event; ui_prompt_end carries no promptId to bind to. For untracked prompts the resolved frame does not fire (phantom confirmation). The fallback-to-steer path emits BOTH the loud-once fallback_to_steer (explanatory sentence) and `pi.human_input.resolved {kind:"fallback", deviceId, ts}` (state-machine input) — different things for different clients. Gulf closed: remote user now perceives whether their own device won, another device won first (which one), or the host converted the tap to steer. Principle/evidence: knowledge-in-the-world; signifier+conceptual model — four-state lifecycle (raised→won/stale/fallback/unanswered); feedback immediate; purity constraint (fold can't mint deviceId/ts — lifecycle layer only); forcing function (the honest answer to a second tap is don't tap again). Falsifiable predictions H1..H7: H1 exactly one resolved frame per (promptId,occurrence) with winning envelope deviceId regardless of direct/fallback; H2 stale is a separate terminal (client sees both resolved{kind:"won"} and stale{winnerDeviceId} in order, distinct frames); H3 fallback carries resolving deviceId + stable identifier, after fallback_to_steer, kind:"fallback"; H4 no resolved for untracked promptId; H5 resolved keyed by (promptId,occurrence) not just promptId (two occurrences each get own terminal); H6 exactly-once even under retry (keyed on entry.settled, second arrival → stale not second resolved); H7 the resolved frame is the only frame that closes the row; client listens only to lifecycle pi.human_input.resolved — no pure-fold output needed for the flip (if a future SDK stopped emitting ui_prompt_end the UI would still close correctly). §4-adjacent amendment: add one paragraph after the stale sentence in §5.4 (line 192): **Resolution confirmation (FLLWUP-5)** — when a pi.human_input prompt is resolved by a remote device, the extension emits a single CUSTOM pi.human_input.resolved {promptId, occurrence, kind:"won"|"fallback", deviceId, ts}; deviceId the envelope's resolving device; kind:"won" direct (fixture-only), kind:"fallback" permanent steering-fallback (R3 Side A); stale answers receive pi.human_input.stale {promptId, winnerDeviceId} and no resolved; untracked promptIds receive no resolved. No §4 row edits. Preferences: kind discriminator on the resolved frame (one namespace, one dispatcher, three terminal frames; mirror the injector's two-valued result); ts = lifecycle-layer clock (the injected `now`). **Residuals to route:** (1) should resolved carry kind:"won" ever in production — per R3 Side B resolvePendingPrompt returns false in production so the live path is always kind:"fallback"; "won" only honest in fixtures; keeping it costs one discriminator per client switch, forward-compatible — product ruling, argues keep but not authoritative; (2) should pi.human_input.resolved be REPLAYED — replay (JSONL→translate) doesn't carry these events (they originate in the lifecycle layer and have no JSONL entry); on resync a reconnecting client re-sees the raise but not the resolved frame, so a reconnecting client sees the prompt as "open" in replay even though resolved. Acceptable iff client treats replayed history as a snapshot then continues on live frames; a design defect iff client expects replay self-sufficient. No test in this card covers it (replayActiveBranch doesn't run the lifecycle emit path). Route to product-owner. (3) should client see kind:"fallback" REPLACE the fallback_to_steer notice — argues no (notice=sentence user reads; resolved=state the row transitions to), settle at client level, one-line spec confirmation the notice is not deprecated.
