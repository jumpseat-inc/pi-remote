## Intent

The data plane, on the page in full: the WS upgrade with the one-time token;
the envelope is exactly `{v, seq, ack, frame}` — four keys, no extension point;
`seq` is monotonic and **client-owned** (the server never reorders, renumbers,
or stamps); `ack` echoes the highest processed inbound seq; the server relays
and never interprets frames. The two server-to-client control frames are
specified exactly: `{type:"resume", deviceId, lastAckedSeq}` (client requests
catch-up) and `{type:"resync", fromSeq}` (server cannot serve from cache and
asks the client to replay) — plus the rule that these are the only control
frames on the wire, so a server needing more must version the protocol, not
improvise. Fan-out: 1:N to granted devices, identical ordered stream, per-device
bookkeeping only. Ring-buffer caching is best-effort and disposable (the client
replays from its own store when the cache misses) — stated as a MUST-not-rely
for the server and a SHOULD for capacity. Non-normative guidance: ring sizing,
connection state machine, backpressure, deployment topology.

**Self-containment requirement:** the control-frame shapes are restated
completely on the page; the council-side check confirms byte-level agreement
with the client's `parseInbound` union, but the page cites no client code.

# Design position — EV-12, §4 "Data-plane relay"

## 1. The card has one real defect: "four keys, no extension point" is falsified by the shipped parser

The card's verbatim claim is that the envelope is *exactly* `{v, seq, ack, frame}`. But `parseInbound` reads an optional fifth key:

- `src/transport.ts` `parseInbound`: `const deviceId = typeof o.deviceId === "string" ? o.deviceId : undefined;` — every member of the `InboundFrame` union carries `deviceId?: string`.
- PI-SPEC §7.3: "The extension's only device-awareness is the frame envelope: inbound frames (input, acks, resumes) carry the sending `deviceId`." §5.4 and FLLWUP-5 take the resolving `deviceId` "from the envelope (never free text)".
- Runnable probe (against today's code): `parseInbound('{"v":1,"seq":1,"ack":0,"deviceId":"d1","frame":{"type":"TEXT_MESSAGE_START","id":"x"}}')` returns the envelope with `deviceId:"d1"`. A spec page that says "the envelope has exactly four keys, always" makes the shipped reference parser disagree with the page — which fails the acceptance criterion "match the shipped client's parser exactly."

So §4 must state the envelope rule **per direction**, which is both parser-true and security-correct:

- **Host→server envelopes**: exactly `{v, seq, ack, frame}`. Four keys.
- **Server→host envelopes**: `{v, seq, ack, frame}` plus one server-controlled optional key `deviceId` identifying which granted device produced the frame.
- **No other key, in any direction, ever.** The key set is closed; the extension point for evolution is `v` (§4.5 below), not extra keys.

Who writes `deviceId` is a security question: INV-4 makes the server the enforcement point, so the trustworthy rule is that the **server stamps `deviceId` on host-bound envelopes from the authenticated device connection and MUST NOT trust a device-supplied value** (an audit identity forged by a peer device would poison `pi.human_input` resolution attribution). Stamping an envelope-level field is a relay rule, not payload interpretation, so it does not breach INV-1. This needs a ruling because it contradicts the card's blanket "no extension point" phrasing — see judgment calls.

## 2. The card's "seq is client-owned; the server never stamps" cannot hold on the uplink

The card states the seq rule as if there were one stream. There are two, and they have different owners:

- **Downlink (host→devices)**: the host is the single producer; seq is host-owned, monotonic, never reset within the session instance; the server never renumbers. This is the rule the card means, and §4 must state it exactly so.
- **Uplink (devices→host)**: N devices produce. The host's parser requires a numeric `seq` on every inbound envelope, and the host's single `ack` watermark (`inboundSeq = Math.max(inboundSeq, inbound.seq)` in `transport.ts`) can only acknowledge **one** stream. Per-device counters make that watermark incoherent (device A at seq 100 "acks" device B's seq 3 meaninglessly). Therefore the only design where the shipped host's ack semantics work is: **the server is the single producer of the host-bound stream and owns its seq** — it rebuilds envelopes from device input into one ordered server-owned sequence. That is "stamping" in the card's vocabulary, so the card's blanket rule is wrong as written; it must be scoped to the host's downlink stream.

Falsifiably: if §4 pins "seq is client-owned and the server never stamps" unconditionally, then a conformant server cannot assign seq to device-originated frames, and the host's ack field is unimplementable for N≥2. I recommend §4 state: *the producer of a stream owns that stream's seq; the relay never renumbers a stream's own order; on the host-bound stream the server is the producer.* Ruling required (judgment call #2).

## 3. Proposed §4 structure

Section number 4, title "Data-plane relay" (already fixed by §1.6's document map), appended after §3.6:

- **4.1 Scope and the two streams** — one long-lived host-initiated WS per tunnel (the single data-plane socket of §1.2/§3.1); two logical streams over the relay: the host's downlink stream and the server-multiplexed host-bound stream. The population of *granted connected devices* is defined by the registry section (§5); §4 specifies only how relay behavior interacts with grants. Restates INV-1/INV-2/INV-3 as the section's governing constraints and the §1.2 negative invariant as the section's ceiling: the server reads the envelope, and nothing else.
- **4.2 The envelope** — `{v, seq, ack, frame}`; `v` is the literal `1` today; the four-key base set is closed; the one permitted adjunct is server-stamped `deviceId` on host-bound envelopes (per §1's resolution). Envelope opacity: the server MUST NOT inspect `frame` beyond discriminating the closed set of §4.4. Explicitly: a server that adds any other envelope key is non-conformant.
- **4.3 Sequence and acknowledgement** — seq is a positive integer starting at 1 per stream; ack is the sender's watermark = highest inbound seq it has processed, `0` before any; every envelope carries the sender's current ack (piggybacked, no dedicated ack message required — this matches the shipped host, which has no standalone ack send and only advances its ack by emitting frames); a sender with nothing to transmit MAY send a `{v, seq, ack, frame:null}` envelope to advance its watermark (the ack-only member the parser accepts). **Ack monotonicity**: on any single stream the ack MUST never decrease — the shipped host treats a decreasing ack as a protocol violation and closes the socket (close code 3400); the server MUST enforce the same on its side. **Seq-space continuity across tunnels**: the host's seq is bound to the session instance, not the tunnel — reconnect mints a *new* tunnel (§3.1 spent-tunnel rule) while seq continues unreset. Normative pin the card misses: *the server MUST NOT assume a tunnel's first frame carries seq 1, and MUST NOT reset or renumber seq at tunnel boundaries.*
- **4.4 The frame slot's closed set and the versioning escape hatch** — the `frame` value is exactly one of: (a) an application frame (opaque to the server), (b) `null` (ack-only), (c) `{type:"resume", deviceId, lastAckedSeq}`, (d) `{type:"resync", fromSeq}`. Nothing else — this is the closed-set restatement of the parser union. **The only-these-control-frames rule, normative**: within envelope version `1`, `resume` and `resync` are the only control frames a server may emit or relay, and the frame slot admits no further types. **Versioning escape hatch, named**: a server needing a new control frame or a changed envelope MUST version the protocol — increment `v` and define the new grammar — never improvise inside `v:1`; a conformant server receiving `v` it does not implement closes the connection as a protocol violation.
- **4.5 The resume/resync handshake** — exact shapes restated byte-level against the parser: `{"type":"resume","deviceId":<string>,"lastAckedSeq":<finite number>}` and `{"type":"resync","fromSeq":<finite number>}`, both riding inside the standard envelope's `frame` slot. Rules:
  - A **device** sends `resume` to request catch-up from its own last processed seq (`lastAckedSeq`).
  - The server answers a `resume` from its ring buffer by delivering the missed range of the host's stream, in host-seq order. **The server MUST NOT forward a `resume` frame to the host.** (Evidence: the shipped host, on receiving `resume`, updates its watermark and does nothing else; a forwarded resume would strand the requesting device forever.)
  - On a cache miss the server sends `{type:"resync", fromSeq}` to the **host**, with `fromSeq` = the requesting device's `lastAckedSeq` (the lowest seq the requester is missing). The host replays from its own store as ordinary application frames (INV-2); the server relays them like any others. Boundary semantics: replay is idempotent by application-level event ids — the server's cache is an optimization; the producer's own store is the source of truth; consumers dedupe by event id — hence replay need not correspond seq-for-seq. §4 must state **at-least-once delivery**: a resume/resync path may redeliver; exactly-once is never guaranteed at the relay.
  - Revocation interaction (R6): if the requesting device is revoked while its resume is outstanding, the server cancels *its* catch-up; a resync already sent to the host is not recalled — the host's replay fans out to the remaining granted devices, so it is never wasted work. Per-device bookkeeping for a revoked device is discarded; the stream and other devices are unaffected.
- **4.6 Fan-out (1:N)** — the server delivers each host-produced frame to **every granted connected device**, in host-seq order, identically: same frames, same order, no per-device filtering of the stream. Grant enforcement happens at delivery (INV-4): a device whose grant does not cover the tunnel receives nothing, and revocation (a control-plane act, §5's surface) takes effect at the next delivery opportunity without host cooperation — the server SHOULD close a revoked device's socket promptly and MUST stop delivering to it immediately. Per-device bookkeeping (last delivered seq, in-flight catch-up) is bookkeeping only, never protocol logic (single producer ⇒ one total order ⇒ fan-out is trivially consistent). Uplink concurrency: input from any granted device is accepted; concurrent uplink frames interleave in the server's host-bound stream order; arbitration between devices is out of scope for the data plane.
- **4.7 The ring buffer** — best-effort, disposable. **MUST-not-rely (normative)**: correctness MUST NOT depend on the cache — a server with an empty or short cache MUST still deliver every live frame and MUST resolve every miss via `resync`, never via data loss, a stall, or a fabricated frame; the server MUST NOT treat the cache as authoritative history (INV-2). **SHOULD (capacity)**: a server SHOULD cache a bounded recent window per live tunnel to serve fast catch-up without a host round-trip. Release: per §3.5(c) the cache is discarded at tunnel deletion; because the host's seq continues across tunnels, the server MUST respond to a post-reconnect resume (referencing a seq the new tunnel's cache has never seen) with `resync`, not with an error.
- **4.8 Liveness, close codes, and failure handling** — §3.4 says "Post-upgrade socket close codes are the data plane's business (§4)" and §3.5(b) defers the deletion close code to §4. Specify: liveness via native WS ping/pong (no application-level keepalive requirement); the host heartbeats with WS pings on a short interval (10 s in the reference implementation — non-normative example); the server MUST answer pings per the WS protocol and MAY send its own pings to reap dead sockets. Close codes are **diagnostic, not a contract**: the dialing side's remedy for any close is uniform (re-arm → new tunnel → reconnect), so §4 SHOULD recommend `1000` (deliberate close, including deletion per §3.5(b)) and `3400` (protocol violation) and MUST NOT require the client to parse codes. Protocol violations (malformed envelope, unknown `v`, a frame slot value outside §4.4's set, ack inversion) → close and let the peer's uniform remedy run.
- **4.9 Guidance (non-normative)** — one recommended shape per concern, per R3, clearly marked:
  1. **Ring sizing**: fixed-capacity count-based ring per live tunnel (e.g., last 512 envelopes), oldest evicted; no unbounded growth, no time-based retention to reason about.
  2. **Connection state machine**: host socket `dialing → live → closing → closed`; per-device delivery `attached → catching-up (resume in flight) → streaming → detached`; one line each on what transitions on close, revocation, and cache miss.
  3. **Backpressure**: bounded per-device send queue; on overflow, disconnect that device rather than buffering unboundedly or blocking the host's stream — safe because the device's remedy (reconnect → resume → resync) is total and the host's store is the source of truth. The single-stream invariant means no per-device flow control may ever stall the stream.
  4. **Deployment topology**: the single-live-socket-per-tunnel rule (§3.1) pins each tunnel to one server process, so the ring cache can be in-process memory with no cross-replica coherence; token signing keys can be shared/asymmetric per §3.3's guidance to let any replica verify a dial.

## 4. What the card misses (additions)

1. **Close codes** — mandated by §3.4/§3.5 forward references; the card never mentions them (§4.8 above).
2. **Seq continuity across tunnels** — the spent-tunnel rule of §3.1 plus the host's never-reset seq means a fresh tunnel inherits a non-1 seq space; without this pin an implementer will "helpfully" reset and break resume accounting (§4.3).
3. **Ack piggyback + ack-only envelopes** — the card specifies `ack` but not *when* it advances; the shipped host has no dedicated ack message, so §4 must state the piggyback rule and the `frame:null` envelope or the ack contract is unimplementable for a quiet sender (§4.3).
4. **At-least-once + event-id dedupe** — resume from a ring buffer that races live delivery can duplicate; the relay must name its delivery semantics so consumers know they own dedupe (§4.5).
5. **Resume is never forwarded to the host** — the handshake only works if the server answers resumes itself (§4.5).
6. **Ack monotonicity as a named protocol violation** — the shipped host closes on ack inversion (3400); the server-side obligation should mirror it (§4.3).

## 5. Judgment calls I cannot settle without a ruling

1. **The `deviceId` fifth key.** The card's "exactly four keys, no extension point" conflicts with `parseInbound`'s accepted optional `deviceId`. Ruling needed: amend the envelope rule to "four keys, plus server-stamped `deviceId` on host-bound envelopes", or hold the four-key line and move device attribution elsewhere (there is no elsewhere — the parser only reads the envelope).
2. **Uplink seq ownership.** "The server never stamps" must be scoped to the host's downlink stream, and the server named single producer (and seq owner) of the host-bound stream — otherwise the host's single ack watermark is unimplementable at N≥2.
3. **`resync.fromSeq` boundary semantics.** I propose `fromSeq` = the lowest seq the requester is missing, with replay correctness carried by event-id dedupe rather than seq correspondence — but the shipped client treats `fromSeq` as an opaque trigger, so the page is pinning intent, not observed behavior. Confirm the definition.
4. **Frame-size bound.** §3.2 gives the control plane explicit maxima; the data plane has none. Whether §4 states a MUST-accept minimum envelope size (my lean: yes, e.g. 1 MiB, guidance-grade) or stays silent.

Close codes are already emitted by the reference: `protocolViolation()` → `close(3400, "protocol violation")`; deliberate/local/dial-failed/dead-peer closes all use `1000`. §3.4 and §3.5(b) both forward-reference "the close code is §4's business."

**Blind spots:** `snapshotFrames` (`src/history.ts`) is unbounded — it accumulates the whole active branch's message text with no size cap — so a server-side "MUST accept ≥ 1 MiB" floor is one-sided: the host has no "MUST stay under 1 MiB" ceiling, so the floor protects no one and guarantees nothing. The host's single `Math.max` watermark means per-device seq passthrough on server→host looks natural from inside the server and silently breaks the host. The host's total trust in `deviceId` means only the server spec can state where the trust anchor must live.

**Answers:** (1) **`deviceId` server-stamping — adopt, with a refinement.** It survives INV-1 cleanly: §1.2's negative invariant forbids acting on the *payload* "beyond what the envelope and the relay rules require," and INV-4 already obliges the server to know each connection's device for grant enforcement. Stamping an *envelope* field from that authenticated binding is envelope/relay work, not payload interpretation — and it is the *only* honest source, since the host's trust is total. Refinement: `deviceId` is present **iff the frame is device-originated**; server-originated frames (`resync`, ack-only) carry none; and the server MUST NOT read the value from any device-supplied byte (envelope or in-frame). In-frame `deviceId` on `resume` stays, but `resume` is never forwarded host-ward — the host's `parseInbound` resume handling is defensive tolerance, not a relay path (`transport.test.ts` already pins that resume never surfaces). (2) **Close-code subsection — adopt.** Mandated by §3.4/§3.5(b)'s existing forward refs; two codes are literal in `transport.ts` (1000 deliberate, 3400 protocol violation). Diagnostic, MUST-NOT-require-parsing — the EV-11 pattern. Fold liveness + close codes into one subsection. (3) **`fromSeq` — both live; one precision.** Server-side: `fromSeq` = the requesting device's lowest missing seq. Host-side: advisory (ignored, full-branch replay). Precision: "lowest missing" is `lastAckedSeq + 1`, not `lastAckedSeq` — the owner's round-1 sentence conflates the two. Pin `fromSeq = lastAckedSeq + 1`, and state the host MUST NOT assume exact-range replay. (4) **Seq-continuity, ack-piggyback/ack-only, at-least-once — adopt all three**, with two precisions: (a) ack-only is **MAY**, not MUST, and it is server-emitted — the host reference never emits `frame:null`, it pings at WS level; (b) "at-least-once" must be named as the *ladder* (resume → cache → resync → full-branch replay), with dedupe-by-id on the client as the thing that makes it effectively-once — not a transport-level retransmit, which the code does not do. (5) **Frame-size bound — oppose a unilateral 1 MiB MUST-accept.** `snapshotFrames` is unbounded, so a conformant host can emit frames larger than any floor the server MUST accept. Either make it pure Guidance (byte-based ring budgeting, never silently truncate/split — truncation is an INV-1 transform), or pin a *paired* floor+ceiling sized against the reference host's largest legitimate frame (the `MESSAGES_SNAPSHOT` of a full session), which is not 1 MiB. Do not ship the floor alone. (6) **Genuinely ruling-worthy:** the `deviceId` fifth key + server-stamp trust rule (a security-model statement — the host cannot tell stamped from spoofed); the frame-size bound (paired floor+ceiling vs guidance-only — the only seam where host emission and server cache bound currently disagree). **Test-settled:** downstream seq ownership (host's single `Math.max` watermark / absence of any per-device seq map); seq continuity across tunnels; ack piggyback + 3400-on-inversion; host never emits ack-only; host ignores `fromSeq`; close codes 1000/3400; `resume` not forwarded / host tolerance (already pinned by existing tests).

**Testable claims (principal):** four-key host envelope (`Object.keys`); seq survives tunnel change; one inbound watermark forces merged seq; ack inversion → 3400; `fromSeq` advisory (`runReplay(3)` and `runReplay(999)` produce identical output frames); `deviceId` is host-trusted, therefore server-stamped-or-worthless; snapshot unboundedness refutes a 1 MiB floor.

### Round 4 — consolidation (consolidator job-21.6, 2026-09-02)

**Agreed design (all three seats converged; owner may write these without further ruling):**

1. **Per-direction envelope.** Upstream exactly `{v, seq, ack, frame}`; downstream `{v, seq, ack, frame}` plus one optional server-stamped `deviceId`. No other top-level key in either direction, ever; the evolution point is `v`, not keys.
2. **`deviceId` presence and trust.** Present iff device-originated; server-originated frames carry none. Server stamps from the authenticated device connection identity; MUST NOT read or trust any device-supplied byte (top-level or in-frame). Sole trust anchor (host verifies nothing). Survives INV-1 — envelope metadata is relay work, not payload interpretation.
3. **Resume-frame `deviceId` precision.** On `resume`, top-level is replaced by `frame.deviceId` (skeptic O1). Server MUST validate in-frame `deviceId` against the authenticated connection and MUST NOT serve bookkeeping for another device (cross-device watermark-peek vector).
4. **Frame slot closed set** — application frame | `null` (ack-only) | `{type:"resume", deviceId, lastAckedSeq}` | `{type:"resync", fromSeq}`. Only-these-control-frames rule within `v:1`; escape hatch = increment `v`; unknown `v` closes as protocol violation.
5. **`pi.resync.done` is not a control frame** — ordinary CUSTOM frame, relayed opaquely, MUST NOT be parsed for replay-end; fan-out needs no replay-end signal.
6. **`frame:null` ack-only is downstream-only** — host never emits it; server MAY emit to advance its watermark.
7. **`fromSeq` advisory** — host ignores it, replays full branch; server MUST NOT assume exact-range replay; recipients MUST tolerate duplicates/gaps (at-least-once, deterministic ids).
8. **Resume MUST NOT be forwarded host-ward** (both seats converged; wire consequence nil).
9. **Server-owned merged monotonic downstream seq** (single-watermark fact code-settled, O9).
10. **At-least-once delivery**, dedupe by deterministic event id; ladder: resume → cache → resync → full-branch replay.
11. **Ack piggyback + monotonicity** — ack MUST never decrease on a stream; violation closes 3400.
12. **Seq continuity across tunnels** — server MUST NOT assume first frame seq 1; MUST NOT reset/renumber at tunnel boundaries (O2 probe).
13. **Close codes** — §3.4/§3.5(b) forward refs resolved; `1000` deliberate, `3400` protocol violation; diagnostic, MUST NOT require client parsing.
14. **Cache miss resolves to resync** — including empty cache after fresh tunnel; never an error or fabricated frame.
15. **Revocation interaction** — takes effect at next delivery without host cooperation; outstanding resume cancelled; resync not recalled; per-device bookkeeping discarded.
