## Intent

The tunnel lifecycle, written on the page in full: the POST request (session
id, session name, cwd, host metadata; Bearer access token), the response
(`{tunnelId, url, tokenTtl}`), the signed self-describing token whose claims
are embedded (no server lookup state), single-use consumption at WS upgrade,
TTL default and bounds, DELETE semantics (idempotent, discards token state),
and the error taxonomy. The taxonomy must distinguish — in the document's own
words — the two credential failure classes the client treats differently:
invalid/expired/revoked credentials (retry with re-enrollment) versus
valid-but-insufficient-scope credentials (re-consent plus an administrator
scope grant), because the client renders different remedies for them. Also
specified: the no-double-create expectation while a tunnel is live, and the
consumed-token replay rejection at upgrade.

**Self-containment requirement:** the section cites no client type names and
no PI-SPEC sections; the error taxonomy is stated as the server's contract with
its own reason vocabulary, which the council-side check confirms is exhaustive
over the client's handled cases.

## Acceptance

- POST and DELETE are specified with complete request/response shapes and
  idempotency semantics.
- The signed URL's claims, TTL, single-use consumption, and replay rejection
  are specified to implementation precision.
- The error taxonomy covers, in the document's own vocabulary, every failure
  case the client distinguishes — council-side check against the client's
  TunnelError handling confirms zero gaps and zero contradictions.
