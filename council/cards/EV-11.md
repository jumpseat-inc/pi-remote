## Intent

The tunnel lifecycle, written on the page in full: the POST request (session
id, session name, cwd, host metadata; Bearer access token), the response
(`{tunnelId, url, tokenTtl}`), the signed self-describing token whose claims
are embedded (no server lookup state), single-use consumption at WS upgrade,
TTL default and bounds, DELETE semantics (idempotent, discards token state),
and the error taxonomy. The taxonomy must distinguish — in the document's own
words — the two credential failure classes the client treats differently:
invalid/expired/revoked credentials (retry with re-enrollment) versus
valid-but-insufficient-scope credentials (re-consent plus an administrator
scope grant), because the client renders different remedies for them. Also
specified: the no-double-create expectation while a tunnel is live, and the
consumed-token replay rejection at upgrade.

**Self-containment requirement:** the section cites no client type names and
no PI-SPEC sections; the error taxonomy is stated as the server's contract with
its own reason vocabulary, which the council-side check confirms is exhaustive
over the client's handled cases.

## Acceptance

- POST and DELETE are specified with complete request/response shapes and
  idempotency semantics.
- The signed URL's claims, TTL, single-use consumption, and replay rejection
  are specified to implementation precision.
- The error taxonomy covers, in the document's own vocabulary, every failure
  case the client distinguishes — council-side check against the client's
  TunnelError handling confirms zero gaps and zero contradictions.

**Approach**

The section becomes §3 with six subsections mirroring the lifecycle: **3.1 Tunnel objects and lifecycle** (what a tunnel is, its states, the one-connection rule, the no-double-create expectation), **3.2 Tunnel creation — `POST /tunnels`**, **3.3 The signed connection URL** (shape, token encoding, claims, TTL), **3.4 Token consumption at the WebSocket upgrade** (single-use mechanics, replay rejection, handshake failure statuses), **3.5 Tunnel deletion — `DELETE /tunnels/{tunnelId}`**, **3.6 Error taxonomy**. Each subsection fixes the wire contract normatively and carries at most one Guidance block (R2/R3). Everything below is restated on the page in the document's own vocabulary — no client type names, no PI-SPEC refs, no module paths (R5).

**Detailed position**

**§3.1 Tunnel objects and lifecycle.** A tunnel is a (tenant, host session instance) pair with a server-assigned `tunnelId` — an opaque, URL-safe string, globally unique across all tenants. Lifecycle normatively fixed as: *created* (POST success) → *live* (its single connection token consumed at a successful upgrade) → *spent* (connection ended) or *deleted* (DELETE). Normative rules: **exactly one connection token per tunnel and exactly one successful upgrade per tunnel** — a spent tunnel is never re-connectable; a new connection requires a new POST. This matches the reference behavior where a reconnect re-creates the tunnel, and it makes single-use concrete. **No-double-create: both sides, asymmetrically.** The host-side expectation is normative: a host MUST NOT issue a second create while a tunnel it created is live (the correct behavior is a local no-op with a notification, per the already-live acknowledgment). Server enforcement is MAY: a server MAY reject a create that would produce a second *live* tunnel for the same (tenant, sessionId) with `409`; if it does not enforce, it MUST issue a fresh tunnel. Spent tunnels MUST NOT block a new create.

**§3.2 POST /tunnels.** `Authorization: Bearer <access token>` REQUIRED (§2.6/§2.7 semantics). Body `application/json`, all four fields REQUIRED: `sessionId` (non-empty string, the host session's stable identifier, treated as opaque), `sessionName` (non-empty string, display name), `cwd` (non-empty string, informational — the server MUST NOT interpret it), `hostMetadata` (JSON object with string keys and string values, MAY be empty, informational). Validation the server MUST do: reject a missing/unparseable body, a missing or wrong-typed field, or a non-object `hostMetadata` with `400 invalid_request`. The server MUST accept all values within these maxima and MAY reject beyond them with 400: sessionId ≤ 128 chars, sessionName ≤ 256, cwd ≤ 1024, hostMetadata ≤ 32 entries with keys and values ≤ 256. Unknown request fields MUST be ignored (§2.1's rule inherited). The request carries **no TTL field**; the TTL is server-chosen (§3.3). Tenant is derived from the token alone (§2.6). Response **`200`** (not 201 — one shape) with `application/json`: `tunnelId` REQUIRED (URL-safe: unreserved URL characters only, so it embeds in paths without escaping), `url` REQUIRED (absolute `wss://` URL per §3.3), `tokenTtl` REQUIRED (positive integer seconds, equal to the issued token's actual validity window — the dialer converts it to an absolute expiry). `sessionId`/`sessionName`/`cwd`/`hostMetadata` are retained as tunnel metadata and relayed to granted client devices; nothing here interprets them (INV-1 spirit extended to metadata).

**§3.3 The signed URL.** Shape: `wss://<data-plane host>/<tunnelId>?token=<token>`. Normative: scheme MUST be `wss` (`ws` MUST NOT be issued); the token rides in exactly one query parameter named `token`; the path's final segment MUST equal the `tunnelId`; the authority MAY differ from the control-plane origin (a dedicated data-plane host is permitted); no userinfo, no fragment. The token is a **compact JWS** — three base64url segments — signed with a server-held key; hosts never hold signing keys. Guidance (one recommendation): asymmetric EdDSA with a rotating key pair, so token verification can be delegated to data-plane replicas. Claims, all binding: `tenantId` REQUIRED (MUST equal the creating enrollment token's `tenant_id` — INV-3's second contract point), `tunnelId` REQUIRED (MUST equal the path segment), `sessionId` REQUIRED (MUST equal the create request's `sessionId`), `exp` REQUIRED (epoch seconds), `jti` REQUIRED (unique per issued token — the consumption identity). `iat` SHOULD. **TTL:** default 60 seconds (SHOULD), normative bounds: an issued TTL MUST be ≥ 30 s and ≤ 300 s; `tokenTtl` in the response MUST equal `exp` minus mint time. Below the floor a dialer with a slow link cannot reliably reach the upgrade; above the ceiling a leaked URL lives too long (INV-5). Expiry is judged by the **server's clock** at upgrade only — the server MUST NOT rely on any host clock; a host's local pre-expiry check is advisory.

**§3.4 Consumption at the upgrade.** The upgrade is the WebSocket opening handshake — an HTTP GET against the URL. Authentication happens strictly before `101`: a server MUST NOT accept the upgrade and reject afterwards. Before completing the upgrade the server MUST, in order: verify the signature (`401` on failure); check `exp` against its clock (`401` on expiry); verify the path/claim bindings — path tunnelId = claim `tunnelId`, and the tunnel exists and is not deleted (`401` on any mismatch or absent tunnel); then **atomically consume** the token by recording its `jti` as consumed *before* sending `101`. A second handshake presenting a consumed `jti` MUST be rejected with **`409 token_consumed`** — the replay rejection — regardless of whether the original connection is still live. Guidance: the consumed-set entry need only live until `exp` plus a small skew allowance, after which expiry rejection alone covers the token, so the store garbage-collects itself. Handshake failure statuses (closed set): `400` malformed URL/token, `401` (bad signature, expired, binding mismatch, deleted/unknown tunnel), `409` replay, `5xx` data-plane unavailability; success is `101`. These are diagnostic for operators: the dialing side treats any non-101 as a failed handshake with one uniform remedy — create a fresh tunnel and dial again. It does not parse handshake statuses.

**§3.5 DELETE /tunnels/{tunnelId}.** Bearer-authenticated; tenant derived from the token. Idempotent. Success: **`204 No Content`**, no body. Unknown, already-deleted, expired, or **another tenant's** tunnel id: **`404`** — never 403, so existence is not leaked across tenants, and a repeated delete is indistinguishable from a first success. "Discards token state" precisely means the server MUST do all of: (a) invalidate any un-consumed connection token for that tunnel — subsequent upgrade attempts with it are rejected `401` per §3.4; (b) close the live data-plane connection if one exists (a normal WebSocket close); (c) release tunnel-scoped relay state (cached frame window, fan-out registrations); (d) record the id as deleted so further DELETEs return `404`. Deletion is permanent; the same session returns only via a fresh POST. Statuses: `204`, `401`/`403` per §2.7, `404`, `5xx`. A failed delete notification must be safe to ignore: the server SHOULD expire spent and abandoned tunnels itself, so a host that proceeds with local teardown despite a failed notification leaves no orphan.

**§3.6 Error taxonomy.** The §2.7 body (`{"error", "error_description"}`) and the never-merge-401/403 rule extend to every non-2xx in this section. Vocabulary: inherited `invalid_token`, `insufficient_scope`; new codes defined here — `invalid_request` (400), `tunnel_not_found` (404), `tunnel_already_live` (409, server-enforced double-create), `token_consumed` (409, replay), `internal_error` (5xx). The normative closed status partitions: POST `{200, 400, 401, 403, 409, 5xx}`; DELETE `{204, 401, 403, 404, 5xx}`; handshake `{101, 400, 401, 409, 5xx}`; a server emitting any other status on these surfaces is non-conformant. Coverage of the connecting side's classes, restated in the document's own words: (i) **invalid/expired/revoked credential** → control-plane `401`, remedy re-enrollment; (ii) **valid-but-insufficient scope** → `403`, remedy re-consent plus administrator grant (§5 surface); (iii) **connection-layer failure** (DNS/TCP/TLS, request never completes) → no HTTP status exists; no server obligation can be stated; the remedy is check network and retry; (iv) **response-shape defense** → a 2xx body deviating from §3.2/§3.5 is emitted only by a non-conformant server; the connecting side's validation failure maps to no status; (v) **failed delete notification** → any DELETE non-2xx other than 401/403/404 — with this taxonomy only 5xx can produce it; the host correctly proceeds with local teardown regardless (§3.5's expiry rule makes that safe); (vi) **handshake failures** → §3.4's closed set, uniform remedy re-create. **The one refinement of §2.7 this section must state explicitly:** `401` at a *control-plane* tunnel endpoint means the enrollment credential is dead (re-enroll); `401` at the *data-plane handshake* means the connection token is unusable (re-create the tunnel). Same status, different credential, different remedy — disambiguated by surface, and stated as such so §2.7's "status alone selects the remedy" rule stays true per-surface.

**Tradeoffs accepted**

- **409-on-POST renders as a generic server error for the host.** I keep server-side double-create enforcement MAY rather than MUST precisely because a host that (wrongly) triggers it would show a misleading "try again" line — a conformant host never sends the second create, so the gap is unreachable in conformant operation. If a future ruling makes enforcement MUST, the client-side reason set needs a new member, which per the closed-vocabulary discipline requires its own ruling — I flag this now.
- **`404`-only for DELETE idempotency, no `410` alternative.** One shape (R3), even though the reference client also treats 410 as success. Client leniency toward a status the page forbids is not a contradiction.
- **CamelCase tunnel-token claims (`tenantId`) vs §2.6's snake_case enrollment claims (`tenant_id`).** Deliberate: the connection token's declared claim vocabulary is already fixed in the host-side contract this section mirrors; renaming it here would break the one place the two documents must describe the identical token. The inconsistency is cosmetic and I'd rather keep the claim names identical across both descriptions of the same wire object.
- **`jti` REQUIRED** rather than SHOULD: single-use consumption needs a stable identity; hashing the raw token string is the fallback I'm deliberately *not* offering (R3).

**Testable claims**

1. **Upgrade-failure uniformity:** the transport treats any non-101 handshake outcome as a failed dial (`onerror` → the unreachable class) and re-creates the tunnel with backoff — it never parses handshake statuses. Falsifiable check: `src/transport.ts` lines ~380–400 resolve `opened=false` without reading any HTTP status. Therefore the page's 400/401/409/5xx handshake set cannot contradict the client, and the Skeptic should confirm the council check does not demand status-specific client behavior on the data plane.
2. **wss-only vs client leniency:** the client's scheme gate accepts both `ws` and `wss` (`WSS_SCHEME` in `src/tunnel.ts`), so a page mandating `wss`-only still passes every shipped fixture (`happyCreateResponder` issues `wss://`). Falsifiable: `bun test test/tunnel.test.ts` passes unchanged with a wss-only rule; it would fail only if the council check required the page to permit what the client merely tolerates.
3. **DELETE partition closure:** with DELETE statuses fixed to `{204, 401, 403, 404, 5xx}`, every observable client outcome is covered: 2xx and 404/410 → idempotent success, 401 → re-enrollment, 403 → re-consent, 5xx → the teardown-failure class with local teardown proceeding. A page that adds 400 or 409 to DELETE would open an uncovered gap the client folds into teardown-failure — the Skeptic's exhaustiveness check should fail any draft that widens that partition.
4. **TTL floor risk:** the 30 s floor must cover the host's worst path — one silent refresh (two HTTPS round-trips) plus POST plus dial — before the dialer's local advisory pre-check (`now() > expiresAt` → the url-expired class) rejects a valid URL. Falsifiable prediction: on a deployment with sub-second TLS round-trips this never fires; sustained >15 s round-trip latencies could, and the page's "pre-check is advisory" sentence is what keeps that a deployment concern rather than a conformance contradiction.
5. **Clock authority:** the host computes absolute expiry from its own clock, so host-server clock skew beyond the TTL causes the local pre-check to reject a token the server would accept. The page must place expiry authority solely in the server clock (§3.3) or the Skeptic can construct a skew scenario the two documents resolve differently.

## Cross-seam reading

The contract that already exists on the two sides of the seam, before this card writes anything:

**Host side (the shipped client — reference behavior only):**

- `src/tunnel.ts` `createTunnel` POSTs `${serverUrl}/tunnels` with `Authorization: Bearer <token>`, `content-type: application/json`, body `{sessionId, sessionName, cwd, hostMetadata}` — **camelCase keys**, and `hostMetadata` is `Record<string,string>`. It parses the response as `{tunnelId: string, url: string, tokenTtl: finite>0}` and validates `url` against `/^wss?:\/\//` (scheme only — **it never inspects the path or the query parameter name**), `tunnelId` against `typeof === "string"`, `tokenTtl` against finite > 0. It computes `expiresAt = now() + tokenTtl*1000` locally.
- `throwForStatus` is the client's real dispatch table: create/refresh → `401`⇒`enrollment_expired`/`unauthenticated`, `403`⇒`enrollment_rejected`/`forbidden`, `>=500`⇒`server_error`, **any other non-2xx** (so 400, 404, 409, 429…) ⇒ `server_error`; DELETE → `401`/`403` checked first, `404`/`410` handled *before* as idempotent success, network failure swallowed, and **everything else (including 5xx) ⇒ `teardown_failed`**. The body is never parsed for dispatch; the client acts on status alone (§2.7's stated design).
- `src/transport.ts` `rearm` = a fresh `POST /tunnels` **with no DELETE in between**, called on every reconnect. Any failed upgrade (any HTTP status from the handshake) collapses to `relay_unreachable`; `url_expired` is computed **client-side** from the local `expiresAt`, never from a server response.

**Server side (what §3 inherits):**

- §2.6 already fixed the JWT-claim convention as **snake_case** (`sub`, `tenant_id`, `scope`, `exp`, `iss`, `iat`).
- §2.7 already fixed the 401/403 rule (never merged; body `{"error","error_description"}`; 401=`invalid_token`; 403=`insufficient_scope`) and the body shape §3 must reuse.
- §2.5 fixed that `pi-remote:host` is the sole tunnel-operations scope.
- §1.4 INV-3 and INV-5 bound §3: the tunnel token is the second tenancy contract point, signed, short-lived, single-use, self-describing "where feasible".

**The four seams that will bite an implementer drafting this section:**

1. **camelCase vs snake_case is split across surfaces, not uniform.** The host-visible JSON body is camelCase (`sessionId`, `tunnelId`, `url`, `tokenTtl`) — these names are fixed by the host's parser and cannot be "restated". The JWT claims (§2.6) and the error body (§2.7) are snake_case. §7.2's prose says the tunnel token's claims are camelCase (`tenantId`, `tunnelId`, `sessionId`) — but **the host never decodes the tunnel token** (opaque, dialed as-is; only scheme-checked), so the token's claim names are a server-internal contract and §3 is *free to align them with §2.6's snake_case* (`tenant_id`, `tunnel_id`, `session_id`). Importing §7.2's camelCase claim names would contradict §2.6. This is the single most likely contradiction the council check would catch.
2. **§7.2's URL path is `/tunnelId` and the token param is `?token=`, but the test fixture uses `wss://tunnel.example/live?sig=abc`.** The fixture is not normative — the host's regex accepts any `wss?://` — so §3 must *fix* the normative shape (`wss://<data-plane-origin>/<tunnelId>?token=<jwt>`) as a server-emitted-and-server-validated contract, and the "zero contradictions" check must not treat the fixture's `sig`/`/live` as a wire requirement.
3. **"No server lookup state" in the card's Intent is over-broad and, taken literally, false.** Self-describing means claim *verification* needs no lookup. But single-use consumption (replay rejection) is inherently stateful, and "DELETE discards token state" means a post-DELETE token whose signature and `exp` still verify must still be rejected — which requires a live-tunnel existence check. §3 must name **two bounded pieces of required server state** — the consumed-token (`jti`) record (retained ≥ TTL) and the live-tunnel existence record — or a conformant implementer will claim statelessness and get replay rejection wrong.
4. **The client's create-path error mapping is coarser than the server's vocabulary.** On create, 400 (`invalid_request`), 409 (`tunnel_already_live`), and 5xx all land in one host class (`server_error`), while DELETE's 5xx lands in a *different* class (`teardown_failed`). A taxonomy that says "5xx always ⇒ server_error" contradicts `tunnel.test.ts` (`deleteTunnel 500 → teardown_failed`). The section must state the server's fine vocabulary **and** the host's coarse grouping of it, without pretending the host distinguishes 400 from 500.

**Blind spots**

**The import/data-pipeline view (`tunnel.ts`'s author) cannot see:** that the reconnect path POSTs a fresh tunnel with no prior DELETE (`transport.ts` `rearm`). From inside the REST client, "no-double-create" naturally means "reject a second POST for a session that has a row" — but that reading deadlocks reconnection. Only the transport side can see that "live" must key on *host socket connected*, not *tunnel row exists*.

**The render-path/frontend view (`transport.ts`'s author) cannot see:** that the server's WS-upgrade rejection status codes (401 expired, 403 replay, 404 unknown) are all invisible to it — every failed handshake is `relay_unreachable`, and `url_expired` is a purely local pre-check. So a frontend-vantage position will under-specify the upgrade failure vocabulary as "doesn't matter, it's all unreachable", when those codes *are* normative server behavior the council check reads against.

**The §2-author view (enrollment side) cannot see:** that the tunnel response body is camelCase and that the token is opaque to the host — so it will want to harmonize everything to snake_case and miss that §3 must deliberately hold two conventions side by side (camelCase host JSON body, snake_case JWT claims + error body).

**The card-intent view cannot see:** that "no server lookup state" collapses two different properties (claim-verification statelessness vs. replay/post-DELETE statefulness). This is the one phrase in the card that earns a reframe.

**Reframe**

The framing is sound — the card names the right surfaces, the right single-use/replay/DELETE questions, and the right 401-vs-403 inheritance. One reframe, scoped to the card's own Intent:

> **Reframe "no server lookup state" to "no lookup required to *interpret the token's claims*."** Single-use consumption and DELETE-discard are stateful by definition; the section must name the two bounded server-state pieces (consumed-`jti` set retained ≥ TTL, and live-tunnel existence) as *required*, not as an embarrassing exception to a claimed statelessness.

Second, a definition the card leaves open and must not leave open: **"live" = the tunnel's host data-plane WebSocket is currently connected.** The 409 no-double-create key is socket state, never row existence, precisely because the reconnect path POSTs without DELETE.

Beyond those two sharpenings, the design writes itself. Concrete §3:

**§3.1 Endpoint location and authentication.** Tunnel endpoints are fixed paths on the configured control-plane origin (the origin of §2.1 discovery) — `POST /tunnels`, `DELETE /tunnels/{tunnelId}` — not discovered. Every request MUST carry `Authorization: Bearer <access_token>`; §2.7's 401/403 contract governs, and is not restated. Tenancy is derived from the token's `tenant_id` alone (§2.6); the body carries no tenant field, and any tenant-like body field MUST be ignored.

**§3.2 `POST /tunnels`.** Request body (all REQUIRED, camelCase — the host wire names): `sessionId` non-empty string (opaque; the logical connection id), `sessionName` non-empty string, `cwd` non-empty string, `hostMetadata` object of string→string (server MUST store verbatim, MUST NOT interpret — INV-1). Validation: malformed JSON / missing or mistyped / empty-string field ⇒ `400` `invalid_request`; unknown fields MUST be ignored. Success ⇒ `200 OK`, body `{tunnelId, url, tokenTtl}` — `tunnelId` REQUIRED string, server-assigned, globally unique, URL-path-segment-safe; `url` REQUIRED absolute `wss:` string; `tokenTtl` REQUIRED positive integer seconds. (camelCase here is a wire contract the host parses; do not "snake_case" it.) No-double-create: if a live tunnel already exists for the authenticated `(tenant_id, sessionId)` pair, the server MUST answer `409` `tunnel_already_live`; otherwise POST MUST succeed. "Live" is defined in §3.1-adjacent prose as *host data-plane socket connected* — a prior never-connected tunnel (POST succeeded, host never dialed) or a closed socket does NOT block; a new POST MAY (SHOULD) supersede any prior unconsumed token for that session, which is harmless regardless (single-use + `exp`).

**§3.3 The signed one-time URL.** Shape: `wss://<data-plane-origin>/<tunnelId>?token=<jwt>` — `wss` (TLS) MUST, path MUST be exactly one segment equal to `tunnelId`, token MUST ride in a query parameter named `token`. Token encoding: a JWT (three dot-separated base64url segments, RFC 7519), signed by a server-held key (algorithm stack-neutral; MUST verify signature before trusting claims; mint-and-verify are same-side, so the alg is server-internal). Claims — **snake_case, aligned with §2.6, not §7.2's prose**: `tenant_id` REQUIRED (INV-3 tenancy), `tunnel_id` REQUIRED (MUST equal the path segment — a mismatch ⇒ `401 invalid_token`), `session_id` REQUIRED (echo of the POST), `exp` REQUIRED (= issuance + `tokenTtl`), `jti` REQUIRED (unique, the replay marker), `iat` SHOULD, `iss` SHOULD, `aud` SHOULD (`wss:<data-plane-origin>`). State requirement made explicit: claim verification is lookup-free; replay rejection and post-DELETE rejection are not — the server MUST retain (a) consumed `jti` values for ≥ `tokenTtl` after issuance, and (b) live-tunnel existence.

**§3.4 Token lifetime.** Default `tokenTtl` 60 s; bounds `[5, 300]` s, normative (server MUST emit within them; configured values clamp to the nearest bound). Binding rule: `exp − iat == tokenTtl`, so the host's locally-computed `expiresAt` and the server's enforcement window are the same number. Upgrade MUST reject any token past `exp` ⇒ `401` `token_expired`. Guidance (non-normative): allow a few seconds' clock leeway when comparing `exp` to the server clock, and retain consumed `jti` for `tokenTtl + leeway`; the host's local pre-emption and the server's `exp` check are independent clocks, and leeway absorbs a slightly-ahead host clock.

**§3.5 Single-use consumption and replay rejection.** At upgrade: verify signature + claims + path-binding + `exp` + live-tunnel existence; then **atomically** mark `jti` consumed and complete `101`. Two simultaneous upgrades with one token: exactly one `101`, the other gets the replay rejection. Rejections are HTTP responses before `101`, with the standard error body: `401` `token_expired` (past `exp`), `401` `invalid_token` (unverifiable / malformed / claim-path mismatch), `403` `token_already_used` (replay — authenticates but spent), `404` `unknown_tunnel` (deleted or never existed). These are data-plane rejections, explicitly scoped as NOT the §2.7 control-plane 401/403 contract (that contract governs enrollment-token requests only); the 401/403 semantics here mirror it (401 = does not authenticate, 403 = authenticates but no longer authorized). Post-upgrade socket close codes are §4's business — §3 defers there.

**§3.6 `DELETE /tunnels/{tunnelId}`.** `tunnelId` is one URL-encoded path segment; MUST be tenant-scoped — a tunnel outside the token's tenant is treated as non-existent (`404`, no existence leak). Success ⇒ `204 No Content`, empty body. `404` (never existed) and `410` (already deleted) are **idempotent success**, empty body, not errors — repeat DELETE MUST NOT be a 5xx or 409. "Discards token state" precisely: on successful DELETE the server MUST (a) terminate the host socket if connected (close code per §4), (b) delete the tunnel's existence record so a subsequent upgrade of even an unexpired, signature-valid token gets `404`, and (c) purge the consumed-`jti` record. `401`/`403` per §2.7 still apply; any other 4xx/5xx is a server fault that the host reports but does not retry (best-effort teardown).

**§3.7 Error taxonomy (the closed vocabulary).** Body shape inherited from §2.7: `{"error":"<code>","error_description":"<sentence>"}`; the host acts on status alone, never the body. One table, columns *status / surface / `error` code / meaning / host-side class (restated) / remedy*:

| Status | Surface | `error` | Meaning | Host class | Remedy |
|---|---|---|---|---|---|
| 401 | POST, DELETE | `invalid_token` | credential invalid/expired/revoked | re-enrollment | re-enroll (§2.7) |
| 403 | POST, DELETE | `insufficient_scope` | valid, missing `pi-remote:host` | re-consent | re-consent + admin grant (§2.7) |
| 400 | POST | `invalid_request` | malformed/mistyped body | generic retryable | correct the request |
| 409 | POST | `tunnel_already_live` | live tunnel exists | generic retryable | defense-in-depth; not normally seen (host refuses while live) |
| 5xx | POST | `server_error` | internal fault | generic retryable | retry |
| 5xx/other 4xx | DELETE | (any) | teardown fault | teardown failure, non-blocking | local teardown proceeds; no retry |
| — (no response) | any | — | network/DNS/TCP/TLS/discovery | unreachable | check network/URL |
| 2xx malformed | POST | — | success body fails response table | validation | server conformance violation; discard response |
| 401 | WS upgrade | `token_expired` / `invalid_token` | expired / unverifiable | dial-failed | re-dial ⇒ rearm (fresh POST) |
| 403 | WS upgrade | `token_already_used` | replay | dial-failed | re-dial ⇒ rearm |
| 404 | WS upgrade | `unknown_tunnel` | deleted/absent | dial-failed | re-dial ⇒ rearm |

**Testable claims**

These are disagreements-as-tests, each runnable against the repo as it stands:

1. **The tunnel token is opaque to the host.** `grep -E "tenant_id|tenantId|tunnel_id|session_id|decode|atob|jwt|jti" src/tunnel.ts src/transport.ts` must return nothing that parses the `url`'s query string — only the `WSS_SCHEME`/`WS_URL_RE` scheme checks. If any host code reads a token claim, §3's claim naming is *not* server-internal and must match the host, contradicting the "align with §2.6 snake_case" choice.
2. **`rearm` POSTs without DELETE.** Trace `src/transport.ts` `dialLoop`'s `deps.rearm()` path: it must reach `createTunnel` without any `deleteTunnel` call. This is what forces "live = socket connected, not row exists"; if a §3 draft keys 409 on row existence, reconnection deadlocks and this trace refutes it.
3. **The client's create/delete error mapping is asymmetric.** `test/tunnel.test.ts` already pins `deleteTunnel 500 → teardown_failed` while `createTunnel 500 → server_error`. A §3 taxonomy claiming uniform "5xx ⇒ server_error" is contradicted by the existing test; the taxonomy must reproduce this asymmetry.
4. **The client lumps 400/409/5xx on create.** `throwForStatus` has no branch between `403` and `>=500` for the create/refresh kinds, so 400 and 409 fall through to `server_error`. Any §3 statement implying the host renders a distinct remedy for `invalid_request` or `tunnel_already_live` is a contradiction; the taxonomy must mark them one host class.
5. **§2.6 claim convention is snake_case.** `grep "tenant_id" docs/SERVER-SIDE-SPEC.md` at §2.6 vs any camelCase claim names §3 introduces — a §3 that emits `tenantId` (camelCase) contradicts §2.6's own JWT table and fails the "must not contradict §2" check even though §7.2's prose uses camelCase.
6. **Clock-skew boundedness.** With `tokenTtl >= 5` and default 60, a host/server clock delta up to ~`tokenTtl/2` is absorbed by the host's pre-emption; beyond it the host dials a server-expired URL, gets `401` at upgrade, and self-heals via rearm. Falsifiable claim: no code path depends on the two clocks agreeing within less than the TTL; verify by inspection that `expiresAt` is the *only* expiry the host consults before dialing.
